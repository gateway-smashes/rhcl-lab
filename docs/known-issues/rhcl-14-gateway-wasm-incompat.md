# RHCL 1.4 — gateway data plane down after upgrade (wasm-shim ↔ Envoy incompatibility)

> **RESOLVED in RHCL 1.4.1 — but ONLY on Sail-managed gateways (class
> `istio`).** Validated 2026-07-08 on a fresh cluster (`cluster-mck9f`,
> OCP 4.20.27, OSSM 3.3.5, Istio v1.26.4). Minimal stack (Gateway istio +
> HTTPRoute + AuthPolicy api-key + RateLimitPolicy) enforced correctly
> end-to-end: `401` without key, `200` with key, `429` past the limit —
> no `000`s.
>
> ⚠️ **The ingress-operator-managed `openshift-default` gateway class
> STILL BREAKS on 1.4.1** (same cluster, same day): its bundled Envoy
> rejects the wasm field and loops the remote wasm fetch until the
> gateway pod is **OOMKilled** (CrashLoopBackOff, exit 137). The lab
> therefore flipped `gateway_api_gatewayclass_name` to `istio` by
> default — pair `openshift-default` only with a 1.3.x pin.
>
> ⚠️ **Memory sizing on the istio class**: a policy-heavy gateway (10
> listeners, ~8 AuthPolicies + RateLimit + TokenRateLimit ⇒ merged wasm
> configs of ~44 KB) needs more than the default 1Gi proxy limit — the
> wasm warm-up alone peaks >1.1 GiB and the pod OOMs in a loop at 1Gi.
> Fix that sticks: set proxy resources on the Sail **Istio CR** (the
> istiod reverts direct Deployment patches and ignores
> `sidecar.istio.io/proxyMemoryLimit` annotations on the Gateway):
>
> ```yaml
> spec:
>   values:
>     global:
>       proxy:
>         resources:
>           requests: { cpu: 100m, memory: 256Mi }
>           limits:   { cpu: "2",  memory: 4Gi }
> ```
>
> AUTOMATION GAP (follow-up): the lab roles don't yet manage the Sail
> `Istio`/`IstioCNI` CRs — on cluster-mck9f they were created manually
> during validation. gateway_api role should provision them when the
> class is `istio`.
>
> Root-cause validation details:
>
> - The `allow_on_headers_stop_iteration` unknown-field **warning still logs**
>   at EnvoyFilter injection time, but it is non-fatal — Envoy accepts the
>   config and warms the listeners normally.
> - The decisive fix: **1.4.1 serves the wasm module from an in-cluster
>   service** (`kuadrant-operator-wasm.openshift-operators.svc:8082/plugin.wasm`,
>   sha256-pinned) instead of 1.4.0's unstable remote registry fetch that
>   never converged and blocked listener warming.
> - Conclusion: the 1.4.0 failure was a **product bug, not an environment
>   vice** — the same symptom class cannot be reproduced on 1.4.1.
>
> Gotcha rediscovered during validation: a cluster-wide Authorino only reads
> API-key Secrets from its own namespace unless the AuthPolicy sets
> `spec.rules.authentication.<name>.apiKey.allNamespaces: true` (a key in a
> different namespace fails with 401 despite the policy showing Enforced).

## Summary

After upgrading **RHCL / Kuadrant `rhcl-operator` 1.3.4 → 1.4.0** (alongside
ServiceMesh `servicemeshoperator3` 3.0.11 → 3.1.0, Istio **v1.26.2**), the
Istio Gateway data plane stops serving traffic. The gateway pod reports
`1/1 Ready`, but Envoy never programs its listeners, so **every request to the
gateway returns `000`** (connection/TLS failure) — even when hitting the
LoadBalancer (ELB) IP directly with `--resolve`.

Consequence: no traffic flows through `rhcl-apps-gateway`, so
`istio_requests_total` is empty and the Developer Portal / console Analytics
show no data. The control plane looks healthy (`Kuadrant` CR `Ready=True`,
`Istio` CR `Healthy`), which masks the problem.

## Affected versions (observed)

| Component | Version |
|---|---|
| `rhcl-operator` (Kuadrant) | **v1.4.0** (upgraded from v1.3.4) |
| `servicemeshoperator3` (Sail) | v3.1.0 (from v3.0.11) |
| Istio (Sail `Istio` CR) | **v1.26.2** |
| wasm-shim image | `registry.access.redhat.com/rhcl-1/wasm-shim-rhel9@sha256:db9a00dc…` |
| Gateway proxy | `openshift-service-mesh/istio-proxyv2-rhel9` (v1.26.2) |

## Symptoms / evidence

Gateway pod logs (`oc -n openshift-ingress logs <rhcl-apps-gateway pod>`):

```
warning  envoy config  Unknown field: type envoy.extensions.filters.http.wasm.v3.Wasm
         reason INVALID_ARGUMENT: invalid JSON in envoy.extensions.filters.http.wasm.v3.Wasm
         @ config: message envoy.extensions.wasm.v3.PluginConfig … no such field: 'allow_on_headers_stop_iteration'
warning  envoy wasm  Wasm remote code fetch is unstable and may cause a crash
warn     xdsproxy  sendDownstreamDelta took 56.243s
error    failed scraping envoy metrics: …localhost:15090/stats/prometheus: context deadline exceeded
```

- The **wasm-shim config generated by Kuadrant 1.4** includes the Envoy field
  `allow_on_headers_stop_iteration`, which the **Envoy 1.26.2** shipped by
  OSSM 3.1 does not recognize.
- Envoy also attempts an **unstable remote wasm code fetch**, blocking listener
  warming. Combined with multi-tens-of-seconds xDS pushes, the gateway never
  becomes functional.

Reachability checks (all `000`, from inside the cluster):

```
# via the *.apps hostname (resolves to the OpenShift router, NOT the gateway ELB)
curl -sk https://banking-api-connectivity.apps.<cluster>/api/echo            # 000
# directly at the gateway ELB IP with correct SNI/Host
curl -sk --resolve banking-api-connectivity.apps.<cluster>:443:<ELB_IP> \
     https://banking-api-connectivity.apps.<cluster>/api/echo                 # 000
```

Kuadrant injects the wasm via **EnvoyFilters** (not a WasmPlugin):
`oc -n openshift-ingress get envoyfilter` →
`kuadrant-rhcl-apps-gateway`, `kuadrant-auth-…`, `kuadrant-ratelimiting-…`,
`kuadrant-tracing-…`.

## Root cause

Version incompatibility introduced by **RHCL 1.4**: the 1.4 wasm-shim emits an
Envoy wasm `PluginConfig` that the bundled OSSM 3.1 / Istio 1.26.2 Envoy
rejects, and relies on a remote wasm fetch that does not converge. This is a
**control-plane ↔ data-plane (Kuadrant ↔ Istio) compatibility regression**, not
a cluster/networking misconfiguration.

## What does NOT fix it

- **Restarting the gateway** (`rollout restart deploy/rhcl-apps-gateway-openshift-default`):
  pod returns to `1/1` but Envoy still rejects the config.
- **Reinstalling the operators at the same versions**: the `stable` channel of
  `redhat-operators` currently advertises only `rhcl-operator.v1.4.0`, and a
  reinstall regenerates the same broken EnvoyFilter.

## Remediation options

1. **Escalate to Red Hat (recommended).** This is a product regression in
   RHCL 1.4 GA. Open a support case referencing the `allow_on_headers_stop_iteration`
   wasm field rejection and the OSSM/Istio version in use (1.26.2). Ask for the
   supported OSSM/Istio matrix for RHCL 1.4 and/or a fixed wasm-shim z-stream.

2. **Roll back the Kuadrant operator to 1.3.4** (last known-good). Caveats:
   - The current `stable` channel only carries 1.4.0, so a plain OLM downgrade
     is not available. You must point a pinned `CatalogSource` at an older
     RHCL 1.3 index image, then downgrade — or re-provision the (ephemeral) lab
     on 1.3 via `automation/` with a 1.3 catalog pin.
   - Keep `servicemeshoperator3` at 3.1.0 (the Istio data plane itself is
     healthy; only the Kuadrant wasm config is incompatible).

3. **Prevent re-upgrade churn.** The `rhcl-operator` Subscription is
   `installPlanApproval: Automatic` (that is how 1.3.4 auto-upgraded to 1.4.0).
   Set it to `Manual` so versions don't move again unexpectedly:
   `oc -n kuadrant-system patch subscription rhcl-operator --type=merge -p '{"spec":{"installPlanApproval":"Manual"}}'`

## Workaround for demos (no gateway)

The Developer Portal and `banking-api` remain fully functional **bypassing the
gateway** via the backend's own OpenShift Route
(`banking-api-v1-rhcl-apps.apps.<cluster>`), which goes straight to the pod
(no Envoy/Authorino). Useful for showing the API, OpenAPI/Swagger and the portal
flows while the gateway issue is being resolved. Gateway-dependent features
(API-key enforcement, rate limiting, per-API traffic metrics) require the fix
above.
