# Item 10 — Load balancing of one API across sites / cloud providers

## Requirement

| Item | Requirement |
|------|-------------|
| **10** | Without third-party software, **load-balance the same API** hosted on **different sites / cloud providers**, using rules such as **weight** and **geographic proximity**. |

Satisfied natively by **Red Hat Connectivity Link (Kuadrant) `DNSPolicy`** with `loadBalancing`. No external GSLB / traffic manager is used — the load balancing is expressed in Route53 records that Kuadrant writes and reconciles from **each cluster independently**.

---

## PoC topology (live)

Same hostname `banking-api-connectivity.poc.rhcl.com.br` served by **two clusters in two clouds**, both fronting the identical `banking-api` app behind their own RHCL Gateway:

```
                    client → banking-api-connectivity.poc.rhcl.com.br
                                        │  (Route53, zone poc.rhcl.com.br)
                                        ▼
                              klb.poc.rhcl.com.br            ← weighted round-robin
                                        │
                                geo-na.klb.poc.rhcl.com.br   ← geo bucket (GEO-NA default)
                              ┌─────────┴─────────┐
                weight 120 ▼                       ▼ weight 120
        AWS  us-east-2                       Azure  centralus
   rhcl-apps-gateway (ELB)             rhcl-apps-gateway (LB IP 20.106.44.162)
   ...elb.amazonaws.com                banking-api-v1 / v2
```

| Cluster | Cloud / Region | Gateway address | DNSPolicy ownerID |
|---------|----------------|-----------------|-------------------|
| `mycluster.sandbox546` | AWS `us-east-2` | `…elb.amazonaws.com` | `tmycba6c` |
| `cluster-azure.f54tx` | Azure `centralus` | `20.106.44.162` | `2867jg2l` |

Both DNSPolicies target the same Route53 hosted zone `Z04631642WLNFO9ZK0A5U` and both report `Enforced=True`.

## Configuration

Each cluster's `DNSPolicy` (namespace `openshift-ingress`, targeting `rhcl-apps-gateway`) carries the `loadBalancing` block. Enabling it is what turns the per-cluster record into the shared `klb` weighted tree — **without it, the two clusters fight over the record type** (`A` vs `CNAME` conflict) and only one site publishes.

```yaml
apiVersion: kuadrant.io/v1
kind: DNSPolicy
metadata:
  name: rhcl-apps-gateway-dns
  namespace: openshift-ingress
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: Gateway
    name: rhcl-apps-gateway
  providerRefs:
    - name: rhcl-dns-credentials
  loadBalancing:
    defaultGeo: true        # this geo is the catch-all bucket
    geo: GEO-NA             # Route53 geo code for this cluster
    weight: 120             # relative weight inside the geo bucket
```

Via automation (`automation/roles/dns/`):

```bash
RHCL_DNS_PROVIDER=aws \
RHCL_DNS_POLICY_ENABLED=true \
RHCL_DNS_POLICY_LOAD_BALANCING_ENABLED=true \
RHCL_DNS_POLICY_DEFAULT_GEO=true \
RHCL_DNS_POLICY_GEO=GEO-NA \
RHCL_DNS_POLICY_WEIGHT=120 \
ansible-playbook automation/playbooks/dns-install.yml
```

## Live demonstration

### 1. Show the weighted DNS tree Kuadrant built in Route53

```bash
HOST=banking-api-connectivity.poc.rhcl.com.br
NS=$(dig +short NS poc.rhcl.com.br | head -1)
dig +noall +answer $HOST @${NS}
```

Actual output (2026-07-09):

```
banking-api-connectivity.poc.rhcl.com.br. 300 IN CNAME klb.poc.rhcl.com.br.
klb.poc.rhcl.com.br.        300 IN CNAME geo-na.klb.poc.rhcl.com.br.
geo-na.klb.poc.rhcl.com.br.  60 IN CNAME rbvayn-1p55s8.klb.poc.rhcl.com.br.   # Azure leaf
geo-na.klb.poc.rhcl.com.br.  60 IN CNAME ...us-east-2.elb.amazonaws.com.       # AWS leaf
rbvayn-1p55s8.klb.poc.rhcl.com.br. 60 IN A 20.106.44.162
```

The `geo-na` node returns **both** cluster leaves; Route53 picks one per query by weight.

### 2. Show traffic actually splitting across both clouds

```bash
HOST=banking-api-connectivity.poc.rhcl.com.br
NS=$(dig +short NS poc.rhcl.com.br | head -1)
for i in $(seq 1 20); do
  dig +short geo-na.klb.poc.rhcl.com.br @${NS} | grep -E 'elb|klb' | head -1
done | sort | uniq -c
```

Actual output (equal weights 120/120):

```
  11 ...us-east-2.elb.amazonaws.com.     # AWS  ~55%
   9 rbvayn-1p55s8.klb.poc.rhcl.com.br.  # Azure ~45%
```

### 3. Prove each HTTP request is served by a different cluster

The echo endpoint reflects the serving gateway pod in `x-envoy-peer-metadata-id`:

```bash
HOST=banking-api-connectivity.poc.rhcl.com.br
AWS=...us-east-2.elb.amazonaws.com ; AZ=20.106.44.162
curl -sk --resolve ${HOST}:443:$(dig +short $AWS|head -1) https://${HOST}/api/echo | jq -r '.headers."x-envoy-peer-metadata-id"'
curl -sk --resolve ${HOST}:443:${AZ}                       https://${HOST}/api/echo | jq -r '.headers."x-envoy-peer-metadata-id"'
```

```
router~…~rhcl-apps-gateway-openshift-default-c58479895-9kwlh.openshift-ingress…   # AWS pod
router~…~rhcl-apps-gateway-openshift-default-c58479895-b789l.openshift-ingress…   # Azure pod
```

Same URL, two clusters, two clouds — HTTP 200 from both.

## Steering rules to demo

### Weight (shift the ratio)

Bias traffic 2:1 toward Azure by raising its weight (apply on the **Azure** cluster):

```bash
oc --context azure patch dnspolicy rhcl-apps-gateway-dns -n openshift-ingress --type=merge \
  -p '{"spec":{"loadBalancing":{"defaultGeo":true,"geo":"GEO-NA","weight":240}}}'
```

Re-run step 2 after ~60s (record TTL) — Azure now wins ~2/3 of queries.

### Geographic proximity

Put each cluster in its own geo bucket so resolvers are steered by client location:

```bash
# Azure serves South America; stop being the global default
oc --context azure patch dnspolicy rhcl-apps-gateway-dns -n openshift-ingress --type=merge \
  -p '{"spec":{"loadBalancing":{"defaultGeo":false,"geo":"GEO-SA","weight":120}}}'
# AWS stays the GEO-NA default (catch-all for everyone else)
```

Route53 then answers Brazilian resolvers with the Azure leaf and everyone else with the AWS default.

**Geo codes** (Route53): `GEO-NA`, `GEO-SA`, `GEO-EU`, `GEO-AF`, `GEO-AS`, `GEO-OC`, `*` (default). Exactly one cluster should keep `defaultGeo: true`.

## Operability note (this PoC)

The AWS cluster runs RHCL 1.4.1, which has a gateway-killing operator regression; it is currently mitigated per
[`docs/known-issues/rhcl-141-envoyfilter-churn-gateway-oom.md`](../docs/known-issues/rhcl-141-envoyfilter-churn-gateway-oom.md).
DNS load balancing itself is unaffected — the records are already reconciled — but **applying a weight/geo change on the AWS side** requires the short operator runbook in that doc. Weight/geo changes on the **Azure** cluster (RHCL 1.3.5) apply normally.

## Out of scope

- Active health-checking / failover between sites (DNS weight is not liveness-aware; use gateway/route health + short TTL, or add Route53 health checks).
- Session affinity across sites (each DNS answer is independent).
