# Item 66 — Auditoria e rastreabilidade de chamadas

## Requisito demonstrado


| Item   | Requisito                                                                                                                                                             |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **66** | Capacidade de **auditoria e rastreabilidade de chamadas** que passam pelo gateway, com registro estruturado e correlação de ponta a ponta entre todos os componentes. |


O RHCL 1.3 atende este requisito com **access logs estruturados (JSON)** no gateway, contendo campos de auditoria e correlação:


| Capacidade | Como o RHCL implementa |
|---|---|
| **Registrar cada chamada** | EnvoyFilter injeta access log JSON no stdout do gateway (100% das requests) |
| **Identificar quem chamou** | Campos `client_ip`, `x_forwarded_for`, `consumer_id` (identidade do Authorino) |
| **Registrar o que foi chamado** | Campos `method`, `path`, `authority`, `route_name` |
| **Registrar o resultado** | Campos `response_code`, `response_flags`, `duration_ms`, `auth_reason` |
| **Rastrear de ponta a ponta** | `request_id` (UUID gerado pelo Envoy) aparece no access log, trace, logs do Authorino e Limitador. Para correlação pelo cliente, use `flow_trace_id` (header `x-flow-trace-id`) |
| **Correlacionar com trace** | Campo `traceparent` (W3C Trace Context) permite link direto com trace no Tempo |
| **Auditar segurança TLS** | Campos `downstream_tls_version`, `downstream_tls_cipher` |


Referências:
- [RHCL 1.3 — Observability](https://docs.redhat.com/en/documentation/red_hat_connectivity_link/1.3/html/observability/rhcl-observability)

## Diferença entre req038, req035 e req066

| Aspecto | req038 | req035 | **req066** |
|---|---|---|---|
| **Função** | Traces e métricas OTel | Log de erros do gateway | **Auditoria e rastreabilidade** |
| **O que captura** | Spans OTLP (timing) | Apenas erros (≥400) | **Todas as requests (100%)** |
| **Destino** | Tempo (via Collector) | Arquivo no Collector | **stdout do gateway** |
| **Onde ver** | Observe → Traces | `oc exec` no Collector | **`oc logs` do gateway** |
| **Consumer ID** | Não | Sim | **Sim** |
| **Auth reason** | Não | Sim | **Sim** |
| **TLS info** | Não | Não | **Sim** |
| **Trace de negócio** | Não | Sim | **Sim** |

Os três são **complementares**:
- **req038** = rastreabilidade de performance (spans com timing de cada componente)
- **req035** = auditoria de erros centralizada (erros via OTLP para arquivo/SIEM)
- **req066** = registro de auditoria completo (todas as chamadas no stdout com identidade)

## Arquitetura

```text
Client
  │  curl -H "x-flow-trace-id: audit-001" -H "api-key: alice-gold-secret"
  │  (Envoy gera x-request-id automaticamente)
  ▼
Gateway / Envoy (istio-proxy)
  │  ├─ ACCESS LOG (req066)  → JSON no stdout
  │  │    {request_id (Envoy UUID), flow_trace_id (cliente),
  │  │     consumer_id, method, path, response_code,
  │  │     traceparent, auth_reason, tls_version, ...}
  │  │
  │  ├─ TRACE SPAN (req038)  → OTLP para Tempo
  │  │    Spans com timing: gateway → wasm-shim → auth → ratelimit
  │  │
  │  └─ ERROR LOG (req035)   → OTLP para Collector → arquivo
  │       Apenas 4xx/5xx com PII scrub
  ▼
RHCL policies: AuthPolicy / RateLimitPolicy
  │  Authorino ─── log com request_id    ← consumer_id injetado
  │  Limitador ─── log com request_id    ← rate limit check
  ▼
Correlação: flow_trace_id (cliente) → access log → request_id (Envoy) → traces/Authorino/Limitador
```

| Evidência | Como demonstrar |
|---|---|
| **Access log JSON** | `oc logs` do gateway mostra entradas JSON para cada request |
| **Identidade do consumidor** | `consumer_id` preenchido com nome do consumer para rotas autenticadas |

## Notas

- O EnvoyFilter de access log coexiste com os EnvoyFilters do req038 (tracing) e req035 (error log).
- Em produção, os access logs do stdout podem ser coletados por ClusterLogForwarder (OpenShift Logging) para envio centralizado a Loki, Splunk ou outro SIEM.
- O `x-request-id` é **sempre** gerado pelo Envoy (sobrescreve qualquer valor enviado pelo cliente). Para correlação pelo lado do cliente, use o header `x-flow-trace-id`.
- O campo `DOWNSTREAM_TLS_CIPHER_SUITE` **não é suportado** na versão do Envoy deste cluster. Use `DOWNSTREAM_TLS_CIPHER` (já corrigido nos manifests).
