# Item 48 — Comunicar com o backend das APIs via gRPC

## Requisito demonstrado

| Item   | Requisito                                                                 |
| ------ | ------------------------------------------------------------------------- |
| **48** | Capacidade de **comunicar com o backend das APIs via gRPC**. |

---

## Visão Geral

Este item demonstra como o gateway do RHCL (Envoy/Istio) roteia tráfego **gRPC** para backends que implementam serviços Protocol Buffers. O gRPC opera nativamente sobre HTTP/2 e o RHCL suporta esse cenário configurando o `appProtocol: kubernetes.io/h2c` no Service Kubernetes.

A demonstração cobre três modalidades de comunicação gRPC:

| Modalidade | Transporte | Ferramenta de teste |
|------------|-----------|---------------------|
| **gRPC nativo (unary)** | HTTP/2 cleartext (h2c) | `grpcurl` |
| **gRPC server-streaming** | HTTP/2 cleartext (h2c) | `grpcurl` |
| **gRPC-Web** | HTTP/1.1 ou HTTP/2 com content-type `application/grpc-web+proto` | `curl` |

---

## Diferença entre req048 e req054

| Aspecto | req048 (este) | req054 |
|---------|---------------|--------|
| **Foco** | Comunicação gRPC (Protocol Buffers) | Protocolos HTTP genéricos (HTTP/1.1, HTTP/2) |
| **Backend** | Serviço gRPC `io.gatewaysmashes.rhcl.grpc.BankingService` | REST `/api/v1/accounts/summary` |
| **Validação** | `grpcurl` + `curl` gRPC-Web | `curl` HTTP |
| **appProtocol** | `kubernetes.io/h2c` (obrigatório para gRPC) | `kubernetes.io/h2c` (demonstração HTTP/2) |

---

## Como o RHCL implementa

| Capacidade | Como o RHCL implementa |
|---|---|
| **gRPC nativo via gateway** | HTTPRoute roteia paths `/package.Service/Method` para backend com `appProtocol: kubernetes.io/h2c`; Envoy conecta via HTTP/2 |
| **gRPC-Web** | Mesmo HTTPRoute; o content-type `application/grpc-web+proto` é tratado transparentemente pelo Envoy |
| **Server streaming** | HTTP/2 suporta multiplexing nativo; o Envoy mantém a conexão aberta para streams |
| **Reflexão gRPC** | O backend expõe reflection service; `grpcurl` pode listar serviços sem .proto local |
| **Detecção de protocolo** | Istio/Envoy detecta `appProtocol: kubernetes.io/h2c` no Service e configura o cluster upstream automaticamente |
| **GRPCRoute (exemplo complementar)** | GRPCRoute `v1` (GA, Gateway API 1.3.0) com matching por serviço/método gRPC em listener/hostname dedicados; sem políticas Kuadrant (limitação do RHCL 1.3.5) |

## Hostname dinâmico

```
req048-grpc.<CLUSTER_DOMAIN>        # exemplo principal (HTTPRoute)
req048-grpcroute.<CLUSTER_DOMAIN>   # exemplo complementar (GRPCRoute)
```

Exemplos:
- `req048-grpc.apps.ocp.xxx.sandboxNNNN.opentlc.com` (lab)
- `req048-grpc.apps.cluster.example.com` (produção)

> Os dois exemplos usam hostnames/listeners distintos porque a spec da Gateway API aceita apenas a rota mais antiga quando um HTTPRoute e um GRPCRoute com hostnames intersectantes compartilham o mesmo listener.

## Validação rápida

```bash
CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
HOST="req048-grpc.${CLUSTER_DOMAIN}"

# gRPC nativo — unary call via gateway
grpcurl -plaintext -d '{"api_version":"v1"}' \
  $HOST:80 io.gatewaysmashes.rhcl.grpc.BankingService/GetSummary

# gRPC-Web via curl
printf '\x00\x00\x00\x00\x04\x0a\x02v1' | \
  curl -sS -X POST --data-binary @- \
    -H 'content-type: application/grpc-web+proto' \
    -H 'x-grpc-web: true' \
    "http://${HOST}/io.gatewaysmashes.rhcl.grpc.BankingService/GetSummary" -i | head

# gRPC via GRPCRoute (exemplo complementar — matching por serviço)
grpcurl -plaintext -d '{"api_version":"v1"}' \
  req048-grpcroute.${CLUSTER_DOMAIN}:80 io.gatewaysmashes.rhcl.grpc.BankingService/GetSummary
```

## Evidências da POC

| Evidência | Como demonstrar |
|---|---|
| **gRPC unary via gateway** | `grpcurl` retorna `SummaryResponse` com bancos e saldos |
| **gRPC streaming** | `grpcurl` retorna múltiplos `HealthEvent` com timestamps e sequence crescente |
| **gRPC-Web** | `curl` com content-type `grpc-web+proto` retorna HTTP 200 e `grpc-status: 0` |
| **appProtocol no Service** | `oc get svc -n req048-grpc req048-grpc-backend -o yaml` mostra `appProtocol: kubernetes.io/h2c` |
| **Reflexão gRPC** | `grpcurl -plaintext $HOST:80 list` retorna lista de serviços disponíveis |
| **GRPCRoute (matching por serviço)** | `grpcurl` via `req048-grpcroute.<domain>` retorna a mesma resposta; serviços fora das `rules` recebem `UNIMPLEMENTED` do gateway |
| **Coexistência HTTPRoute + GRPCRoute** | Os dois hostnames respondem simultaneamente (validado por `validate-grpcroute.sh`) |

## HTTPRoute × GRPCRoute

O requisito 48 é atendido pelo **HTTPRoute** (abordagem principal): funciona para gRPC nativo, streaming e gRPC-Web, e é o único tipo de rota que integra com as políticas Kuadrant. O **GRPCRoute** `v1` está disponível no cluster (Gateway API 1.3.0) e é demonstrado como exemplo complementar de roteamento gRPC idiomático (matching por serviço/método).

> **Atenção (governança):** no RHCL 1.3.5, AuthPolicy/RateLimitPolicy não podem targetear GRPCRoute (`targetRef` aceita apenas `Gateway` e `HTTPRoute`) e o enforcement do plano de dados (wasm-shim) deriva apenas de HTTPRoutes — tráfego roteado por GRPCRoute **não passa pelas políticas Kuadrant, nem pelo deny-all do gateway**. Para APIs gRPC governadas pelo RHCL, use HTTPRoute.

Comparação completa e critérios de escolha: [`req048/README.md`](req048/README.md#httproute--grpcroute-para-grpc).
