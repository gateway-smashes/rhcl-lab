# REQ 40 - Token counting per route (RHCL-native)

REQ 40 validates that AI token usage can be observed without instrumenting the
backend application. Counting happens **inside Kuadrant Limitador**, driven by
the existing `TokenRateLimitPolicy` from REQ 60 attached to
`HTTPRoute/banking-api-connectivity`. The `banking-api` does not emit any
Micrometer counter for tokens — its sole responsibility is to return an
OpenAI-shaped `usage` block in each response, which Limitador's
`add_n_to_counter` CEL expression converts into the `authorized_hits`
Prometheus counter.

Per-consumer visibility is delivered by **gateway access logs → Loki → Grafana**:
an EnvoyFilter on `rhcl-apps-gateway` logs `x-consumer-id` (and path, status,
duration) as `RHCL_ACCESS` structured text on stdout; Grafana Alloy ships
those lines to Loki; the **RHCL AI Consumer Access Logs** dashboard queries
LogQL with `regexp` parsers by consumer.

## Metrics (from `kuadrant-system/limitador-limitador:8080/metrics`)

| Metric | Labels | Purpose |
| ------ | ------ | ------- |
| `authorized_hits` | `limitador_namespace` (= `<ns>/<HTTPRoute>`) | Sum of token counts added by every TokenRateLimitPolicy on the route — i.e. the total tokens authorized in the window. |
| `authorized_calls` | `limitador_namespace` | Number of calls that crossed the gateway and were authorized. |
| `limited_calls` | `limitador_namespace` | Calls that hit a rate-limit (HTTP 429). |

The metrics are scraped by **OpenShift User Workload Monitoring** through the
ServiceMonitor shipped in this requirement, so the data is queryable end-to-end
from the in-cluster Thanos / Grafana stack.

## Logs (from `rhcl-apps-gateway` istio-proxy → Loki)

| Label / field | Source | Purpose |
| ------------- | ------ | ------- |
| `consumer` | `x-consumer-id` request header | Per-consumer breakdown of AI API calls. |
| `path` | Envoy `%REQ(X-ENVOY-ORIGINAL-PATH?:PATH)%` | Filter to `/api/v1/chat/completions` and sibling OpenAI paths. |
| `status` | HTTP response code | Spot HTTP 429 from Limitador rate-limit. |
| `duration_ms` | Envoy request duration | Gateway latency per call. |

## Relationship with other requirements

- **Req 33** exposes the OpenAI-compatible API surface under `/api/v1` (where
  the `usage` block originates). REQ 33 stays purely about the API contract.
- **Req 38** provides OpenTelemetry/Tempo for span correlation when enabled
  (still useful for per-request trace context).
- **Req 41** provides the Grafana/Prometheus stack the dashboards plug into.
- **Req 60** owns the actual `TokenRateLimitPolicy` and rate-limit semantics;
  REQ 40 consumes the Prometheus counters that Limitador exposes as a
  side-effect of REQ 60 being in place.

## Known limitations

- Limitador 2.3.1 does not expose `authorized_hits` with a per-consumer label.
  Loki provides **per-consumer call counts** and HTTP 429 visibility; token
  totals per consumer remain aggregated in Limitador until upstream surfaces
  counter qualifiers as Prometheus labels.
- The Limitador dashboard breaks down "Top routes by tokens" by
  `limitador_namespace` (which encodes `<ns>/<HTTPRoute>`); inside a single
  route only aggregated token totals are shown in Prometheus.
- Loki in this PoC uses ephemeral `emptyDir` storage with a 7-day retention
  window.
