REQ 14

CORS no Gateway origin: …

Demonstra que o backend /api/v1/cors não emite cabeçalhos Access-Control-Allow-*: o navegador bloqueia chamadas cross-origin direto contra o backend. A HTTPRoute em cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN} injeta esses cabeçalhos via ResponseHeaderModifier e o navegador libera a resposta.

Cenário

[ navegador @ origem desta página ]
        |
        |  fetch(URL escolhida abaixo)
        v
[ backend direto         ]   --> bloqueado: sem Access-Control-Allow-Origin
[ via cors.     ]   --> liberado: gateway adiciona cabeçalhos CORS
Antes de tudo, abra o DevTools. Quando o CORS bloqueia uma chamada, o JavaScript só vê TypeError: Failed to fetch. A mensagem detalhada ("No 'Access-Control-Allow-Origin' header is present") só aparece no Console (F12) e na Network do navegador. Mantenha o DevTools aberto durante o teste.

Matriz de testes

Mesmo endpoint /api/v1/cors no backend, mas dois caminhos até o navegador:

Origem do fetch URL chamada Cabeçalhos CORS na resposta Resultado esperado
página em outra origem https://banking-api-v1-rhcl-apps.<cluster>/api/v1/cors nenhum fetch bloqueado pelo navegador
página em outra origem https://cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN}/api/v1/cors Access-Control-Allow-* (gateway) 200 OK, corpo lido normalmente
curl / mesma origem qualquer um dos dois nenhum (curl) / não importa (same-origin) 200 OK — CORS é regra de navegador
CORS é só no navegador. O backend continua respondendo a todo mundo; o que muda é o navegador permitir o JS ler a resposta. Isso é demonstrado rodando este teste a partir de http://localhost:8080 (origem diferente do cluster) — o fetch só "vê" os dados quando passa pela rota cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN}.
