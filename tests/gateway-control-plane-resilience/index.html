Resilience Gateway resilience to a control-plane outage

Requirement: "The gateways must survive a manager outage without interrupting any functionality."

Connectivity Link separates the control plane (operators that reconcile resources) from the data plane (Envoy/Authorino/Limitador that serve traffic). The demo shows that scaling the entire CP in kuadrant-system to zero does not interrupt traffic.

Deep dive — the "control plane" is not one thing

The test above covers the 4 Kuadrant operators. Full-resilience analysis means separating all the components classifiable as CP — each fails forma diferente.

Headline — Connectivity Link inherits the Envoy/Istio pattern: the data plane survives control-plane outages. The gateway Envoys, Authorino and Limitador keep serving traffic with the last known configuration even if the whole CP goes down. This is architectural, not accidental.

O que degrada — categorias

A — Immediate degradation (seconds)

  • Changes stop propagating: new AuthPolicy/RateLimitPolicy/HTTPRoute stay pending in etcd until the CP returns.
  • Auto-scaling stops: HPA depends on kube-apiserver. If load rises, there is no scale-up.
  • Pod restarts are fatal: if a data-plane pod dies during a kube-apiserver outage, the scheduler cannot schedule a replacement.

B — Time-based degradation (clock)

  • Cert-manager stopped: renewal does not happen → TLS Routes eventually expire (cert-manager renews with ~30 days of slack, so tolerance is high).
  • Authorino JWKS cache: if Keycloak/OAuth is also down, the TTL eventually expires and JWT starts failing.
  • Authorino external metadata: calls to external enrichment services have a cache TTL.

C — Contract degradation (rate limit / Redis)

Limitador mode Redis down Behavior
in-memory N/A No Redis — counters die with the Limitador pod.
redis-cached Down Local per-site cache → counters diverge (over-admits).
pure redis Down Every check goes to Redis → failure_mode decides between fail-open and fail-closed.

The stance must be decided explicitly per API: "fail-open" is the pragmatic default (it does not take the app down over Redis being unavailable, temporarily losing protection); "fail-closed" preserves the limit even if it costs the SLA.

D — Special degradation: Authorino failureMode

Envoy calls Authorino via ext_authz. If the Authorino service is fully down:

  • Kuadrant default: failureModeAllow: false → the request is denied (fail-closed).
  • Auth-protected APIs become unavailable during the outage.
  • The opposite (fail-open) would let authenticated APIs serve without auth — usually unacceptable for a bank.

Production recommendations

Reduce the probability

  • HA the operators: default replicas: 1. In production, raise kuadrant-operator, authorino-operator, limitador-operator to replicas: 2 with leader election (they support it).
  • HA istiod: already ships with replicas: 2 in OSSM 3 production.
  • HA the data plane: Limitador and Authorino accept scale horizontally. Recommend replicas: 3+ in production.
  • HA the Redis: replace the lab emptyDir with Redis Enterprise / ElastiCache / Sentinel.
  • HA Keycloak/OAuth: a Keycloak cluster with 2+ instances behind an LB; replicated PostgreSQL.

Reduce the impact

  • Aggressive operator monitoring — kuadrant_operator_reconcile_errors_total is a direct "CP healthy" proxy.
  • Policies via GitOps (Argo CD) — if etcd comes back empty, restore is minutes, not hours.
  • Pre-staged config: data plane com imagePullPolicy: IfNotPresent and locally cached images.
  • Failure mode per API: critical endpoints (payments, transfers) fail-closed; read endpoints (balance) fail-open for SLA.

Reduce the recovery time

  • Runbook per component — each operator has documented health/reset commands.
  • CR backups automatizados (Velero) — RTO ditado by how long the snapshot's oc apply takes.
