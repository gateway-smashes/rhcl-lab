4. O que foi configurado no cluster pra JWT funcionar

Toda a configuração é declarativa — três CRs versionadas em Git, aplicadas pelo playbook apps-install / rhbk-install. O backend (banking-api) não tem nenhuma linha de código de autenticação: o gateway entrega o request com as claims já confiadas.

① AuthPolicy — regra jwt-keycloak

Adiciona uma nova identidade à AuthPolicy do banking-api, ao lado das identidades api-key-header, api-key-query, ai-mock e cors-preflight já existentes. Authorino aceita qualquer identidade que validar — então um cliente pode usar api-key, JWT ou ambos. O escopo é controlado pelo bloco when:. 

apiVersion: kuadrant.io/v1
kind: AuthPolicy
metadata:
  name: banking-api-connectivity-apikey
  namespace: rhcl-apps
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: banking-api-connectivity
  rules:
    authentication:
      # ─── identidade nova: JWT emitido pelo RHBK ─────────────
      jwt-keycloak:
        jwt:
          # Issuer URL = base do Keycloak + /realms/<realm>.
          # Authorino busca o JWKS em <issuer>/protocol/openid-connect/certs,
          # valida sig (RS256), iss, aud, exp. Cache automático.
          issuerUrl: https://keycloak.<apps-domain>/realms/rhcl
        # Predicates CEL — controlam ONDE essa identidade é exigida.
        # Outras paths continuam usando api-key.
        when:
          - predicate: "request.path.startsWith('/api/whoami')"
          - predicate: "request.method != 'OPTIONS'"  # libera CORS preflight

② AuthPolicy — bloco response.success (claims injetadas)

Authorino lê os claims do JWT validado e injeta como headers x-jwt-* no request upstream. O backend recebe tudo já confiado — só consome os headers, não revalida nada. 

spec:
  rules:
    response:
      success:
        headers:
          # auth.identity.* = claims do token JWT após validação.
          x-jwt-sub:                { plain: { selector: "auth.identity.sub" } }
          x-jwt-preferred-username: { plain: { selector: "auth.identity.preferred_username" } }
          x-jwt-email:              { plain: { selector: "auth.identity.email" } }
          x-jwt-aud:                { plain: { selector: "auth.identity.aud" } }
          x-jwt-roles:              { plain: { selector: "auth.identity.realm_access.roles" } }
          # Header unificado pra audit/log — mesma key pra api-key e JWT.
          x-consumer-id:            { plain: { selector: "auth.identity.metadata.name" } }

Como o gateway descobre o JWKS (RFC 8414)

Authorino faz GET <issuerUrl>/.well-known/openid-configuration no startup e em refresh periódico (cache TTL configurável). De lá pega o jwks_uri, busca as chaves públicas e usa pra validar assinatura. Não há shared secret entre gateway e Keycloak — a confiança é via JWKS público.

5. Customização — flexibilidade pra regras internas corporativas

A AuthPolicy expõe vários pontos de extensão. Tudo declarativo, sem mudar app. Abaixo os principais "ganchos" que costumam ser usados em produção bancária — cada linha pode ser ajustada via PR no Git, sem rebuild.

Ponto de extensãoO que você mudaExemplo no contexto banco
Múltiplas identidades coexistindo rules.authentication.<nome> aceita várias entradas (apiKey, jwt, oauth2, mtls, x509, anonymous, kubernetesTokenReview). Authorino tenta cada uma em paralelo e aceita a primeira que validar. Funcionários internos usam JWT do AD/LDAP federado no Keycloak; sistemas legados usam api-key; partners externos usam mTLS. Mesma AuthPolicy.
Predicates CEL (when:) Expressões CEL avaliadas pelo gateway. Acesso a request.method, request.path, request.headers, request.host, connection.requested_server_name, etc. "request.headers['x-canal'] == 'mobile'" só permite o endpoint /transfers/pix em horário comercial: "request.time.getHours() >= 6 && request.time.getHours() < 22".
Authorization por role/claim Bloco rules.authorization com opa.rego ou patternMatching. Decisão depois do auth — pode usar qualquer claim do JWT. POST /api/v1/transfers/>5000 exige banking-admin nas roles + claim device_attested; POST /api/v1/cards/block exige auth.identity.acr == "urn:bcb:mfa:hardware".
OPA Rego para regras complexas authorization.<nome>.opa.rego aceita policy Rego inline (ou via ConfigMap). Acesso a metadata, identidade, request inteiro e atributos enriched (geo-IP, fraud score, etc.). Bloquear transferências quando a soma das últimas 24h excede limite do plano + alertar SIEM via webhook. Tudo em ~20 linhas de Rego.
Metadata externa (enriquecimento) rules.metadata.http chama um serviço externo durante o request flow — fraud score, KYC, score de risco, BACEN PIX dict — e o resultado vira input das regras de autz. Pré-aprovação consulta o motor de fraud-check corporativo via POST /risk/score com user + amount + device; se score > 80 exige step-up.
Step-up authentication Resposta condicional com WWW-Authenticate: Bearer error="insufficient_user_authentication" quando o acr do token é insuficiente. Login normal pode ler saldo (acr=urn:bcb:auth:password), mas POST /transfers retorna 401 com hint pra reautenticar com biometria (acr=urn:bcb:auth:biometric) — frontend redireciona pro fluxo MFA do Keycloak.
Headers injetados no upstream response.success.headers permite qualquer header customizado, com selector em auth.identity.*, auth.metadata.*, context.*. x-app-segment: {{ auth.identity.attributes.segment }}, x-app-customer-id-hash: {{ sha256(auth.identity.customer-id) }}, x-trace-id: {{ context.request.id }}.
Bloco response.success.filters.identity Transforma a identidade antes de ser usada por RateLimit ou auditoria — útil pra mascarar PII ou colapsar IDs equivalentes. Já em uso hoje no PoC: extrai plan-id e user-id das annotations do Secret e expõe pra RateLimitPolicy decidir o plano (gold/silver/bronze) por chamada.
Rate-limit por claim do JWT RateLimitPolicy com counters usando auth.identity.preferred_username ou qualquer claim como discriminator. 50 req/min por usuário (claim sub), 10 req/min em /api/v1/transfers por usuário, 1000 req/min por aud (app cliente).
Logs de auditoria estruturados req035: EnvoyFilter + OTel Collector já capturam todo 4xx/5xx com claims + correlation_id + path. Custom-headers via response.success.headers entram automaticamente no audit log. Compliance LGPD/BACEN: cada denial vai pro SIEM com x-jwt-sub, x-app-customer-id-hash, request_id, auth.reason e trace_id (correlação com Tempo).
Federação com AD/LDAP corporativo No Keycloak: User Federation → LDAP / Active Directory. Usuários do banco logam com a credencial corporativa; roles AD viram roles do realm; tudo isso aparece nos claims do JWT. Funcionário corporativo autentica com matrícula corporativa, claim realm_access.roles chega com ["banking-customer","cib-trader"] — Rego decide acesso.
Política de allow-list por aud jwt.audiences: lista de audiences aceitas. Tokens com aud fora da lista são rejeitados antes de validar qualquer claim. Mesmo realm Keycloak serve mobile e internet banking; AuthPolicy do PIX só aceita tokens com aud=pix-app (impede um token web reutilizado pra ferramentas internas).

Exemplo composto — regra "PIX só com biometria, em horário comercial, fraud-score < 80"

Combinando 4 pontos de extensão acima. Toda a regra cabe na AuthPolicy: 

spec:
  rules:
    metadata:
      fraud-score:
        http:
          urlExpression: '"https://fraud.internal.example.com/risk/score"'
          method: POST
          body:
            user: "{auth.identity.sub}"
            amount: "{request.body.amount}"
            device: "{request.headers.x-device-id}"
        sharedSecretRef: { name: fraud-service-token, key: token }

    authorization:
      pix-policy:
        opa:
          rego: |
            default allow = false
            allow {
              # 1. precisa ser banking-customer
              input.auth.identity.realm_access.roles[_] == "banking-customer"
              # 2. tem que ser horário comercial (6h–22h BRT)
              hour := time.weekday_hour(input.context.request.time)
              hour >= 6; hour < 22
              # 3. step-up: ACR de biometria
              input.auth.identity.acr == "urn:bcb:auth:biometric"
              # 4. fraud-score do enrichment < 80
              to_number(input.metadata["fraud-score"].score) < 80
            }
        when:
          - predicate: "request.method == 'POST' && request.path.startsWith('/api/v1/pix')"

Tudo declarativo, tudo em Git, tudo revisável via PR. Mudança de regra regulatória = commit. Sem rebuild do backend, sem janela de manutenção da app — só oc apply.
