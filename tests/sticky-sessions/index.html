Sticky sessions Session-aware load balancing

Requirement: session affinity across replicas of the backend, configured by an HTTP cookie at the gateway level.

This demo uses the banking-api-v1 backend (already exposed by rhcl-apps-gateway via HTTPRoute banking-api-connectivity), with 2+ replicas and a DestinationRule do Istio aplicando consistentHash.httpCookie.

The path matters — the demo must use the rhcl-apps-gateway hostname (Gateway API). If it enters via the default OpenShift Route (*.apps.<cluster>), traffic goes HAProxy → Service directly, bypassing Istio, and the DestinationRule is silently ignored. The "sticky" you see on that path comes from HAProxy's default cookie, not from CUSTOM_COOKIE_SESSION do Envoy.

Configuration

Setup Uma vez por cluster

1. Scale to 2 replicas

Sticky with 1 replica is a false positive (every request hits the same pod independentemente da DR). 

oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=2
oc rollout status deploy/banking-api-v1 -n rhcl-apps

2. Backend reporta o nome do pod no /api/echo

Quarkus reads APP_INSTANCE_NAME and returns it in the field instance. Trocar o valor fixo por fieldRef makes each pod report its own name. 

oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME-

oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/template/spec/containers/0/env/0",
    "value": {
      "name": "APP_INSTANCE_NAME",
      "valueFrom": {"fieldRef": {"fieldPath": "metadata.name"}}
    }
  }
]'
oc rollout status deploy/banking-api-v1 -n rhcl-apps

3. Patch da DestinationRule existente

The DestinationRule banking-api-v1-http1 already exists (manages the connection pool). Just add the loadBalancer: 

oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/trafficPolicy/loadBalancer",
    "value": {
      "consistentHash": {
        "httpCookie": {
          "name": "CUSTOM_COOKIE_SESSION",
          "path": "/",
          "ttl": "1800s"
        }
      }
    }
  }
]'

1 Baseline — round-robin without a cookie

Without a cookie, the DR has no hash key, so Envoy does round-robin and traffic spreads across the 2 pods. This step proves the DR is active and that there are multiple pods behind the Service. 

HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')
for i in $(seq 1 10); do
  # occasional backend 503s do not break the script
  curl -sk "https://$HOST/api/echo" 2>/dev/null \
    | python3 -c '
import json, sys
try: print(json.load(sys.stdin).get("instance",""))
except: pass
' 2>/dev/null
done | grep -v '^$' | sort | uniq -c

2 Verificar caminho (browser) + Set-Cookie (CLI)

In the browser (cross-origin), Set-Cookie is a "forbidden response header" per the Fetch spec — JS can never read it. So the button here validates what is visible from the browser: that the call reaches the backend and that the instance field of /api/echo holds nome de pod (= setup do APP_INSTANCE_NAME via fieldRef deu certo). Se vier backend-a, the env var did not reach the process (Quarkus default).

To see the literal cookie, use the CLI only:

curl -sk -i "https://$HOST/api/echo" | grep -i 'set-cookie'
# set-cookie: CUSTOM_COOKIE_SESSION="37c5519780cbe86f"; Max-Age=1800; Path=/; HttpOnly

3 Sticky — 5 cookies × N reqs

Each cookie represents a session. Each session must stick to a single pod. Different cookies may land on different pods (distribution is hash-based). 

for cookieval in aaa111 bbb222 ccc333 ddd444 eee555; do
  pods=$(for i in $(seq 1 8); do
    curl -sk -H "Cookie: CUSTOM_COOKIE_SESSION=$cookieval" \
         "https://$HOST/api/echo" 2>/dev/null \
      | python3 -c '
import json, sys
try: print(json.load(sys.stdin).get("instance",""))
except: pass
' 2>/dev/null
  done | grep -v '^$' | sort -u | tr '\n' ',' | sed 's/,$//')
  echo "cookie=$cookieval → pods: $pods"
done

Troubleshooting

SymptomDiagnosis
Set-Cookie comes with the name <md5hash> instead of CUSTOM_COOKIE_SESSION Traffic entered via the OpenShift Route, not the Gateway API. Confirm the hostname matches spec.hostnames of HTTPRoute banking-api-connectivity.
Round-robin happens even with a cookie The DR was not applied or its host does not match the Service. oc get destinationrule banking-api-v1-http1 -n rhcl-apps -o yaml.
401 / 403 em /api/echo A gateway-level deny-all AuthPolicy is catching it. The /api/echo route is anonymous in the banking-api-connectivity-apikey AuthPolicy — confirm Enforced=True.
instance always the same, but there are 2 replicas APP_INSTANCE_NAME is still fixed. Re-run setup step 2 (fieldRef metadata.name).
Sticky degrades after oc rollout restart Expected — new pods have new names, so the cookie hash maps to another bucket. Sessions opened before the restart "jump" to a pod (still stable thereafter).

Rollback

# Revert the DR to its original state (no sticky)
oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/trafficPolicy/loadBalancer"}
]'

# Revert APP_INSTANCE_NAME to a fixed value
oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/template/spec/containers/0/env/0"}
]'
oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME=banking-api-v1
oc rollout status deploy/banking-api-v1 -n rhcl-apps

# (Optional) back to 1 replica
oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=1
