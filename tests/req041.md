### Req 41 — API Metrics Interface (Grafana Dashboards)

**Requisito:** "Possuir interface com métricas das APIs contendo minimamente:
throughput, tempos de execução, volumetria por status code, visão por endpoint,
visão por consumidores das APIs."

**Goal:** provide Grafana dashboards that give full visibility into API traffic
flowing through the RHCL Gateway (Kuadrant + Gateway API). The dashboards
cover all five sub-requirements using Istio proxy metrics emitted by the
Gateway pod and joined with Gateway API state metrics so panels resolve to
meaningful HTTPRoute / API names.

The Grafana instance is deployed via the **Grafana Operator** (installed from
OperatorHub) and reads metrics from the OpenShift **Thanos Querier**
(user-workload monitoring).

## Sub-requirement mapping

| Sub-requirement | Metric source | Dashboard / panel |
|---|---|---|
| **Throughput** (req/s) | `rate(istio_requests_total[5m])` | API Overview — "Request Rate" |
| **Execution times** (latency) | `histogram_quantile(P, istio_request_duration_milliseconds_bucket)` | API Overview — "Latency Percentiles" |
| **Volumetry by status code** | `sum by (response_code)(istio_requests_total)` | API Overview — "Status Code Distribution" |
| **View per endpoint** | `sum by (request_url_path)(istio_requests_total)` | API Overview — "Per-Endpoint Breakdown" |
| **View per consumer** | `sum by (request_headers_x_consumer_id)(istio_requests_total)` | API Consumers — all panels |

## Prerequisites

1. Cluster with RHCL installed (Kuadrant + Gateway API with Istio gateway
   controller).
2. **Grafana Operator** installed from OperatorHub (community or certified
   channel). The operator must be watching the `rhcl-grafana` namespace or
   all namespaces.
3. **User-workload monitoring** enabled (`MONITORING_ENABLE_USER_WORKLOAD=true`
   — this is the lab default).
4. Prometheus scraping the Gateway pod metrics (handled by the Istio
   integration with OpenShift monitoring).

## Deploy

### Step 1 — Apply all resources with kustomize

```bash
oc apply -k tests/req041/manifests/
```

This creates:
- The `rhcl-grafana` namespace
- An Istio Telemetry CR (in `openshift-ingress`) adding `request_url_path` and
  `x-consumer-id` as metric labels on the Gateway proxy
- A Grafana instance with an OpenShift Route (TLS edge)
- A ServiceAccount token + ClusterRoleBinding for Thanos access
- A GrafanaDatasource pointing to `thanos-querier.openshift-monitoring.svc:9091`
- Four GrafanaDashboard CRs

### Step 2 — Inject the Thanos bearer into the datasource

> **Grafana Operator bug** (observed on v5.24.0): the `valuesFrom` →
> Secret pathway on `GrafanaDatasource` silently fails — the operator
> reports `ApplySuccessful` but `secureJsonFields` stays empty and every
> dashboard query returns `401 Authentication to data source failed`. So
> the bearer has to be **inlined into the CR** rather than referenced from
> a Secret. The `05-grafana-datasource-thanos.yaml` manifest carries a
> `__BEARER_TOKEN__` placeholder to make the substitution obvious.

The kustomize bundle applies a `kubernetes.io/service-account-token`
Secret bound to `rhcl-grafana-sa`; Kubernetes populates it with a JWT
once the SA exists.

After `oc apply -k` finishes, substitute the token into the datasource
and re-apply it:

```bash
TOKEN=$(oc -n rhcl-grafana get secret rhcl-grafana-sa-token \
  -o jsonpath='{.data.token}' | base64 -d)
sed "s/__BEARER_TOKEN__/${TOKEN}/" \
  tests/req041/manifests/05-grafana-datasource-thanos.yaml | oc apply -f -
```

Verify the datasource is healthy:

```bash
GRAFANA_URL=$(oc -n rhcl-grafana get route -o jsonpath='{.items[0].spec.host}')
curl -sk -u rhcl-admin:rhcl-poc-2026 -G \
  "https://${GRAFANA_URL}/api/datasources/proxy/uid/$(
    oc -n rhcl-grafana get grafanadatasource rhcl-prometheus \
      -o jsonpath='{.status.uid}')/api/v1/query" \
  --data-urlencode 'query=up' -w "\nHTTP=%{http_code}\n" | tail -3
# {"status":"success","data":...}
# HTTP=200
```

> **Batch alternative:** the same substitution is automated by
> `automation/roles/grafana/` (reads the SA token, stamps it into the
> CR, applies it), reachable via `ansible-playbook
> automation/playbooks/grafana-install.yml`. Either path lands the
> cluster in the same state — pick whichever fits the change window.

### Step 3 — Verify the Grafana instance is ready

```bash
oc -n rhcl-grafana get grafana rhcl-grafana
# NAME           AGE
# rhcl-grafana   ...

oc -n rhcl-grafana get pods -l app=grafana
# NAME                            READY   STATUS    RESTARTS   AGE
# rhcl-grafana-deployment-...     1/1     Running   0          ...

oc -n rhcl-grafana get route
# NAME                HOST/PORT                                    ...
# rhcl-grafana-route  rhcl-grafana-route-rhcl-grafana.apps...      ...
```

### Step 4 — Verify the datasource is connected

```bash
oc -n rhcl-grafana get grafanadatasource rhcl-prometheus \
  -o jsonpath='{.status.conditions[0].message}'
# Datasource was successfully applied to 1 instances
```

> **Troubleshooting:** if the datasource shows `InvalidSpec` / secret not
> found, re-run the bearer token command in Step 2. If it shows
> "Unauthorized", verify the ClusterRoleBinding:
>
> ```bash
> oc get clusterrolebinding rhcl-grafana-cluster-monitoring-view
> ```

### Step 5 — Verify the Istio Telemetry CR

```bash
oc -n openshift-ingress get telemetry rhcl-api-metrics
```

> **Cardinality warning:** enabling `request_url_path` adds one label
> value per distinct path. In production environments with unbounded path
> segments (UUIDs, IDs) consider normalizing paths or restricting this
> to PoC namespaces only.

### Step 6 — Verify dashboards are provisioned

```bash
oc -n rhcl-grafana get grafanadashboard
# NAME                  AGE
# rhcl-api-overview     ...
# rhcl-api-consumers    ...
# rhcl-authorino        ...
# rhcl-limitador        ...
```

Open the Grafana Route URL in a browser. The two dashboards appear
automatically under the managed folder.

### Alternative — Manual JSON import

If you prefer to import dashboards manually instead of using the
GrafanaDashboard CRs:

1. Open Grafana UI.
2. Go to **Dashboards → Import**.
3. Upload `tests/req041/manifests/grafana-dashboard-api-overview.json`.
4. Select the Prometheus datasource.
5. Repeat for `grafana-dashboard-api-consumers.json`,
   `grafana-dashboard-authorino.json`, and
   `grafana-dashboard-limitador.json`.

## Dashboard details

### Dashboard 1 — RHCL API Overview

Based on the [Kuadrant App Developer Dashboard](https://grafana.com/grafana/dashboards/21538)
pattern. Template variables: `$datasource`, `$namespace`.

| Row | Panel | PromQL basis |
|---|---|---|
| 1 | **Total Requests** (stat) | `sum(increase(istio_requests_total{...}[$__range]))` |
| 1 | **Error Rate %** (stat) | `sum(rate(istio_requests_total{response_code=~"5.."}[5m])) / sum(rate(istio_requests_total[5m]))` |
| 1 | **Avg Latency** (stat) | `sum(rate(istio_request_duration_milliseconds_sum[5m])) / sum(rate(istio_request_duration_milliseconds_count[5m]))` |
| 2 | **Request Rate** (timeseries) | `sum(rate(istio_requests_total[5m]))` |
| 2 | **Latency Percentiles** (timeseries) | `histogram_quantile(0.50/0.90/0.95/0.99, sum(rate(istio_request_duration_milliseconds_bucket[5m])) by (le))` |
| 3 | **Status Code Distribution** (timeseries, stacked) | `sum by (response_code)(rate(istio_requests_total[5m]))` |
| 3 | **Status Code Breakdown** (pie) | `sum by (response_code)(increase(istio_requests_total[$__range]))` |
| 4 | **Per-Endpoint Request Rate** (timeseries) | `sum by (request_url_path)(rate(istio_requests_total[5m]))` |
| 4 | **Endpoint Summary Table** (table) | req/s + P95 latency + error % per path |

### Dashboard 2 — RHCL API Consumers

Template variables: `$datasource`, `$namespace`, `$consumer`.

| Row | Panel | PromQL basis |
|---|---|---|
| 1 | **Traffic by Consumer** (timeseries) | `sum by (request_headers_x_consumer_id)(rate(istio_requests_total[5m]))` |
| 1 | **Latency by Consumer P95** (timeseries) | `histogram_quantile(0.95, sum by (le, request_headers_x_consumer_id)(...))` |
| 2 | **Status Codes by Consumer** (timeseries, stacked) | `sum by (request_headers_x_consumer_id, response_code)(rate(istio_requests_total[5m]))` |
| 2 | **Top Consumers** (table, instant) | `topk(20, sum by (request_headers_x_consumer_id)(increase(istio_requests_total[$__range])))` |

### Dashboard 3 — RHCL Authorino — Auth Decisions

Template variables: `$datasource`, `$authconfig`.

| Row | Panel | PromQL basis |
|---|---|---|
| 1 | **Total Evaluations** (stat) | `sum(increase(auth_server_authconfig_total[$__range]))` |
| 1 | **Auth Eval Rate** (stat) | `sum(rate(auth_server_authconfig_total[5m]))` |
| 1 | **OK Rate** (stat) | `sum(rate(auth_server_authconfig_response_status{status="OK"}[5m]))` |
| 1 | **Denied Rate** (stat) | `sum(rate(auth_server_authconfig_response_status{status!="OK"}[5m]))` |
| 1 | **Auth Decisions/sec by Status** (timeseries, stacked) | `sum by (status)(rate(auth_server_authconfig_response_status[5m]))` |
| 1 | **Auth Decision Distribution** (pie) | `sum by (status)(increase(auth_server_authconfig_response_status[$__range]))` |
| 2 | **Mean Auth Latency** (stat) | `sum(rate(..._sum[5m])) / sum(rate(..._count[5m]))` |
| 2 | **Auth Latency Percentiles** (timeseries) | `histogram_quantile(0.50/0.95/0.99, sum(rate(auth_server_authconfig_duration_seconds_bucket[5m])) by (le))` |
| 3 | **Evaluations/sec per AuthConfig** (timeseries) | `sum by (authconfig)(rate(auth_server_authconfig_total[5m]))` |
| 3 | **P95 Latency per AuthConfig** (timeseries) | `histogram_quantile(0.95, sum by (le, authconfig)(rate(..._bucket[5m])))` |
| 3 | **AuthConfig Summary Table** (table) | Evals/s, OK/s, P50/P95/P99 latency per authconfig |
| 4 | **Authorino Ready** (stat) | `kuadrant_component_ready{component="authorino"}` |
| 4 | **Total / Enforced / Not Enforced AuthPolicies** (stat) | `kuadrant_policies_total{kind="AuthPolicy"}`, `kuadrant_policies_enforced{...}` |

> **Note:** the `authconfig` label is a SHA-256 hash generated by Kuadrant. The dashboard variable lists all available hashes for filtering.

### Dashboard 4 — RHCL Limitador — Rate Limiting

Template variables: `$datasource`.

| Row | Panel | PromQL basis |
|---|---|---|
| 1 | **Allowed Rate** (stat) | `sum(rate(kuadrant_allowed[5m]))` |
| 1 | **Denied Rate** (stat) | `sum(rate(kuadrant_denied[5m]))` |
| 1 | **Deny Ratio** (stat) | `100 * denied / (allowed + denied)` |
| 1 | **Total Requests** (stat) | `sum(increase(kuadrant_allowed[$__range])) + sum(increase(kuadrant_denied[$__range]))` |
| 1 | **Allowed vs Denied Over Time** (timeseries, stacked) | `sum(rate(kuadrant_allowed[5m]))`, `sum(rate(kuadrant_denied[5m]))` |
| 1 | **Allowed / Denied Breakdown** (pie) | `sum(increase(kuadrant_allowed[$__range]))`, `sum(increase(kuadrant_denied[$__range]))` |
| 1 | **Deny Ratio Over Time** (timeseries) | `100 * denied_rate / (allowed_rate + denied_rate)` |
| 2 | **Wasm Filter Counters/sec** (timeseries) | `sum(rate(kuadrant_hits[5m]))`, `kuadrant_misses`, `kuadrant_errors` |
| 2 | **Error Rate** (stat) | `sum(rate(kuadrant_errors[5m]))` |
| 2 | **Wasm Configs** (stat) | `sum(kuadrant_configs)` |
| 3 | **Limitador Ready** (stat) | `kuadrant_component_ready{component="limitador"}` |
| 3 | **Limitador Up** (stat) | `limitador_up` |
| 3 | **Total / Enforced RateLimitPolicies** (stat) | `kuadrant_policies_total{kind="RateLimitPolicy"}`, `kuadrant_policies_enforced{...}` |
| 3 | **Policy Enforcement Status** (table) | `kuadrant_policies_enforced{kind=~"RateLimitPolicy|AuthPolicy"}` |

> **Note:** Limitador does not expose per-request rate-limit decision metrics (counters, histograms).
> The dashboard uses `kuadrant_allowed` / `kuadrant_denied` from the Kuadrant Wasm plugin on the gateway
> as proxies for rate-limiting activity.

## Test procedure

### 1. Generate traffic through the Gateway

```bash
for i in $(seq 1 50); do
  curl -sk -H "x-consumer-id: consumer-A" \
    "https://banking-api-connectivity.${RHCL_ZONE_ROOT_DOMAIN}/api/v1/accounts/summary" &
  curl -sk -H "x-consumer-id: consumer-B" \
    "https://banking-api-connectivity.${RHCL_ZONE_ROOT_DOMAIN}/api/v1/transfers" &
done
wait
```

Or use the existing k6 scripts:

```bash
k6 run tests/k6/test-be-and-weight-rhcl.js
```

### 2. Verify metrics are available in Prometheus

```bash
oc -n openshift-monitoring port-forward svc/thanos-querier 9091:9091 &

curl -sk -H "Authorization: Bearer $(oc whoami -t)" \
  'https://localhost:9091/api/v1/query?query=istio_requests_total' | \
  jq '.data.result[0].metric | keys'
```

Should include: `request_url_path`, `request_headers_x_consumer_id`.

### 3. Open the API Overview dashboard

Get the Grafana Route:

```bash
oc -n rhcl-grafana get route -o jsonpath='{.items[0].spec.host}'
```

Navigate to **Dashboards → RHCL API Overview**.

**Expected:**

- **Request Rate** panel shows req/s matching the traffic generated.
- **Latency Percentiles** shows P50, P90, P95, P99 curves.
- **Status Code Distribution** shows 2xx bars (and 4xx/5xx if errors
  were injected).
- **Per-Endpoint Breakdown** table lists `/api/v1/accounts/summary`,
  `/api/v1/transfers`, etc. with individual rates.

### 4. Open the API Consumers dashboard

Navigate to **Dashboards → RHCL API Consumers**.

**Expected:**

- **Traffic by Consumer** shows separate timeseries for `consumer-A` and
  `consumer-B`.
- **Top Consumers** table ranks consumers by total request count.
- **Status Codes by Consumer** breaks down 2xx/4xx/5xx per consumer.

### 5. Verify with different consumer identities

```bash
curl -sk -H "x-consumer-id: mobile-app" \
  "https://banking-api-connectivity.${RHCL_ZONE_ROOT_DOMAIN}/api/v1/accounts/summary"

curl -sk -H "x-consumer-id: partner-api" \
  "https://banking-api-connectivity.${RHCL_ZONE_ROOT_DOMAIN}/api/v1/accounts/summary"
```

After ~30 seconds the new consumer IDs should appear in the Consumer
dashboard.
