### Req 4 — Resiliência do gateway à indisponibilidade do control plane

**Requisito:** "Os gateways devem conseguir suportar uma indisponibilidade do
manager sem interrupção de nenhuma funcionalidade."

**Contexto RHCL:** o Red Hat Connectivity Link não possui o conceito de
"API Manager" centralizado como o 3scale. A arquitetura é baseada em
operadores Kubernetes (control plane) que reconciliam recursos declarativos,
e um data plane (Istio ingress gateway) que efetivamente roteia o tráfego.

Para este requisito, o **control plane** (equivalente ao "manager") é composto
pelos operadores do namespace `kuadrant-system`:

| Componente | Deployment |
|---|---|
| Kuadrant Operator | `kuadrant-operator-controller-manager` |
| Authorino Operator | `authorino-operator` |
| Limitador Operator | `limitador-operator-controller-manager` |
| DNS Operator | `dns-operator-controller-manager` |

**Goal:** demonstrar que o data plane (gateway Istio) continua roteando
tráfego normalmente mesmo quando todos os operadores do control plane estão
indisponíveis. Rotas, políticas e configurações já aplicadas permanecem
ativas porque estão materializadas na configuração do Envoy/Istio — os
operadores só são necessários para **reconciliar mudanças**, não para manter
o tráfego fluindo.

---

## Pré-requisitos

1. Cluster OpenShift com RHCL instalado e funcionando.
2. Backend e frontend da PoC (banking-api + Red Bank) acessíveis através do
   gateway RHCL.
3. Acesso `cluster-admin` para escalar os deployments em `kuadrant-system`.

**Via curl:**

## Por que funciona

A arquitetura do RHCL separa **control plane** e **data plane**:

```
Control Plane (kuadrant-system)              Data Plane (openshift-ingress)
┌──────────────────────────────┐             ┌──────────────────────────────┐
│  Kuadrant Operator           │  reconcilia │                              │
│  Authorino Operator          │ ──────────> │  Istio Ingress Gateway       │
│  Limitador Operator          │  (configura │  (Envoy proxy)               │
│  DNS Operator                │   o Envoy)  │                              │
└──────────────────────────────┘             └──────────────────────────────┘
       ▲                                              ▲
       │                                              │
  Só necessário para                          Processa o tráfego
  aplicar MUDANÇAS                            real das aplicações
  (criar/alterar rotas,                       (HTTP, WebSocket, TLS)
   políticas, etc.)
```

Os operadores do control plane **apenas reconciliam mudanças** — quando um
`HTTPRoute`, `AuthPolicy`, `RateLimitPolicy` ou `TLSPolicy` é criado ou
alterado, o operador correspondente traduz essa configuração para o Envoy.
Uma vez aplicada, a configuração persiste no data plane **independentemente**
do estado dos operadores.

Isso significa que:

- **Rotas existentes** continuam funcionando.
- **Políticas de rate limit** continuam sendo aplicadas pelo Limitador.
- **Políticas de autenticação** continuam sendo aplicadas pelo Authorino.
- **Certificados TLS** já emitidos continuam válidos.
- O único impacto é que **novas alterações** em rotas/políticas não serão
  reconciliadas até os operadores voltarem.

## Aprofundamento — "control plane" não é uma coisa, são várias

O teste acima cobre os 4 operadores do Kuadrant. Mas a pergunta de
resiliência completa exige separar **todos** os componentes que podem ser
classificados como CP, porque cada um falha de forma diferente e tem
impacto diferente no tráfego:

| Componente | Camada | Função | Único responsável por... |
|---|---|---|---|
| `istiod` | Istio CP | Programa Envoy via xDS | Aplicar mudanças em HTTPRoute/Gateway/AuthPolicy |
| `kuadrant-operator` | Kuadrant CP | Reconcilia Kuadrant CR | Mudanças na config do produto |
| `authorino-operator` | Kuadrant CP | Traduz AuthPolicy → AuthConfig | Propagar novas políticas de auth |
| `limitador-operator` | Kuadrant CP | Reconcilia Limitador CR | Mudar storage backend (Redis ↔ memória) |
| `dns-operator` | Kuadrant CP | Reconcilia DNSRecord | Atualizar registros DNS / failover |
| `Authorino` (serviço) | **Data plane** | Servidor gRPC ext_authz | Decisão allow/deny por request |
| `Limitador` (serviço) | **Data plane** | Servidor gRPC ratelimit | Contadores e decisão 429 |
| Envoy do Gateway | **Data plane** | Proxy reverso | Atender o tráfego em si |
| `kube-apiserver` | OCP CP | API do K8s | Tudo que envolve criar/alterar recursos |
| `cert-manager` | OCP CP | Emite / renova TLS | Renovação automática antes do `notAfter` |

> O Connectivity Link herda o padrão **Envoy/Istio**: o data plane sobrevive
> a quedas do control plane. Os Envoys do gateway, o Authorino e o Limitador
> continuam atendendo tráfego com a **última configuração conhecida** mesmo
> se todo o CP cair. Isso é arquitetural, não acidental.

## O que continua funcionando durante uma queda de CP

| Cenário | Tráfego segue normal? | Por quê |
|---|---|---|
| `istiod` cai | Sim | Envoys têm cache xDS local |
| `kuadrant-operator` cai | Sim | Authorino/Limitador já provisionados continuam |
| `authorino-operator` cai | Sim | `AuthConfig`s já traduzidos vivem em memória no Authorino |
| `limitador-operator` cai | Sim | Pod do Limitador segue com a config carregada |
| `dns-operator` cai | Sim | DNS já publicado segue resolvendo |
| `cert-manager` cai | Sim (curto prazo) | Certificados atuais válidos até `notAfter` |
| `kube-apiserver` cai | Sim (sem mudanças) | Pods rodando seguem rodando; só não dá pra criar/alterar nada |

## O que degrada — categorias

Categorizar a degradação ajuda a definir SLA e estratégia de monitoramento:

### A — Degradação imediata (em segundos)

- **Mudanças param de propagar**: nova `AuthPolicy`, novo `RateLimitPolicy`,
  alteração de `HTTPRoute` ficam pendentes no etcd até o CP voltar.
- **Scaling automático para**: HPA depende do `kube-apiserver`. Se a carga
  subir durante a queda, não há scale-up.
- **Pod restarts são fatais**: se um Envoy/Authorino/Limitador morrer
  durante a queda do `kube-apiserver`, o scheduler não consegue agendar
  substituto.

### B — Degradação por tempo (relógio)

- **Cert-manager parado**: renovação de certificado não acontece →
  eventualmente os Routes com TLS expiram. O cert-manager renova com
  ~30 dias de folga antes do `notAfter`, então a janela de tolerância é
  longa.
- **JWKS cache do Authorino**: se o Keycloak/OAuth também estiver down,
  eventualmente o cache TTL expira e validação de JWT começa a falhar.
- **Authorino metadata externa**: chamadas a serviços externos para
  enrichment de identity têm cache TTL — quando expira, depende de o
  serviço externo estar up.

### C — Degradação por contrato (rate limit / Redis)

Este é o ponto mais sutil e merece decisão **explícita** com o cliente:

| Modo do Limitador | Redis cai | Comportamento |
|---|---|---|
| `in-memory` | N/A | Sem Redis — contadores morrem com o pod do Limitador |
| `redis-cached` | Down | Cada site usa cache local → contadores divergem entre sites (over-admite no global) |
| `redis` puro | Down | Cada check vai pro Redis → `failure_mode` decide entre fail-open (admite tudo) e fail-closed (nega tudo) |

A postura precisa ser **decidida explicitamente por API**: "fail-open" é o
padrão pragmático (não derruba a app por causa de Redis indisponível, perde
temporariamente a proteção); "fail-closed" preserva o limite mesmo que
custe o SLA.

### D — Degradação especial: Authorino failure mode

O Envoy chama `Authorino` via ext_authz. Se o serviço Authorino estiver
**completamente down** (não respondendo):

- **Default Kuadrant: `failureModeAllow: false`** → request é negado
  (fail-closed).
- Significa: queda do Authorino → APIs auth-protegidas ficam indisponíveis.
- Trade-off: o oposto (fail-open) deixaria APIs autenticadas servirem
  **sem auth** durante a queda — geralmente inaceitável em banco.

## Recomendações de produção

### Reduzir a probabilidade
- **HA dos operadores**: por default a maioria roda com `replicas: 1`. Em
  produção, subir `kuadrant-operator`, `authorino-operator`,
  `limitador-operator` pra `replicas: 2` com leader election (eles
  suportam).
- **HA do `istiod`**: já vem com `replicas: 2` no OSSM 3 em produção.
- **HA do data plane**: o Limitador e o Authorino aceitam scale horizontal.
  Recomendar `replicas: 3+` em prod.
- **HA do Redis**: trocar o Redis em `emptyDir` da PoC por Redis Enterprise
  / ElastiCache / Sentinel.
- **HA do Keycloak/OAuth**: cluster Keycloak com 2+ instâncias atrás de LB;
  PostgreSQL replicado.

### Reduzir o impacto quando acontece
- **Monitoring + alerta agressivo nos operadores** (todos têm métricas
  Prometheus). `kuadrant_operator_reconcile_errors_total` é um proxy
  direto de "CP saudável".
- **Definir políticas como GitOps** (ArgoCD) — se o etcd voltar zerado,
  restauração é minutos, não horas.
- **Pre-staged config**: deployments dos componentes data plane com
  `imagePullPolicy: IfNotPresent` e imagens local-cacheadas — não dependem
  de registry externo pra restart.
- **Definir o failure mode por API** — endpoints críticos (Pix,
  transferência) podem ser fail-closed; endpoints de leitura (saldo) podem
  ser fail-open por SLA.

### Reduzir o tempo de recuperação
- **Runbook por componente** — cada operador tem comandos de health/reset
  documentados.
- **CR backups** automatizados (Velero, etc.) — RTO ditado por quanto
  tempo leva o `oc apply` do snapshot.
