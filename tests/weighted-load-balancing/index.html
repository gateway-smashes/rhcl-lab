Weighted LB

Weighted load balancing origin: …

Shows that the gateway (RHCL / Gateway API) splits traffic between the two versions of banking-api (banking-api-v1 and banking-api-v2) by the weight field of each backendRef on the HTTPRoute. Since both Deployments run the same image, the neutral path chosen (/api/whoami) is served by both; the instance field of the response (banking-api-v1 or banking-api-v2) identifies which Service the gateway chose per call. A filter RequestHeaderModifier per backendRef also injects x-route-version: v1|v2 before forwarding, and the backend echoes that header in allHeaders — a second signal independent of the split.

Scenario

[ cliente ]                       [ RHCL / Gateway ]                   [ backends ]
    |                                       |                                 |
    |  GET /api/whoami                      |                                 |
    |-------------------------------------->|                                 |
    |                                       |  weight: v1=90 / v2=10          |
    |                                       |                                 |
    |                                  ┌────┴────┐                            |
    |                                  │ ~90%    │ injeta x-route-version: v1 |
    |                                  │         │------------------------->  |
    |                                  │         │                  banking-api-v1
    |                                  │         │ <-------------------------|
    |                                  │         │ instance=banking-api-v1    |
    |                                  ├─────────┤ allHeaders[x-route-version]=v1
    |                                  │ ~10%    │ injeta x-route-version: v2 |
    |                                  │         │------------------------->  |
    |                                  │         │                  banking-api-v2
    |                                  │         │ <-------------------------|
    |                                  │         │ instance=banking-api-v2    |
    |                                  └─────────┘ allHeaders[x-route-version]=v2
    |  HTTP 200 OK { instance, allHeaders, … }                                |
    | <--------------------------------------|                                |
What this page proves. Firing N sequential (or parallel) requests against the same neutral path, the gateway selects a backend per call honoring the weights of the HTTPRoute. The page tabulates instance (and the x-route-version echo) of each response and compares the observed proportion with the expected one. In small samples deviation is normal — raise N to watch the distribution converge.
Why not URLRewrite per backendRef? O controller openshift.io/gateway-controller/v1 (Istio) declares URLRewrite only in HTTPRouteRule.filters, not in HTTPBackendRef.filters. Applying it per backendRef makes the resource go ResolvedRefs=False, reason=InvalidFilter, message="unsupported filter type URLRewrite". Por isso o demo uses a path that exists on both pods and the signal comes from RequestHeaderModifier (core support in Istio) + the response instance.

Distribution by instance

The response's instance field comes from the APP_INSTANCE_NAME Deployment env — it is banking-api-v1 or banking-api-v2. Replicas of the same Deployment share the value (not the pod hostname). The x-route-version column is the echo, from allHeaders, of the header injected by the RequestHeaderModifier on each backendRef — confirmation independent of the gateway's choice.

Comparison shortcuts /api/v1 and /api/v2

The same HTTPRoute also publishes two shortcuts without rewriting: /api/v1/accounts/summary always goes to banking-api-v1 and /api/v2/accounts/summary always goes to banking-api-v2. Useful to confirm the Services are healthy before drawing conclusions from the weighted sample.
