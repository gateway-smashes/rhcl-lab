### Req 19 — Motor de políticas com expressões personalizadas

**Requisito:** "A solução deve oferecer um motor de políticas que suporte
expressões personalizadas para definir regras de controle de acesso e
rate limiting com granularidade fina."

**Contexto RHCL:** O Red Hat Connectivity Link (baseado no Kuadrant) utiliza
**CEL (Common Expression Language)** como motor nativo de expressões
personalizadas. CEL permite escrever condições complexas que avaliam atributos
da requisição HTTP em tempo real, sem necessidade de linguagens externas.

CEL aparece em dois contextos nas policies do Kuadrant:

1. **`when` → `predicate`** (AuthPolicy, RateLimitPolicy) — expressões que
   determinam QUANDO uma regra se aplica.
2. **`counters` → `expression`** (RateLimitPolicy) — expressões que definem
   chaves de contagem dinâmica para rate limiting granular.

Referência: https://docs.kuadrant.io/dev/kuadrant-operator/doc/cel/introduction/

---

## O que é demonstrado

### AuthPolicy com CEL (`01-cel-custom-expressions.yaml`)

Abordagem **integrada**: a AuthPolicy usa o **mesmo nome** da policy de API Key
existente (`banking-api-connectivity-apikey`), fazendo um update in-place que
mantém a autenticação intacta e adiciona regras de **authorization** com CEL.

Regras de authorization adicionadas:

| Regra | Expressão CEL (when) | Efeito | Impacto |
|-------|---------------------|--------|---------|
| `cel-transfer-idempotency` | `request.method == 'POST' && request.path.startsWith('/api/v1/transfers')` + `request.headers['x-cel-strict'] == 'true'` | Exige `x-idempotency-key` | Nenhum — só ativa com `x-cel-strict: true` |
| `cel-bot-blocking` | `request.headers['user-agent'].contains('bot')` + `request.method != 'OPTIONS'` | Bloqueia com 403 | Nenhum — nenhum teste usa 'bot' |

### RateLimitPolicy com CEL (`02-cel-ratelimit-expressions.yaml`)

Uma `RateLimitPolicy` com expressões CEL em predicates e counters:

| Limit | Expressão CEL | Efeito |
|-------|---------------|--------|
| `financial-writes` | when: `request.method == 'POST' && (...transfers)` / counter: `request.headers['x-idempotency-key']` | 5 req/min por chave de idempotência |
| `reads-per-consumer` | when: `request.method == 'GET' && ...v1` / counter: `request.headers['x-consumer-id']` | 60 req/min por consumer |

### Funcionalidades CEL exercitadas

- Operadores lógicos: `&&`, `||`, `!`
- Funções de string: `startsWith()`, `contains()`
- Comparação direta de headers: `request.headers['x'] == 'value'`
- Expressões compostas com negação e agrupamento
- Extração de valores de headers como chave de counter

## Estratégia: integração na AuthPolicy principal

As regras CEL estão integradas diretamente no template Ansible da AuthPolicy
(`automation/roles/apps/templates/connectivity-authpolicy-apikey.yml.j2`),
sendo criadas automaticamente no provisionamento do ambiente. A abordagem:

1. Mantém todas as regras de **authentication** (API Key, CORS, WebSocket, etc.)
2. Inclui regras de **authorization** com expressões CEL
3. Preserva compatibilidade com PlanPolicy (`auth.identity` continua disponível)
4. Não impacta os demais testes (regras CEL ativadas por condições específicas)

### Para a RateLimitPolicy

A RateLimitPolicy **não conflita** da mesma forma — múltiplas RLPs podem
coexistir no mesmo target (desde que respeitem o limite de 2 entries em
`limits` por RLP). Porém, se já existe uma RLP no mesmo HTTPRoute, o Kuadrant
pode exigir que apenas uma seja enforced (depende da versão). Verificar:

```bash
oc get ratelimitpolicy -n rhcl-apps -o wide
```

Se houver conflito, remover a RLP existente ou aplicar a do req 19 no Gateway.

## Validação rápida

```bash
HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps \
       -o jsonpath='{.spec.hostnames[0]}')

# Verificar que a AuthPolicy está Enforced (já criada pelo Ansible)
oc get authpolicy banking-api-connectivity-apikey -n rhcl-apps \
  -o jsonpath='{.status.conditions[?(@.type=="Enforced")].status}'
# Esperado: True

# Fluxo normal preservado (API Key + sem bot)
curl -sk -o /dev/null -w "normal=%{http_code}\n" \
  -H "api-key: <SUA_API_KEY>" \
  "https://$HOST/api/v1/accounts/summary"

# CEL bot-blocking: user-agent com 'bot' → 403
curl -sk -o /dev/null -w "bot=%{http_code}\n" \
  -H "api-key: <SUA_API_KEY>" \
  -H "user-agent: scraperbot/1.0" \
  "https://$HOST/api/v1/accounts/summary"

# CEL idempotency (strict mode): sem key → 403
curl -sk -o /dev/null -w "no-key=%{http_code}\n" \
  -X POST "https://$HOST/api/v1/transfers" \
  -H "api-key: <SUA_API_KEY>" \
  -H "x-cel-strict: true" \
  -H "content-type: application/json" \
  -d '{"fromBank":"Example Bank","toBank":"EXT","amount":100}'

# CEL idempotency (strict mode): com key → 200
curl -sk -o /dev/null -w "with-key=%{http_code}\n" \
  -X POST "https://$HOST/api/v1/transfers" \
  -H "api-key: <SUA_API_KEY>" \
  -H "x-cel-strict: true" \
  -H "x-idempotency-key: txn-$(date +%s)" \
  -H "content-type: application/json" \
  -d '{"fromBank":"Example Bank","toBank":"EXT","amount":100}'
```

Resultado esperado:

```
normal=200
bot=403
no-key=403
with-key=200
```
