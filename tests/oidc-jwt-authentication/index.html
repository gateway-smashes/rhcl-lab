4. What was configured on the cluster for JWT to work

All configuration is declarative — three CRs versioned in Git, applied by the apps-install / rhbk-install playbook. The backend (banking-api) has no line of authentication code: the gateway delivers the request with the claims already trusted.

① AuthPolicy — rule jwt-keycloak

Adds a new identity to the banking-api AuthPolicy, alongside the api-key-header, api-key-query identities, the existing ai-mock and cors-preflight. Authorino accepts any identity it validates — so a client can use api-key, JWT or both. The scope is controlled by the when: block. 

apiVersion: kuadrant.io/v1
kind: AuthPolicy
metadata:
  name: banking-api-connectivity-apikey
  namespace: rhcl-apps
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: banking-api-connectivity
  rules:
    authentication:
      # ─── new identity: JWT issued by RHBK ─────────────
      jwt-keycloak:
        jwt:
          # Issuer URL = Keycloak base + /realms/<realm>.
          # Authorino fetches the JWKS at <issuer>/protocol/openid-connect/certs,
          # validates sig (RS256), iss, aud, exp. Automatic cache.
          issuerUrl: https://keycloak.<apps-domain>/realms/rhcl
        # CEL predicates — control WHERE this identity is required.
        # Other paths keep using api-key.
        when:
          - predicate: "request.path.startsWith('/api/whoami')"
          - predicate: "request.method != 'OPTIONS'"  # allows CORS preflight

② AuthPolicy — response.success block (injected claims)

Authorino reads the validated JWT claims and injects them as headers x-jwt-* on the upstream request. The backend receives everything already trusted — it just consumes the headers, revalidating nothing. 

spec:
  rules:
    response:
      success:
        headers:
          # auth.identity.* = JWT token claims after validation.
          x-jwt-sub:                { plain: { selector: "auth.identity.sub" } }
          x-jwt-preferred-username: { plain: { selector: "auth.identity.preferred_username" } }
          x-jwt-email:              { plain: { selector: "auth.identity.email" } }
          x-jwt-aud:                { plain: { selector: "auth.identity.aud" } }
          x-jwt-roles:              { plain: { selector: "auth.identity.realm_access.roles" } }
          # Unified header for audit/log — same key for api-key and JWT.
          x-consumer-id:            { plain: { selector: "auth.identity.metadata.name" } }

③ Keycloak — Client banking-api in realm rhcl

Imported via KeycloakRealmImport (RHBK Operator CR). Relevant snippet of the client: 

apiVersion: k8s.keycloak.org/v2alpha1
kind: KeycloakRealmImport
metadata:
  name: rhcl-realm
  namespace: rhcl-keycloak
spec:
  realm:
    realm: rhcl
    enabled: true
    roles:
      realm:
        - { name: banking-customer }
        - { name: banking-admin }
    clients:
      - clientId: banking-api
        publicClient: false               # confidential client (has secret)
        secret: banking-api-secret        # demo only — use External Secrets in production
        # Enables the password grant — used by this page's browser flow and by scripts.
        # In production use the OIDC redirect flow (PKCE) instead.
        directAccessGrantsEnabled: true
        standardFlowEnabled: true
        # webOrigins controls who Keycloak allows to make CORS against
        # /protocol/openid-connect/token. "*" allows any origin;
        # adjust to the real host of your SPAs in production.
        webOrigins: ["*"]
        redirectUris: ["*"]
    users:
      - { username: alice, enabled: true, credentials: [{ type: password, value: alice123 }],
          realmRoles: [banking-customer] }
      - { username: bob,   enabled: true, credentials: [{ type: password, value: bob123 }],
          realmRoles: [banking-customer, banking-admin] }
How the gateway discovers the JWKS (RFC 8414)

Authorino does GET <issuerUrl>/.well-known/openid-configuration at startup and on periodic refresh (configurable cache TTL). From there it gets the jwks_uri, fetches the public keys and uses them to validate the signature. There is no shared secret between gateway and Keycloak — trust is via the public JWKS.

5. Customization — flexibility for internal rules

The AuthPolicy exposes many extension points. All declarative, without changing the app. Below are the main "hooks" commonly used in banking production — each line can be adjusted via a Git PR, no rebuild.

Extension pointWhat you changeBanking example
Multiple identities coexisting rules.authentication.<name> accepts multiple entries (apiKey, jwt, oauth2, mtls, x509, anonymous, kubernetesTokenReview). Authorino tries each in parallel and accepts the first that validates. Internal employees use a JWT from federated AD/LDAP in Keycloak; legacy systems use api-key; external partners use mTLS. Same AuthPolicy.
Predicates CEL (when:) CEL expressions evaluated by the gateway. Access to request.method, request.path, request.headers, request.host, connection.requested_server_name, etc. "request.headers['x-channel'] == 'mobile'" only allows the /transfers/payments endpoint during business hours: "request.time.getHours() >= 6 && request.time.getHours() < 22".
Authorization by role/claim The rules.authorization block with opa.rego or patternMatching. Decision after auth — can use any JWT claim. POST /api/v1/transfers/>5000 requires banking-admin in roles + claim device_attested; POST /api/v1/cards/block requires auth.identity.acr == "urn:example:mfa:hardware".
OPA Rego for complex rules authorization.<name>.opa.rego accepts inline Rego policy (or via ConfigMap). Access to metadata, identity, the whole request and enriched attributes (geo-IP, fraud score, etc.). Block transfers when the 24h sum exceeds the plan limit + alert the SIEM via webhook. All in ~20 lines of Rego.
External metadata (enrichment) rules.metadata.http calls an external service during the request flow — fraud score, KYC, risk score, a payments directory — and the result becomes input to the authorization rules. Pre-approval calls the bank's fraud engine via POST /risk/score with user + amount + device; if score > 80 it requires step-up.
Step-up authentication Conditional response with WWW-Authenticate: Bearer error="insufficient_user_authentication" when the token's acr is insufficient. A normal login can read the balance (acr=urn:example:auth:password), but POST /transfers returns 401 with a hint to re-authenticate with biometrics (acr=urn:example:auth:biometric) — the frontend redirects to the Keycloak MFA flow.
Headers injected on the upstream response.success.headers allows any custom header, with a selector on auth.identity.*, auth.metadata.*, context.*. x-customer-segment: {{ auth.identity.attributes.segment }}, x-customer-id-hash: {{ sha256(auth.identity.customer_id) }}, x-trace-id: {{ context.request.id }}.
response.success.filters.identity block Transforms the identity before it is used by RateLimit or audit — useful to mask PII or collapse equivalent IDs. Already in use in the lab: extracts plan-id and user-id from the Secret annotations and exposes them to the RateLimitPolicy to decide the plan (gold/silver/bronze) per call.
Rate-limit by JWT claim RateLimitPolicy with counters using auth.identity.preferred_username or any claim as the discriminator. 50 req/min per user (claim sub), 10 req/min on /api/v1/transfers per user, 1000 req/min per aud (client app).
Structured audit logs gateway-error-logging: an EnvoyFilter + OTel Collector already capture every 4xx/5xx with claims + correlation_id + path. Custom headers via response.success.headers automatically enter the audit log. Compliance (e.g. GDPR): every denial goes to the SIEM with x-jwt-sub, x-customer-id-hash, request_id, auth.reason e trace_id (correlation with Tempo).
Federation with corporate AD/LDAP In Keycloak: User Federation → LDAP / Active Directory. Bank users log in with the corporate credential; AD roles become realm roles; all of this appears in the JWT claims. A corporate employee authenticates with their employee ID, claim realm_access.roles arrives with ["banking-customer","cib-trader"] — Rego decides access.
Allow-list policy by aud jwt.audiences: list of accepted audiences. Tokens with aud outside the list are rejected before validating any claim. The same Keycloak realm serves mobile and internet banking; The payments AuthPolicy only accepts tokens with aud=payments-app (prevents a web token from being reused for internal tools).

Composite example — rule "payments only with biometrics, in business hours, fraud-score < 80"

Combining the 4 extension points above. The whole rule fits in the AuthPolicy: 

spec:
  rules:
    metadata:
      fraud-score:
        http:
          urlExpression: '"https://fraud.example.internal/risk/score"'
          method: POST
          body:
            user: "{auth.identity.sub}"
            amount: "{request.body.amount}"
            device: "{request.headers.x-device-id}"
        sharedSecretRef: { name: fraud-service-token, key: token }

    authorization:
      payments-policy:
        opa:
          rego: |
            default allow = false
            allow {
              # 1. must be banking-customer
              input.auth.identity.realm_access.roles[_] == "banking-customer"
              # 2. must be business hours (6:00-22:00)
              hour := time.weekday_hour(input.context.request.time)
              hour >= 6; hour < 22
              # 3. step-up: biometric ACR
              input.auth.identity.acr == "urn:example:auth:biometric"
              # 4. fraud-score from enrichment < 80
              to_number(input.metadata["fraud-score"].score) < 80
            }
        when:
          - predicate: "request.method == 'POST' && request.path.startsWith('/api/v1/payments')"

All declarative, all in Git, all reviewable via PR. A regulatory rule change = a commit. No backend rebuild, no app maintenance window — just oc apply.
