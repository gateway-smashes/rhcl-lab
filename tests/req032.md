### Req 32 — Custom Policies via WasmPlugin

**Requisito:** "Permitir a criação de policies customizadas."

**Goal:** demonstrate that the RHCL gateway (Istio/Envoy) supports injecting
custom WASM-based policies beyond the built-in Kuadrant CRDs (AuthPolicy,
RateLimitPolicy, etc.). A custom **request-logger** Proxy-Wasm filter is
compiled, deployed to the gateway pods, and activated via an `EnvoyFilter` CR.
Every HTTP request passing through the gateway is logged as pretty-printed
JSON — proving that arbitrary user-written logic can run inside the Envoy
filter chain without modifying the upstream application.

---

## Scenario

```
                 ┌──────────┐
                 │  Client   │
                 └────┬──────┘
                      │  curl / browser
                      v
         ┌────────────────────────────────┐
         │   RHCL Gateway (Istio/Envoy)   │
         │                                │
         │   ┌──────────────────────────┐ │
         │   │  WASM Filter             │ │
         │   │  (request-logger)        │ │
         │   │                          │ │
         │   │  1. Capture headers      │ │
         │   │  2. Capture body (if any)│ │
         │   │  3. Emit JSON log line   │ │───► Gateway pod logs
         │   │  4. Forward unchanged    │ │     (oc logs ... | grep request-logger:)
         │   └──────────────────────────┘ │
         └────────────┬───────────────────┘
                      │  request forwarded unchanged
                      v
         ┌────────────────────────────────┐
         │  Upstream backend              │
         │  (any app behind the gateway)  │
         └────────────────────────────────┘
```

## Prerequisites

1. OpenShift cluster with RHCL (Istio-based gateway) installed.
2. `oc` CLI authenticated with access to the `ingress-gateway` namespace.
3. **For the Rust build:** Rust stable toolchain (`rustup` installed).
4. **For the Go build:** Go 1.24 or later.
5. At least one backend application already routed through the RHCL gateway
   (e.g. the PoC banking-api) so you have traffic to observe.

```bash
GATEWAY_NS=ingress-gateway
GATEWAY_LABEL="gateway.istio.io/managed=istio.io-gateway-controller"
```

## Implementation choice

Two implementations are provided — pick one:

| | Rust | Go |
|---|---|---|
| Binary size | ~276 KB | ~2.8 MB |
| Delivery | ConfigMap (under 1 MB limit) | Init container + OCI image |
| Envoy compat | Broad (V8 runtime) | Envoy ≥ 1.33 (WASI reactor) |
| SDK | [proxy-wasm-rust-sdk](https://github.com/proxy-wasm/proxy-wasm-rust-sdk) | [proxy-wasm-go-sdk](https://github.com/proxy-wasm/proxy-wasm-go-sdk) |

**Recommendation:** use the Rust version for simplicity (smaller binary,
ConfigMap delivery, broader Envoy compatibility). The instructions below
default to the Rust path; the Go alternative is documented in
`req032/go-version/README.md`.

## Build the WASM module (Rust)

```bash
cd tests/req032/rust-version
./build.sh
```

Output: `target/wasm32-unknown-unknown/release/rust_request_logger.wasm`

Verify the binary exists and is under 1 MB:

```bash
ls -lh target/wasm32-unknown-unknown/release/rust_request_logger.wasm
# ~ 276 KB
```

## Deploy to the gateway

### Step 1 — Create ConfigMap with the WASM binary

```bash
oc create configmap request-logger-wasm \
  --from-file=policy.wasm=target/wasm32-unknown-unknown/release/rust_request_logger.wasm \
  -n $GATEWAY_NS
```

Verify:

```bash
oc get configmap request-logger-wasm -n $GATEWAY_NS
# NAME                    DATA   AGE
# request-logger-wasm     1      ...
```

### Step 2 — Mount in gateway pods

```bash
GATEWAY_DEPLOYMENT=$(oc get deployment -n $GATEWAY_NS -o jsonpath='{.items[0].metadata.name}')

oc patch deployment $GATEWAY_DEPLOYMENT -n $GATEWAY_NS --type='json' -p='[
  {"op": "add", "path": "/spec/template/spec/volumes/-", "value": {
    "name": "request-logger-wasm", "configMap": {"name": "request-logger-wasm"}}},
  {"op": "add", "path": "/spec/template/spec/containers/0/volumeMounts/-", "value": {
    "name": "request-logger-wasm", "mountPath": "/var/lib/envoy/rust-request-logger.wasm",
    "subPath": "policy.wasm", "readOnly": true}}
]'
```

### Step 3 — Apply the EnvoyFilter

```bash
oc apply -n $GATEWAY_NS -f tests/req032/rust-version/kubernetes/envoyfilter-request-logger.yaml
```

Verify the EnvoyFilter was created:

```bash
oc get envoyfilter rust-request-logger-wasm -n $GATEWAY_NS
# NAME                          AGE
# rust-request-logger-wasm      ...
```

### Step 4 — Restart the gateway

```bash
oc rollout restart deployment -n $GATEWAY_NS
oc rollout status deployment/$GATEWAY_DEPLOYMENT -n $GATEWAY_NS --timeout=120s
```

## Test procedure

### 1. GET request — verify header logging

Send a simple GET to any route behind the gateway:

```bash
curl -sk https://<GATEWAY_HOST>/api/v1/accounts/summary
```

Check gateway pod logs:

```bash
oc logs -n $GATEWAY_NS -l $GATEWAY_LABEL --tail=50 | grep "rust-request-logger:"
```

**Expected:** a JSON log entry showing the request method, path, authority,
scheme, and all headers:

```json
{
  "method": "GET",
  "path": "/api/v1/accounts/summary",
  "authority": "<GATEWAY_HOST>",
  "scheme": "https",
  "headers": {
    ":method": "GET",
    ":path": "/api/v1/accounts/summary",
    ":authority": "<GATEWAY_HOST>",
    ":scheme": "https",
    "user-agent": "curl/...",
    "accept": "*/*"
  },
  "body": null
}
```

### 2. POST request — verify body logging

```bash
curl -sk -X POST https://<GATEWAY_HOST>/api/v1/transfers \
  -H 'content-type: application/json' \
  -d '{"fromBank":"Example Bank","toBank":"EXTERNAL","amount":500}'
```

Check logs again:

```bash
oc logs -n $GATEWAY_NS -l $GATEWAY_LABEL --tail=50 | grep -A 20 "rust-request-logger:"
```

**Expected:** the log entry includes the full JSON body:

```json
{
  "method": "POST",
  "path": "/api/v1/transfers",
  "authority": "<GATEWAY_HOST>",
  "scheme": "https",
  "headers": {
    ":method": "POST",
    ":path": "/api/v1/transfers",
    "content-type": "application/json"
  },
  "body": "{\"fromBank\":\"Example Bank\",\"toBank\":\"EXTERNAL\",\"amount\":500}"
}
```

### 3. Request forwarding — confirm observe-only behavior

The upstream response should be identical to what it returns without the WASM
filter. The filter never blocks or modifies requests.

```bash
# Must return 200 and valid JSON — same as without the filter
curl -sk -o /dev/null -w "%{http_code}\n" https://<GATEWAY_HOST>/api/v1/accounts/summary
# → 200
```

### 4. Remove the policy — confirm it is reversible

Delete the EnvoyFilter and verify logging stops:

```bash
oc delete envoyfilter rust-request-logger-wasm -n $GATEWAY_NS
oc rollout restart deployment -n $GATEWAY_NS
oc rollout status deployment/$GATEWAY_DEPLOYMENT -n $GATEWAY_NS --timeout=120s
```

Send another request and check logs:

```bash
curl -sk https://<GATEWAY_HOST>/api/v1/accounts/summary

oc logs -n $GATEWAY_NS -l $GATEWAY_LABEL --tail=20 | grep "rust-request-logger:"
# (no output — filter removed)
```

**Expected:** no `rust-request-logger:` entries in the logs after removing the
EnvoyFilter.

## How it works

The `EnvoyFilter` CR patches the Istio gateway's HTTP filter chain to insert
a WASM filter (`envoy.filters.http.wasm`) before the existing filters. Envoy
loads the `.wasm` binary from the ConfigMap-mounted path and creates a new
filter instance per request.

```
EnvoyFilter (rust-request-logger-wasm)
  ↓ patches
Envoy HTTP filter chain
  ├── envoy.filters.http.wasm  ← NEW (rust-request-logger)
  ├── envoy.filters.http.jwt_authn
  ├── envoy.filters.http.ext_authz  (Authorino)
  ├── envoy.filters.http.ratelimit  (Limitador)
  └── envoy.filters.http.router
```

The WASM filter uses the [Proxy-Wasm ABI](https://github.com/proxy-wasm/spec):

1. `on_http_request_headers` — captures all request headers (including
   pseudo-headers `:method`, `:path`, `:authority`, `:scheme`) into a local
   buffer so they remain available during the body callback.
2. `on_http_request_body` — waits for the full body (`Action::Pause` until
   `end_of_stream`), then reads the buffer.
3. Emits a single `warn`-level log line with pretty-printed JSON.
4. Returns `Action::Continue` — the request is never blocked or modified.

This pattern can be extended to implement any custom logic: header injection,
request transformation, custom authentication schemes, audit logging, etc.

## Go alternative (init-container delivery)

The Go binary (~2.8 MB) exceeds the Kubernetes ConfigMap 1 MB limit. Use the
init-container approach instead:

```bash
cd tests/req032/go-version
go mod tidy
./build.sh

# Build and push the OCI image
IMAGE=quay.io/<your-org>/request-logger-wasm:latest
podman build -t $IMAGE -f Containerfile.wasm .
podman push $IMAGE

# Patch gateway with init container
GATEWAY_DEPLOYMENT=$(oc get deployment -n $GATEWAY_NS -o jsonpath='{.items[0].metadata.name}')

oc patch deployment $GATEWAY_DEPLOYMENT -n $GATEWAY_NS --type='json' -p='[
  {"op": "add", "path": "/spec/template/spec/initContainers", "value": [{
    "name": "copy-wasm-plugin",
    "image": "'$IMAGE'",
    "command": ["/usr/bin/cp", "/plugin.wasm", "/wasm/request-logger.wasm"],
    "volumeMounts": [{"name": "wasm-plugins", "mountPath": "/wasm"}]
  }]},
  {"op": "add", "path": "/spec/template/spec/volumes/-", "value": {
    "name": "wasm-plugins", "emptyDir": {}}},
  {"op": "add", "path": "/spec/template/spec/containers/0/volumeMounts/-", "value": {
    "name": "wasm-plugins", "mountPath": "/var/lib/wasm-plugins", "readOnly": true}}
]'
```

> **Note:** Update the EnvoyFilter `filename` to
> `/var/lib/wasm-plugins/request-logger.wasm` when using this method.

## Cleanup

```bash
oc delete envoyfilter rust-request-logger-wasm -n $GATEWAY_NS 2>/dev/null || true
oc delete configmap request-logger-wasm -n $GATEWAY_NS 2>/dev/null || true

# Remove volume/volumeMount patches from the gateway deployment
GATEWAY_DEPLOYMENT=$(oc get deployment -n $GATEWAY_NS -o jsonpath='{.items[0].metadata.name}')

# Identify and remove the volume mount and volume by name
oc patch deployment $GATEWAY_DEPLOYMENT -n $GATEWAY_NS --type='json' -p="$(
  oc get deployment $GATEWAY_DEPLOYMENT -n $GATEWAY_NS -o json | \
  python3 -c "
import sys, json
d = json.load(sys.stdin)
patches = []
vols = d['spec']['template']['spec'].get('volumes', [])
for i, v in enumerate(vols):
    if v['name'] in ('request-logger-wasm', 'wasm-plugins'):
        patches.append({'op': 'remove', 'path': f'/spec/template/spec/volumes/{i}'})
mounts = d['spec']['template']['spec']['containers'][0].get('volumeMounts', [])
for i, m in enumerate(mounts):
    if m['name'] in ('request-logger-wasm', 'wasm-plugins'):
        patches.append({'op': 'remove', 'path': f'/spec/template/spec/containers/0/volumeMounts/{i}'})
inits = d['spec']['template']['spec'].get('initContainers', [])
for i, c in enumerate(inits):
    if c['name'] == 'copy-wasm-plugin':
        patches.append({'op': 'remove', 'path': f'/spec/template/spec/initContainers/{i}'})
print(json.dumps(patches))
"
)"

oc rollout restart deployment -n $GATEWAY_NS
```

## Result summary

| Step | Result |
|---|---|
| Build WASM binary | Compiles successfully (~276 KB Rust / ~2.8 MB Go) |
| Deploy via ConfigMap + EnvoyFilter | Filter loaded by Envoy without errors |
| GET request | Headers logged as JSON in gateway pod logs |
| POST request with body | Headers **and** body logged as JSON |
| Upstream response | Unchanged — filter is observe-only (`Action::Continue`) |
| Remove EnvoyFilter | Logging stops; gateway returns to default behavior |

**Conclusion:** RHCL supports custom policies via the Proxy-Wasm extension
mechanism. Any logic that can be compiled to a `.wasm` module — from simple
request logging to complex header manipulation, custom auth, or traffic
shaping — can be deployed to the gateway without modifying application code
or the RHCL control plane.
