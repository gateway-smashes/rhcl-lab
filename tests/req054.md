# Item 54 — Consumir backends em HTTP/1.1, HTTP/2 e HTTP/3

## Requisito demonstrado

| Item   | Requisito                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------- |
| **54** | Capacidade de **consumir backends** utilizando os protocolos HTTP/1.1, HTTP/2 e HTTP/3. |

> **Nota:** O enunciado original menciona "HTTP 1.2", porém essa versão não existe. Interpretamos como **HTTP/1.1**, que é a versão padrão do protocolo.

---

## Visão Geral

Este item demonstra como o gateway do RHCL (Envoy/Istio) se comunica com os **backends (upstream)** usando diferentes versões do protocolo HTTP. A direção avaliada aqui é **Gateway → Backend**, diferente do req057 que avalia **Cliente → Gateway**.

| Versão | Suporte upstream (Gateway → Backend) | Mecanismo de configuração |
|--------|--------------------------------------|---------------------------|
| HTTP/1.1 | **Suportado (GA)** — padrão | Comportamento default do Envoy; Service sem `appProtocol` ou com `appProtocol: http` |
| HTTP/2 (h2c) | **Suportado (GA)** | `appProtocol: kubernetes.io/h2c` no Service, ou `DestinationRule` com `h2UpgradePolicy: UPGRADE` |
| HTTP/3 (QUIC) | **Não suportado** | Veja seção abaixo |

---

## Diferença entre req054 e req057

| Aspecto | req054 (este) | req057 |
|---------|---------------|--------|
| **Direção** | Gateway → Backend (upstream) | Cliente → Gateway (downstream/ingress) |
| **O que demonstra** | Protocolo usado pelo Envoy para conectar ao pod do backend | Protocolo negociado entre o cliente externo e o gateway |
| **Configuração** | `appProtocol` no Service / `DestinationRule` | Listeners no Gateway (HTTP/HTTPS), ALPN, `alt-svc` header |
| **HTTP/3** | Não suportado (upstream usa TCP) | Experimental no ingress (QUIC/UDP) |

---

## HTTP/3 — Por que NÃO é suportado para comunicação com backends

O HTTP/3 (baseado em QUIC/UDP) **não é suportado** para conexões upstream (gateway → backend) pelos seguintes motivos:

1. **Arquitetura do Istio/Envoy:** O tráfego interno do service mesh sempre utiliza TCP. O Envoy conecta-se aos backends via HTTP/1.1 ou HTTP/2 sobre TCP, com mTLS opcional. HTTP/3/QUIC é suportado **apenas no ingress** (cliente → gateway).

2. **OpenShift Service Mesh 3.x — protocolos suportados:**
   A tabela oficial de features do OSSM 3.x lista apenas:
   > `Protocols: HTTP1.1/HTTP2/HTTPS/gRPC/TCP/TLS`
   
   HTTP/3 não consta na lista.

3. **Limitação do Envoy upstream:** O Envoy proxy não implementa QUIC como protocolo upstream. Mesmo na versão mais recente do Istio, QUIC é restrito ao listener do ingress gateway.

4. **Benefício mínimo em rede interna:** HTTP/3 foi projetado para redes instáveis (mobile, WAN). Em uma rede interna de data center (onde gateway e backend estão na mesma rede), HTTP/2 sobre TCP já oferece multiplexing e compressão de headers sem overhead do QUIC.

**Referências:**
- [Istio Wiki — Experimental QUIC/HTTP3 (ingress only)](https://github.com/istio/istio/wiki/Experimental-QUIC-and-HTTP-3-support-in-Istio-gateways)
- [OSSM 3.x Feature Support Tables](https://docs.redhat.com/en/documentation/red_hat_openshift_service_mesh/3.1/html/release_notes/ossm-release-notes-feature-support-tables)
- [Istio Issue #58247 — HTTP/3 não suportado via Gateway API para upstream](https://github.com/istio/istio/issues/58247)

## Como o RHCL implementa

| Capacidade | Como o RHCL implementa |
|---|---|
| **Backend HTTP/1.1** | Comportamento padrão — Envoy conecta via HTTP/1.1 ao pod. Nenhuma configuração adicional necessária |
| **Backend HTTP/2 (h2c)** | Service com `appProtocol: kubernetes.io/h2c` instrui o Envoy a usar HTTP/2 cleartext (sem TLS) para o upstream |
| **Negociação automática** | O Istio detecta o `appProtocol` do Service e configura o cluster upstream do Envoy automaticamente |
| **Validação via access log** | O campo `protocol` no access log do gateway mostra a versão usada no downstream; logs do backend confirmam a versão recebida |
| **Validação via endpoint** | O endpoint `/api/tls/info` do backend retorna o campo `alpn` indicando o protocolo negociado |

## Hostname dinâmico

O hostname é resolvido **dinamicamente** com base no domínio do cluster:

```
req054-backend.<CLUSTER_DOMAIN>
```

Exemplos:
- `req054-backend.apps.ocp.xxx.sandboxNNNN.opentlc.com` (lab)
- `req054-backend.apps.cluster.example.com` (produção)

Na **automação Ansible**, a variável `apps_req054_route_hostname` (ou default `req054-backend.<apps_effective_dns_suffix>`) controla o hostname. Nos **scripts manuais**, é detectado via `oc get ingresses.config.openshift.io cluster`.

## Componentes e manifests

Todos os manifests estão em [`req054/manifests/`](req054/manifests/):

| Manifest | O que cria | Namespace |
| --- | --- | --- |
| [`service-http11.yaml`](req054/manifests/service-http11.yaml) | Service apontando para banking-api-v1 (sem `appProtocol` → HTTP/1.1 upstream) | `rhcl-apps` |

## Aplicação

Pré-requisitos: banking-api-v1 já rodando (é ele que atende os dois
Services criados aqui) + gateway RHCL online.

Standalone (só os 3 manifests desta req):

```bash
cd tests/req054/manifests
oc apply -f service-http11.yaml   # backend Service pinado em HTTP/1.1
oc apply -f service-http2.yaml    # backend Service pinado em HTTP/2 (h2c)
oc apply -f httproute.yaml        # HTTPRoute com 2 rules escolhendo o service por match
```

Batch alternativo — o role `apps` gera os mesmos 3 objetos quando
`APPS_REQ054_ENABLED=true` (default):

```bash
cd automation
ansible-playbook playbooks/apps-install.yml
```

Pra desligar:

```bash
# manual
cd tests/req054/manifests
oc delete -f httproute.yaml -f service-http2.yaml -f service-http11.yaml

# ansible
APPS_REQ054_ENABLED=false ansible-playbook automation/playbooks/apps-install.yml
```

## Validação rápida

```bash
CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
HOST="req054-backend.${CLUSTER_DOMAIN}"

# HTTP/1.1 backend — path /http11
curl -sv http://$HOST/http11/api/v1/accounts/summary 2>&1 | head -20

# HTTP/2 backend — path /h2
curl -sv http://$HOST/h2/api/v1/accounts/summary 2>&1 | head -20
```

## Evidências da POC

| Evidência | Como demonstrar |
|---|---|
| **Backend HTTP/1.1** | `curl` via gateway para `/http11/*` retorna 200; access log mostra comunicação bem-sucedida |
| **Backend HTTP/2 (h2c)** | `curl` via gateway para `/h2/*` retorna 200; backend reporta `alpn: HTTP_2` via `/api/tls/info` |
| **appProtocol no Service** | `oc get svc -n rhcl-apps req054-backend-h2c -o yaml` mostra `appProtocol: kubernetes.io/h2c` |
| **HTTP/3 não suportado** | Documentação e tabela de features do OSSM 3.x; não há configuração possível para QUIC upstream |
