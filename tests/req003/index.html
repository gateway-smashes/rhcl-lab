REQ 03

Native HPA on the Gateway API data plane (autoscaling/v2)

Generates HTTP load against the connectivity gateway hostname so the HorizontalPodAutoscaler watching Deployment/rhcl-apps-gateway-istio in openshift-ingress scales from 2 to 6 replicas. The browser log shows RPS/latency; the source of truth is oc get hpa -w in the cluster (blocks below).

Scenario

[ browser @ this page ]
        |
        |  N parallel workers issuing GET (configurable path)
        v
[ Gateway data plane pod (istio-proxy) ] --> Pod CPU climbs --> metrics-server
                                                                   |
                                                                   v
                                          [ HPA rhcl-apps-gateway ]
                                          target: cpu 200m / mem 384Mi (AverageValue)
                                          min 2  ->  max 6
                                                                   |
                                                                   v
                            kube-controller-manager scales the gateway Deployment
The browser is a "best-effort" load generator. For an authoritative run (stable numbers, in-cluster metrics) use the oc run hey-loadgen ... block below. The HPA reacts the same way — what matters is the CPU on the target pods (the gateway data plane), not where the client runs. Hitting the backend host directly will not drive this HPA, because that path bypasses the gateway.

Controls

(the preset fills the Base URL — only "Via gateway" drives the HPA)

HPA manifest

Manifest applied to the cluster (also available at tests/req003/manifests/hpa-gateway.yaml). 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rhcl-apps-gateway
  namespace: openshift-ingress
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rhcl-apps-gateway-istio
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: AverageValue
          averageValue: 200m
    - type: Resource
      resource:
        name: memory
        target:
          type: AverageValue
          averageValue: 384Mi
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 15
      selectPolicy: Max
      policies:
        - type: Percent
          value: 100
          periodSeconds: 30
        - type: Pods
          value: 2
          periodSeconds: 30
    scaleDown:
      stabilizationWindowSeconds: 300
      selectPolicy: Max
      policies:
        - type: Pods
          value: 1
          periodSeconds: 60

Cluster commands (source of truth)

1) Apply the HPA
oc apply -f tests/req003/manifests/hpa-gateway.yaml
2) Watch the HPA scale
oc -n openshift-ingress get hpa rhcl-apps-gateway -w
3) Watch gateway pods coming up
oc -n openshift-ingress get pods \
  -l gateway.networking.k8s.io/gateway-name=rhcl-apps-gateway -w
4) HPA events (rescale reason)
oc -n openshift-ingress describe hpa rhcl-apps-gateway
5) Top CPU/mem per gateway pod (what the HPA sees)
oc -n openshift-ingress adm top pods \
  -l gateway.networking.k8s.io/gateway-name=rhcl-apps-gateway
6) Authoritative load via hey (in-cluster, hitting the gateway)
oc -n rhcl-apps run hey-loadgen --rm -i --tty --restart=Never \
  --image=quay.io/luksa/hey -- \
  -z 180s -c 100 \
  http://rhcl-apps-gateway-istio.openshift-ingress.svc.cluster.local/api/v1/accounts/summary
