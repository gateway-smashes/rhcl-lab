# Item 5 — Balanceamento de carga por peso

## Requisito Demonstrado

- **Item 5: Balanceamento de carga por peso** entre back-ends e entre clusters.

---

## Visão Geral

O Red Hat Connectivity Link sustenta dois eixos de balanceamento de carga ponderado, que podem ser combinados:

| Eixo | Onde acontece | Mecanismo |
|------|----------------|-----------|
| **Backend (intra-cluster)** | Dentro do cluster, no Envoy | `HTTPRoute.spec.rules[].backendRefs[].weight` |
| **DNS (inter-cluster)** | Antes de chegar ao cluster, na resolução do hostname | `DNSPolicy.spec.loadBalancing.weight` em provedores externos (Route53, Azure DNS, Cloud DNS) |

O cenário backend tem **dois caminhos prontos** no PoC, escolha conforme o que você quer demonstrar:

| Caminho | Onde está | Quando usar |
|---------|-----------|-------------|
| `/api/lb-test` (URLRewrite a nível de rule) | Embutido no `HTTPRoute` principal pelo playbook `apps-install` | Demo rápida sem aplicar nada — já vem ligado por default no install |
| `/api/whoami` (RequestHeaderModifier por backendRef) | Manifest standalone em [`req005/manifests/httproute-weighted.yaml`](req005/manifests/httproute-weighted.yaml) + console HTML em [`req005/index.html`](req005/index.html) | Demo no hostname dedicado `weighted.${RHCL_ZONE_ROOT_DOMAIN}` com canary 90/10 e console embutido. Documentação detalhada em [`req005/README.md`](req005/README.md) |

Os dois usam os backends `banking-api-v1` e `banking-api-v2` que rodam a mesma imagem com `APP_INSTANCE_NAME` diferente — o backend retorna esse env no campo `instance`, que é a fonte de verdade sobre qual Service o gateway escolheu.

## Pré-requisitos

```bash
# Login no cluster
oc whoami

# A aplicação banking-api já deve estar instalada (via apps-install playbook).
```

A rota `/api/lb-test` é pública (sem APIKey) — está exposta como anônima na `AuthPolicy` para facilitar a demonstração.

## Cenário 1 — Balanceamento intra-cluster (backend weights)

### 1a. Caminho integrado — `/api/lb-test` no install padrão

A rota `/api/lb-test` já vem no HTTPRoute principal `banking-api-connectivity`
(rendered pelo role `apps` quando `APPS_CONNECTIVITY_LB_TEST_ENABLED=true`,
o default). Se a rota já está no cluster, mudar os pesos é um patch
direto — não precisa re-rodar playbook nenhum:

```bash
# ex.: 80% v1 / 20% v2
oc -n rhcl-apps patch httproutes.gateway.networking.k8s.io banking-api-connectivity \
  --type=json -p='[
    {"op":"replace","path":"/spec/rules/6/backendRefs/0/weight","value":80},
    {"op":"replace","path":"/spec/rules/6/backendRefs/1/weight","value":20}
  ]'
# Confere qual rule é a de LB (o index pode variar):
oc -n rhcl-apps get httproutes.gateway.networking.k8s.io banking-api-connectivity \
  -o jsonpath='{range .spec.rules[*]}{.matches[0].path.value}{"  "}{range .backendRefs[*]}{.name}={.weight} {end}{"\n"}{end}'
```

Se preferir gerenciar tudo pelo declarativo, os defaults + envs seguem
disponíveis via role `apps`:

| Variável | Default | Descrição |
|----------|---------|-----------|
| `APPS_CONNECTIVITY_LB_TEST_ENABLED` | `true` | Habilita a rota `/api/lb-test` |
| `APPS_CONNECTIVITY_LB_TEST_PATH` | `/api/lb-test` | Path público de teste |
| `APPS_CONNECTIVITY_LB_V1_WEIGHT` | `50` | Peso do `banking-api-v1` |
| `APPS_CONNECTIVITY_LB_V2_WEIGHT` | `50` | Peso do `banking-api-v2` |

```bash
APPS_CONNECTIVITY_LB_V1_WEIGHT=80 \
APPS_CONNECTIVITY_LB_V2_WEIGHT=20 \
ansible-playbook automation/playbooks/apps-install.yml -e apps_skip_build=true
```

A rota usa `URLRewrite` a **nível de rule** (`HTTPRouteRule.filters`) reescrevendo `/api/lb-test` → `/api/echo`. Esse uso de `URLRewrite` é suportado pelo controller Istio do OpenShift Gateway API. **Atenção**: `URLRewrite` em `HTTPBackendRef.filters` (por backendRef) é rejeitado com `InvalidFilter` — esse é o motivo do caminho 1b ter sido escolhido para o demo standalone.

### 1b. Caminho standalone — `/api/whoami` com hostname dedicado

Variante mais elaborada, com hostname próprio (`weighted.${RHCL_ZONE_ROOT_DOMAIN}`), pesos default 90/10 (canary), e injeção de `x-route-version: v1|v2` via `RequestHeaderModifier` por backendRef. A documentação completa, manifestos e console HTML estão em [`req005/README.md`](req005/README.md).

### Validação manual via curl

```bash
HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')

# Bater 100x e contar a distribuição
for i in $(seq 1 100); do
  curl -sk "https://$HOST/api/lb-test" | jq -r '.instance'
done | sort | uniq -c
```

Saída esperada com pesos 50/50 (aproximadamente):

```
  52 banking-api-v1
  48 banking-api-v2
```

### Validação visual — PoC Console

Abra o frontend `mobile-bank` e navegue até `PoC Console → Load Balancing`:

1. Configure o número de requisições (10–500)
2. Clique em **Run**
3. A barra de distribuição mostra a divisão real entre v1/v2
4. A tabela detalha as contagens, e o log cronológico mostra a ordem de chegada

## Cenário 2 — Balanceamento inter-cluster (DNS weights)

> Requer um **segundo cluster** com gateway próprio publicando o mesmo hostname. Use `DNSPolicy.loadBalancing.weight` para que o provedor DNS (Route53/Azure/GCP) entregue resoluções proporcionais ao peso. Manifest standalone em [`req005/dnspolicy-weighted.yaml`](req005/dnspolicy-weighted.yaml).

### Setup do segundo cluster

Em cada cluster, o objeto é a `DNSPolicy` que anexa peso no registro DNS
do hostname. Você pode aplicar diretamente:

```bash
# No cluster A (peso 80) — edita o manifest antes ou usa envsubst
export WEIGHT=80 && envsubst < tests/req005/manifests/dnspolicy-weighted.yaml | oc apply -f -

# No cluster B (peso 20)
export WEIGHT=20 && envsubst < tests/req005/manifests/dnspolicy-weighted.yaml | oc apply -f -
```

Se o cluster já tem uma `DNSPolicy` gerenciada, só faça patch do peso:

```bash
oc -n openshift-ingress patch dnspolicy rhcl-apps-gateway --type=merge \
  -p '{"spec":{"loadBalancing":{"weight":80}}}'
```

Batch alternativo — via `role rhcl`:

```bash
RHCL_DNS_POLICY_LOAD_BALANCING_ENABLED=true \
RHCL_DNS_POLICY_WEIGHT=80 \
ansible-playbook automation/playbooks/dns-install.yml
```

Ambos os clusters precisam apontar pro mesmo `RHCL_ZONE_ROOT_DOMAIN` e usar o mesmo `RHCL_DNS_PROVIDER` com credenciais com permissão na hosted zone compartilhada.

### Validação

```bash
# Resolver o hostname N vezes e ver IPs distintos
for i in $(seq 1 20); do
  dig +short banking-api-connectivity.<root-domain> @8.8.8.8 | head -1
done | sort | uniq -c
```

Saída esperada com pesos 80/20:

```
  16 <IP-do-cluster-A>
   4 <IP-do-cluster-B>
```

> **Cache TTL:** o resolver pode cachear a resposta. Use `+nocache` no `dig` ou diferentes resolvers (1.1.1.1, 8.8.8.8) pra observar a distribuição real.

### Combinando os dois eixos

Os dois balanceamentos compõem: o DNS escolhe o cluster, o HTTPRoute escolhe o backend. Em produção isso permite uma estratégia tipo:

- Cluster A (80% via DNS) com backend v1=70, v2=30
- Cluster B (20% via DNS) com backend v1=0, v2=100 (canary do v2)

Resultando em distribuição efetiva: v1=56%, v2=24%+20%=44%.

## Notas técnicas

- **`URLRewrite` no Gateway API:** O filtro `URLRewrite` reescreve o path antes do envio ao backend. No OpenShift Gateway API (controller Istio) é aceito **a nível de rule** (`HTTPRouteRule.filters`) — usado em `/api/lb-test` para mapear para `/api/echo`. **NÃO** é aceito por `backendRef` (`HTTPBackendRef.filters`) — o controller marca como `InvalidFilter`. Para diferenciar versão por backendRef use `RequestHeaderModifier` (caminho 1b).
- **Distribuição estatística:** A escolha do backend por requisição é feita pelo Envoy via random weighted choice. Em volumes baixos (~10) a distribuição pode parecer desbalanceada; com 100+ requests o desvio fica < 5%.
- **`alt-svc` automático:** Como `/api/lb-test` herda os filtros padrão da rota, o header `alt-svc: h3=":443"` é enviado também nessas respostas (item 057).
- **Headers de identificação:** A rota `/api/lb-test` adiciona `x-lb-target-path: /api/echo` na resposta para facilitar troubleshooting. A rota `/api/whoami` (caminho 1b) injeta `x-route-version: v1|v2` por backendRef.
- **DNSPolicy + Geo:** O campo `geo` no `loadBalancing` permite estratégia geográfica (`GEO-NA`, `GEO-EU` etc.) — sem ele, o peso é avaliado globalmente. Quando `defaultGeo: true`, o cluster atende qualquer região como fallback.
