Per-route timeouts

Per-route request timeouts origin: …

Demonstrates that the gateway (RHCL / Gateway API) enforces a request timeout independent of how long the backend takes to respond. When the backend is slower than the timeout configured for the route, the gateway ends the call with 504 Gateway Timeout without waiting for the backend.

Scenario

[ client ]                         [ RHCL / Gateway ]                   [ backend ]
    |                                       |                                |
    |  GET /api/test/echo-error?delay=1500  |                                |
    |-------------------------------------> |                                |
    |                                       |  forwards to the backend       |
    |                                       |------------------------------> |
    |                                       |  (gateway timeout = 2000ms)    |
    |                                       |                                |
    |                                       |  response after 1500ms         |
    |                                       | <----------------------------- |
    |  HTTP 200 OK                          |                                |
    | <-------------------------------------|                                |
    |                                       |                                |
    |  GET /api/test/echo-error?delay=5000  |                                |
    |-------------------------------------> |------------------------------> |
    |                                       |  (gateway timeout = 2000ms)    |
    |                                       |  *** fires after 2000ms ***    |
    |  HTTP 504 Gateway Timeout             |                                |
    | <-------------------------------------|                                |
    |                                       |                                |
    |                                       |  backend still processing      |
    |                                       |  (pod log records the request) |
What this page proves. The duration measured by the browser shows the gateway cutting the request around the configured timeout even when the backend was told to take longer. The endpoint /api/test/echo-error?delay=N makes the backend sleep N ms before responding, so comparing the elapsed time and the HTTP status makes it clear the limit came from the gateway, not the backend.

Controls

backend delay = 3000 ms (fixed on /api/v1/timeout)

Dedicated endpoint /api/v1/timeout (fixed 3s)

The backend has a single endpoint /api/v1/timeout that sleeps 3 seconds before responding. The HTTPRoute exposes the same backend over two external paths with different timeouts — click both buttons to see them side by side:

  • /api/v1/timeout — route timeout = 2s → gateway cuts with 504.
  • /api/v1/timeout-longer — route timeout = 30s; the gateway rewrites to /api/v1/timeout before calling the backend, so the message arrives in ~3s.

Test matrix

Every route reaches the same backend endpoint (/api/v1/timeout, which sleeps 3s). The difference is the timeouts.request on each rule of the HTTPRoute:

External path Route timeout Final backend Who responds Expected result
/api/v1/timeout 2000 ms /api/v1/timeout Gateway 504 in ~2000 ms
/api/v1/timeout-longer 30000 ms /api/v1/timeout (URLRewrite) Backend 200 OK in ~3000 ms
direct backend — /api/v1/timeout Backend 200 OK in ~3000 ms
Different timeouts per endpoint. The Gateway API lets you set timeouts.request on each rule of the HTTPRoute. Combined with the URLRewrite filter, you can expose the same backend endpoint over different external paths with distinct limits — proving the timeout is tied to the route, not to the upstream resource.
