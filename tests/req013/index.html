REQ 13

Timeout por endpoint/recurso origin: …

Demonstra que o gateway (RHCL / Gateway API) impõe um timeout de requisição independente do tempo que o backend leva para responder. Quando o backend é mais lento que o timeout configurado para a rota, o gateway encerra a chamada com 504 Gateway Timeout sem esperar o backend.

Cenário

[ cliente ]                        [ RHCL / Gateway ]                   [ backend ]
    |                                       |                                |
    |  GET /api/test/echo-error?delay=1500  |                                |
    |-------------------------------------> |                                |
    |                                       |  encaminha para o backend      |
    |                                       |------------------------------> |
    |                                       |  (timeout do gateway = 2000ms) |
    |                                       |                                |
    |                                       |  resposta após 1500ms          |
    |                                       | <----------------------------- |
    |  HTTP 200 OK                          |                                |
    | <-------------------------------------|                                |
    |                                       |                                |
    |  GET /api/test/echo-error?delay=5000  |                                |
    |-------------------------------------> |------------------------------> |
    |                                       |  (timeout do gateway = 2000ms) |
    |                                       |  *** dispara após 2000ms ***   |
    |  HTTP 504 Gateway Timeout             |                                |
    | <-------------------------------------|                                |
    |                                       |                                |
    |                                       |  backend ainda está processando|
    |                                       |  (log do pod registra o pedido)|
O que esta página prova. A duração medida pelo navegador mostra que o gateway corta a requisição em torno do timeout configurado mesmo quando o backend foi instruído a demorar mais. O endpoint /api/test/echo-error?delay=N faz o backend dormir N ms antes de responder, então comparando o tempo decorrido e o status HTTP fica claro que o limite veio do gateway, não do backend.

Controles

delay do backend = 3000 ms (fixo em /api/v1/timeout)

Log

Endpoint dedicado /api/v1/timeout (3 s fixos)

O backend tem um único endpoint /api/v1/timeout que dorme 3 segundos antes de responder. A HTTPRoute expõe o mesmo backend por dois paths externos com timeouts diferentes — clique nos dois botões para ver lado a lado:

  • /api/v1/timeout — timeout da rota = 2 s → gateway corta em 504.
  • /api/v1/timeoutmaior — timeout da rota = 30 s; o gateway reescreve para /api/v1/timeout antes de chamar o backend, então a mensagem chega em ~3 s.
(aguardando)
A mensagem retornada pelo backend aparecerá aqui depois de ~3 segundos.

Matriz de testes

Todas as rotas chegam ao mesmo endpoint do backend (/api/v1/timeout, que dorme 3 s). A diferença está no timeouts.request de cada rule da HTTPRoute:

Path externo Timeout da rota Backend final Quem responde Resultado esperado
/api/v1/timeout 2000 ms /api/v1/timeout Gateway 504 em ~2000 ms
/api/v1/timeoutmaior 30000 ms /api/v1/timeout (URLRewrite) Backend 200 OK em ~3000 ms
backend direto — /api/v1/timeout Backend 200 OK em ~3000 ms
Diferentes timeouts por endpoint. O Gateway API permite definir timeouts.request em cada rule da HTTPRoute. Combinado com o filtro URLRewrite, é possível expor o mesmo endpoint do backend em paths externos diferentes com limites distintos — provando que o timeout é amarrado à rota, não ao recurso de upstream.
