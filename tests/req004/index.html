Item 4 Resiliência do gateway à indisponibilidade do control plane

Requisito: "Os gateways devem conseguir suportar uma indisponibilidade do manager sem interrupção de nenhuma funcionalidade."

O Connectivity Link separa control plane (operadores que reconciliam recursos) de data plane (Envoy/Authorino/Limitador que atendem o tráfego). A demo mostra que derrubar todo o CP do kuadrant-system não interrompe o tráfego.

O que degrada — categorias

A — Degradação imediata (em segundos)

  • Mudanças param de propagar: novas AuthPolicy/RateLimitPolicy/HTTPRoute ficam pendentes no etcd até o CP voltar.
  • Scaling automático para: HPA depende do kube-apiserver. Se a carga subir, não há scale-up.
  • Pod restarts são fatais: se um pod do data plane morrer durante a queda do kube-apiserver, o scheduler não agenda substituto.

B — Degradação por tempo (relógio)

  • Cert-manager parado: renovação não acontece → eventualmente Routes com TLS expiram (cert-manager renova com ~30 dias de folga, então a tolerância é alta).
  • JWKS cache do Authorino: se o Keycloak/OAuth também estiver down, eventualmente o TTL expira e JWT começa a falhar.
  • Metadata externa do Authorino: chamadas a serviços externos para enrichment têm cache TTL.

C — Degradação por contrato (rate limit / Redis)

Modo do Limitador Redis cai Comportamento
in-memory N/A Sem Redis — contadores morrem com o pod do Limitador.
redis-cached Down Cache local por site → contadores divergem (over-admite).
redis puro Down Cada check vai pro Redis → failure_mode decide entre fail-open e fail-closed.

A postura precisa ser decidida explicitamente por API: "fail-open" é o padrão pragmático (não derruba a app por causa de Redis indisponível, perde temporariamente a proteção); "fail-closed" preserva o limite mesmo que custe o SLA.

D — Degradação especial: Authorino failureMode

O Envoy chama Authorino via ext_authz. Se o serviço Authorino estiver completamente down:

  • Default Kuadrant: failureModeAllow: false → request é negado (fail-closed).
  • APIs auth-protegidas ficam indisponíveis durante a queda.
  • O oposto (fail-open) deixaria APIs autenticadas servirem sem auth — geralmente inaceitável em banco.

Recomendações de produção

Reduzir a probabilidade

  • HA dos operadores: default replicas: 1. Em prod, subir kuadrant-operator, authorino-operator, limitador-operator pra replicas: 2 com leader election (suportam).
  • HA do istiod: já vem com replicas: 2 no OSSM 3 produção.
  • HA do data plane: Limitador e Authorino aceitam scale horizontal. Recomendar replicas: 3+ em prod.
  • HA do Redis: trocar o emptyDir da PoC por Redis Enterprise / ElastiCache / Sentinel.
  • HA do Keycloak/OAuth: cluster Keycloak com 2+ instâncias atrás de LB; PostgreSQL replicado.

Reduzir o impacto

  • Monitoring agressivo nos operadores — kuadrant_operator_reconcile_errors_total é um proxy direto de "CP saudável".
  • Políticas via GitOps (ArgoCD) — se o etcd voltar zerado, restauração é minutos, não horas.
  • Pre-staged config: data plane com imagePullPolicy: IfNotPresent e imagens local-cacheadas.
  • Decisão de failure mode por API: endpoints críticos (Pix, transferência) fail-closed; endpoints de leitura (saldo) fail-open por SLA.

Reduzir o tempo de recuperação

  • Runbook por componente — cada operador tem comandos de health/reset documentados.
  • CR backups automatizados (Velero) — RTO ditado pelo tempo do oc apply do snapshot.
