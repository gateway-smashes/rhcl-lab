CORS policy

CORS no Gateway origin: …

Shows that the backend /api/v1/cors emits no Access-Control-Allow-* headers: the browser blocks cross-origin calls straight to the backend. The HTTPRoute on cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN} injects these headers via ResponseHeaderModifier and the browser releases the response.

Scenario

[ browser @ this page's origin ]  
        |
        |  fetch(the URL chosen below)
        v
[ direct backend         ]   --> blocked: no Access-Control-Allow-Origin
[ via cors.      ]   --> allowed: gateway adds CORS headers
First, open DevTools. When CORS blocks a call, JavaScript only sees TypeError: Failed to fetch. The detailed message ("No 'Access-Control-Allow-Origin' header is present") only appears in the browser Console (F12) and Network tabs. Keep DevTools open during the test.

Matriz de testes

Same /api/v1/cors backend endpoint, but two paths to the browser:

Fetch origin URL called CORS headers in response Expected result
page on another origin https://banking-api-v1-rhcl-apps.<cluster>/api/v1/cors none fetch blocked by the browser
page on another origin https://cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN}/api/v1/cors Access-Control-Allow-* (gateway) 200 OK, body read normally
curl / same origin either one none (curl) / doesn't matter (same-origin) 200 OK — CORS is a browser rule
CORS is browser-only. The backend keeps responding to everyone; what changes is the browser letting JS read the response. Demonstrated by running the test from http://localhost:8080 (a different origin than the cluster) — the fetch only "sees" the data when it goes through the cors.${"$"}{RHCL_ZONE_ROOT_DOMAIN}.
