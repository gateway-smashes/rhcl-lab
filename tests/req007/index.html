Item 7 Balanceamento de carga com suporte à sessão

Requisito: afinidade de sessão entre réplicas do backend, configurada por cookie HTTP no nível do gateway.

Esta demo usa o backend banking-api-v1 (que já está exposto pelo rhcl-apps-gateway via HTTPRoute banking-api-connectivity), com 2+ réplicas e uma DestinationRule do Istio aplicando consistentHash.httpCookie.

Caminho importa — a demo precisa usar o hostname do rhcl-apps-gateway (Gateway API). Se entrar pela Route OCP padrão (*.apps.<cluster>), o tráfego vai HAProxy → Service direto, bypassa o Istio, e a DestinationRule é silenciosamente ignorada. O "sticky" que aparece nesse caminho vem do cookie default do HAProxy, não do CUSTOM_COOKIE_SESSION do Envoy.

Configuração

Setup Uma vez por cluster

1. Escalar para 2 réplicas

Sticky com 1 réplica é falso-positivo (todo request vai pro mesmo pod independentemente da DR). 

oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=2
oc rollout status deploy/banking-api-v1 -n rhcl-apps

2. Backend reporta o nome do pod no /api/echo

O Quarkus lê APP_INSTANCE_NAME e devolve no campo instance. Trocar o valor fixo por fieldRef faz cada pod reportar seu próprio nome. 

oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME-

oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/template/spec/containers/0/env/0",
    "value": {
      "name": "APP_INSTANCE_NAME",
      "valueFrom": {"fieldRef": {"fieldPath": "metadata.name"}}
    }
  }
]'
oc rollout status deploy/banking-api-v1 -n rhcl-apps

3. Patch da DestinationRule existente

A DestinationRule banking-api-v1-http1 já existe (cuida do connection pool). Só adicionar o loadBalancer: 

oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/trafficPolicy/loadBalancer",
    "value": {
      "consistentHash": {
        "httpCookie": {
          "name": "CUSTOM_COOKIE_SESSION",
          "path": "/",
          "ttl": "1800s"
        }
      }
    }
  }
]'

1 Baseline — round-robin sem cookie

Sem cookie, a DR não tem chave de hash, então o Envoy faz round-robin e o tráfego se distribui entre os 2 pods. Esse passo prova que a DR está ativa e que existem múltiplos pods atrás do Service. 

HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')
for i in $(seq 1 10); do
  # 503s ocasionais do backend não derrubam o script
  curl -sk "https://$HOST/api/echo" 2>/dev/null \
    | python3 -c '
import json, sys
try: print(json.load(sys.stdin).get("instance",""))
except: pass
' 2>/dev/null
done | grep -v '^$' | sort | uniq -c

2 Verificar caminho (browser) + Set-Cookie (CLI)

No navegador (cross-origin), Set-Cookie é um "forbidden response header" da spec do Fetch — JS nunca consegue ler ele. Então o botão aqui valida o que é possível ver pelo browser: que a chamada chega no backend e que o instance do /api/echo está com nome de pod (= setup do APP_INSTANCE_NAME via fieldRef deu certo). Se vier backend-a, a env var não chegou no processo (default do Quarkus).

Para ver o cookie literal, só via CLI:

curl -sk -i "https://$HOST/api/echo" | grep -i 'set-cookie'
# set-cookie: CUSTOM_COOKIE_SESSION="37c5519780cbe86f"; Max-Age=1800; Path=/; HttpOnly

3 Sticky — 5 cookies × N reqs

Cada cookie representa uma sessão. Cada sessão deve grudar em um único pod. Cookies diferentes podem cair em pods diferentes (distribuição é hash-based). 

for cookieval in aaa111 bbb222 ccc333 ddd444 eee555; do
  pods=$(for i in $(seq 1 8); do
    curl -sk -H "Cookie: CUSTOM_COOKIE_SESSION=$cookieval" \
         "https://$HOST/api/echo" 2>/dev/null \
      | python3 -c '
import json, sys
try: print(json.load(sys.stdin).get("instance",""))
except: pass
' 2>/dev/null
  done | grep -v '^$' | sort -u | tr '\n' ',' | sed 's/,$//')
  echo "cookie=$cookieval → pods: $pods"
done

Troubleshooting

SintomaDiagnóstico
Set-Cookie vem com nome <md5hash> em vez de CUSTOM_COOKIE_SESSION Tráfego entrou pela Route OCP, não pelo Gateway API. Verificar que o hostname bate com o spec.hostnames da HTTPRoute banking-api-connectivity.
Round-robin acontece mesmo com cookie A DR não foi aplicada ou o host da DR não bate com o Service. oc get destinationrule banking-api-v1-http1 -n rhcl-apps -o yaml.
401 / 403 em /api/echo Algum AuthPolicy gateway-level deny-all está pegando. A rota /api/echo é anonymous no banking-api-connectivity-apikey AuthPolicy — conferir Enforced=True.
instance sempre o mesmo, mas tem 2 réplicas APP_INSTANCE_NAME ainda está fixo. Re-rodar o passo 2 do setup (fieldRef metadata.name).
Sticky degrada após oc rollout restart Esperado — pods novos têm nomes novos, hash do cookie mapeia pra outro bucket. Sessões abertas antes do restart "saltam" pra um pod (ainda estável dali em diante).

Rollback

# Voltar DR para o estado original (sem sticky)
oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/trafficPolicy/loadBalancer"}
]'

# Voltar APP_INSTANCE_NAME para valor fixo
oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/template/spec/containers/0/env/0"}
]'
oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME=banking-api-v1
oc rollout status deploy/banking-api-v1 -n rhcl-apps

# (Opcional) voltar a 1 réplica
oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=1
