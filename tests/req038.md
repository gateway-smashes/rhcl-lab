# Item 38 — Expor trace e métricas nos padrões OpenTelemetry

## Requisito demonstrado


| Item   | Requisito                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| **38** | Capacidade de **expor traces e métricas nos padrões OpenTelemetry** a partir do gateway e das políticas gerenciadas pelo RHCL. |


O RHCL 1.3 atende este requisito com dois mecanismos complementares:


| Sinal        | Padrão nativo          | Como demonstrar no padrão OpenTelemetry                                                                                                                                                                                         |
| ------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Traces**   | OTLP (gRPC/HTTP)       | Direto — gateway, Authorino, Limitador e wasm-shim exportam spans OTLP para um OpenTelemetry Collector.                                                                                                                         |
| **Métricas** | Prometheus/OpenMetrics | Via Collector — o RHCL expõe métricas Prometheus; o OpenTelemetry Collector pode coletá-las e exportá-las como OTLP Metrics. Para a POC, o scrape nativo via OpenShift Monitoring + `ServiceMonitor`/`PodMonitor` é suficiente. |


Referência: [RHCL 1.3 — Observability](https://docs.redhat.com/en/documentation/red_hat_connectivity_link/1.3/html/observability/rhcl-observability)

## Stack de observabilidade da POC

```text
Client
  ↓
Gateway / Envoy (istio-proxy)   ←  EnvoyFilter injeta tracer OpenTelemetry
  ↓
RHCL policies: AuthPolicy / RateLimitPolicy
  ↓  Authorino / Limitador / wasm-shim   ←  Kuadrant observability.tracing
OpenTelemetryCollector   ←  recebe spans OTLP (gRPC :4317)
  ↓
TempoStack               ←  armazena traces (backend S3: MinIO)
  ↓
OpenShift Console — Observe → Traces (via COO UIPlugin)
  ↓
Jaeger UI (deprecated)    ←  visualização alternativa
```

### Nota sobre o Istio CR e a abordagem EnvoyFilter

A documentação oficial do OSSM 3.3 recomenda configurar `extensionProviders` diretamente no Istio CR. Porém, neste cluster o Istio CR (`openshift-gateway`) é **gerenciado pelo controller da GatewayClass** (`openshift-default`), que reconcilia e reverte qualquer modificação via `oc patch` ou `oc apply`. Por isso, o tracing do gateway é configurado via **EnvoyFilter**, que injeta o tracer `envoy.tracers.opentelemetry` diretamente nos listeners do Envoy proxy.

### Gerar tráfego de teste

O endpoint `/api/echo` é público (não exige API Key) e retorna detalhes do request, incluindo headers de tracing (`traceparent`, `tracestate`):

```bash
curl -vk -H "x-request-id: poc-rhcl-otel-001" \
  https://banking-api.poc.rhcl.com.br/api/echo
```

> **Nota:** A flag `-k` (`--insecure`) é necessária porque o certificado TLS do cluster cobre apenas o domínio `*.apps.cluster1.sandbox1992.opentlc.com`, não o CNAME personalizado `banking-api.poc.rhcl.com.br`.

## Propagação de traces backend→backend (W3C tracecontext)

Além de **capturar** spans do gateway e das políticas, a POC demonstra a **propagação** do
contexto de trace entre microserviços. Para isso há um segundo backend — o microserviço
**`ledger-api`** — que é chamado pelo `banking-api`, encadeando os spans sob um **único Trace
ID**:

```text
PoC Console / curl
  ↓ (HTTPS)
Gateway / Envoy            ← inicia o trace e injeta o header W3C `traceparent`
  ↓
banking-api  (/api/test/propagate)
  ├─ DIRETO   → http://ledger-api.rhcl-apps.svc.cluster.local:8080/ledger/record
  └─ GATEWAY  → http://<ledger-api hostname>/ledger/record  (HTTPRoute + AuthPolicy allow-all)
                 ↓
              ledger-api  (/ledger/record)

Trace (1 Trace ID): rhcl-gateway → banking-api (server) → banking-api (client) → ledger-api (server)
                    [+ span do Envoy/Authorino/Limitador no hop interno quando target=gateway]
```

### A propagação é configuração, não código

O ponto central deste requisito: **nenhum código de instrumentação OpenTelemetry** foi escrito
nas aplicações. A propagação é feita inteiramente por configuração RHCL/OTel:

| Mecanismo | Onde | O que faz |
|---|---|---|
| `Instrumentation` CR (`rhcl-apps-java`) | role `apps` ([connectivity-instrumentation.yml.j2](../automation/roles/apps/templates/connectivity-instrumentation.yml.j2)) | `propagators: [tracecontext, baggage]` — o agente Java propaga o `traceparent` W3C |
| Anotação `instrumentation.opentelemetry.io/inject-java: "true"` | Deployments do `banking-api` e do `ledger-api` | o OpenTelemetry Operator injeta o agente Java (init container) — instrumenta entrada **e** saída HTTP |
| `EnvoyFilter` de tracing | gateway (req038, manifest `05`) | o Envoy inicia o trace e injeta o `traceparent` na requisição ao `banking-api` |

Resultado: o agente do `banking-api` **extrai** o `traceparent` recebido do gateway e o
**reinjeta** automaticamente na chamada de saída ao `ledger-api`; o agente do `ledger-api`
**continua** o mesmo trace. O `ledger-api` ([apps/backend/ledger-api/](../apps/backend/ledger-api/))
não declara nenhuma dependência OpenTelemetry — apenas `quarkus-rest-jackson` e
`quarkus-smallrye-health`.

O **único** código de aplicação envolvido é a chamada de saída em si (inevitável, pois o
requisito é "ser chamado pelo backend atual"): o endpoint `GET /api/test/propagate` do
`banking-api` usa `java.net.http.HttpClient` (também instrumentado pelo agente) para chamar o
`ledger-api`. Não há código manual de criação de span nem de propagação de header.

### Recursos criados (role `apps`, gated por `apps_ledger_enabled`, default `true`)

| Recurso | Template | Observação |
|---|---|---|
| Deployment/Service `ledger-api` | `ledger-deployment.yml.j2`, `ledger-service.yml.j2` | anotado com `inject-java`; `OTEL_SERVICE_NAME=ledger-api` (serviço distinto no Tempo) |
| ImageStream/BuildConfig | `ledger-imagestream.yml.j2`, `ledger-buildconfig.yml.j2` | build a partir de `apps/backend/ledger-api` |
| HTTPRoute + AuthPolicy | `ledger-httproute.yml.j2`, `ledger-authpolicy.yml.j2` | rota pública (allow-all) no gateway RHCL — caminho `target=gateway` |
| Route OpenShift | `ledger-route.yml.j2` | acesso direto ao Service (debug) |
| Listener no Gateway | `connectivity-gateway.yml.j2` | listener `ledger-http` (HTTP/80) |
| Env no `banking-api` | `backend-v1-deployment.yml.j2` | `LEDGER_DIRECT_URL` e `LEDGER_GATEWAY_URL` |

### Como demonstrar

**Via PoC Console (recomendado):** abra a app `mobile-bank`, ícone **PoC console** → aba
**Trace Propagation**. Defina `Requests` (chamadas ao gateway) e `Downstream calls`
(chamadas `banking-api → ledger-api` por request, 1..20), clique **Run load**. A aba sempre
chama **via gateway RHCL**, pois é esse o caminho que gera a cadeia completa. O campo **API key**
já vem preenchido com a chave gold `alice-gold-secret` (editável e persistido; **limpe o campo
para reproduzir o 401** do Authorino). O painel mostra o **Trace ID** gerado e um botão **Open in
trace UI** — o campo **Trace UI URL** é **auto-preenchido com o endereço do Tempo do cluster atual**
(derivado do host da página; editável; template `{traceId}`).

**Via curl:** a chamada entra pela rota `banking-api-connectivity` (gateway), protegida por API
key → envie o header `api-key`. O parâmetro `target` controla apenas o hop interno
`banking-api → ledger-api`:

```bash
# target=gateway (usado pela aba): banking-api → gateway RHCL → ledger-api
curl -sk -H "api-key: alice-gold-secret" \
  "https://banking-api.<dominio>/api/test/propagate?target=gateway&calls=2" | jq

# target=direct (variação): banking-api → ledger-api via DNS de Service
curl -sk -H "api-key: alice-gold-secret" \
  "https://banking-api.<dominio>/api/test/propagate?target=direct&calls=2" | jq
```

A resposta inclui `traceId`, o `target` usado e, por chamada downstream, o `entryId`,
`downstreamTraceId` e `downstreamInstance` retornados pelo `ledger-api`.

**Verificar o trace encadeado:** console OpenShift → **Observe → Traces** → instância
`tempo-rhcl` (tenant `dev`) → localize pelo Trace ID → confirme os spans
`rhcl-gateway → banking-api → ledger-api` sob o mesmo Trace ID. Com `target=gateway`, aparece um
span adicional do Envoy (e das políticas Authorino/Limitador, se aplicadas) no hop interno.

## Notas

- O MinIO é usado apenas para **lab/POC**. Em produção, usar ODF (OpenShift Data Foundation) ou outro object storage S3-compatível.
- O `random_sampling: 100` no EnvoyFilter garante traces para todas as chamadas. Em produção, reduzir para 1-10%.
- O Istio CR (`openshift-gateway`) **não é modificado** por esta demo — é infraestrutura pré-existente gerenciada pelo controller da GatewayClass.
- A aba do console usa sempre `target=gateway` (cadeia completa, com span do Envoy no hop interno). O `target=direct` (`banking-api → ledger-api` via DNS de Service) continua disponível por curl como alternativa, caso o hostname do `ledger-api` não resolva dentro do cluster. O caminho via gateway usa o listener HTTP (porta 80), sem TLS — evitando problemas de certificado em CNAMEs personalizados.
- A chamada do console/curl ao `/api/test/propagate` entra pela rota `banking-api-connectivity`, protegida pela AuthPolicy de API key (header `api-key`); por isso a aba envia a chave gold `alice-gold-secret`. Sem a chave o gateway responde **401**.
