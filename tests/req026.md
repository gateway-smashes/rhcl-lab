# Item 26 — Streaming de arquivos (controles do RHCL)

> **Objetivo demo:** mostrar que o RHCL controla o **fluxo de bytes** de uploads
> — tamanho máximo (32 MiB) e duração máxima (60 s) — no plano de dados do
> gateway, **em modo streaming** (não buferizando o request inteiro em
> memória pra validar), sem tocar no backend. Um upload de 50 MiB é
> rejeitado pelo gateway com `HTTP 413` **enquanto os bytes ainda estão
> chegando** — a rejeição dispara no chunk que ultrapassa o cap.

## Requisito

| Item   | Requisito                                                                                            |
| ------ | ---------------------------------------------------------------------------------------------------- |
| **26** | Streaming de arquivos com tamanho máximo (e médio) controlado pela gateway RHCL — fluxo de bytes.    |

---

## TL;DR — O que essa stack entrega

Dois controles combinados no gateway (Envoy) via RHCL, **ambos operando
em streaming** — o gateway processa bytes chunk-a-chunk conforme chegam,
sem segurar o request inteiro em memória pra validar tamanho:

| Controle | Valor default | Efeito |
|----------|---------------|--------|
| **Cap de tamanho (streaming)** | 32 MiB | Upload > 32 MiB → `HTTP 413` + `x-rhcl-streaming-cap: 33554432` + `x-rhcl-observed-bytes: <total>`. Rejeição dispara no chunk que estoura o cap, **sem buferizar** o resto — bytes remanescentes nem chegam a ser lidos do cliente. |
| **Timeout do upload** | 60 s | Upload que demorar mais que 60 s (upload lento / conexão fraca) → `HTTP 408` ou `504`. |

**O backing service (banking-api) é tratado como caixa-preta** — nenhum
parâmetro do Quarkus é alterado. `quarkus.http.limits.max-body-size`
continua em `1G` (default), mas o gateway rejeita bem antes.

---

## Por que essa abordagem (e não outra)

Poderia-se limitar body no backend (Quarkus `max-body-size`), no NGINX Route
antes do gateway, ou aceitar tudo e cobrar depois. Escolhemos **EnvoyFilter
no gateway RHCL** por 3 razões:

1. **Proteção de recursos do backend.** Um upload de 500 MiB rejeitado
   pelo gateway não consome memória, CPU nem storage no pod da aplicação.
   Se o backend faz a rejeição, o request já foi buferizado por baixo (JVM
   heap, tmpfs).
2. **Política única no perímetro.** O time de plataforma controla o cap;
   times de aplicação nem precisam saber que existe. Se amanhã mudar de
   32 pra 64 MiB, é 1 patch no gateway — nenhum redeploy de aplicação.
3. **Assinatura RHCL no 413.** A resposta traz `x-rhcl-streaming-cap:
   33554432` + `x-rhcl-observed-bytes: <total>`, provando pro auditor
   que o corte foi na gateway RHCL (não no backend) **e** informando
   quantos bytes o Lua contou até abortar — evidência de que a
   validação foi progressiva, não em burst.

**Trade-off assumido:** a Lua VM roda dentro do processo do Envoy — em
cada request do path alvo há overhead de ~microssegundos de execução
do script. Em prod com upload pesado a métrica importante é `envoy_http_lua_active_scripts`
+ CPU do pod do gateway, não memória (o Lua streaming segura só 1 chunk
por vez, não o request inteiro como o antigo buffer filter).

## Arquitetura

```
                                       ┌─── EnvoyFilter Lua (streaming) ─────────┐
                                       │  envoy.filters.http.lua                 │
Cliente ──HTTPS─► Gateway RHCL ───►   │   for chunk in bodyChunks() do          │──► banking-api
(upload N MiB)    (rhcl-apps-gateway) │     total = total + chunk:length()      │    /api/files/upload
                                       │     if total > 32 MiB then respond(413) │    InputStream → SHA-256
                                       │     end                                 │    (64 KiB chunks, streaming)
                                       │   end                                   │
                                       │   Só ativa em POST /api/files/upload    │
                                       └─────────────────────────────────────────┘

                                       ┌─── HTTPRoute per-rule timeout ──────────┐
                                       │  match: /api/files/upload POST          │
                                       │  timeouts.request: 60 s                 │
                                       └─────────────────────────────────────────┘

Fluxo de rejeição por tamanho (upload de 50 MiB):
  cliente → envia chunks (16-64 KiB cada) → Lua conta em cada iteração
    → total ultrapassa 32 MiB no chunk N → respond(413) IMEDIATO
    → cliente vê 413 + x-rhcl-streaming-cap: 33554432
    → chunks N+1... nem são solicitados do cliente
    → banking-api nunca recebe o request

Fluxo bem-sucedido (upload de 25 MiB):
  cliente → chunks → Lua conta, cada chunk passa pro upstream conforme chega
    → banking-api recebe stream chunk-a-chunk → SHA-256 online
    → memória: 1 chunk em cada perna (gateway ~64 KiB, backend 64 KiB)

Fluxo de rejeição por tempo (upload de 5 MiB a 100 KiB/s ≈ 52 s):
  cliente → envia bytes lentos → timer da HTTPRoute conta 60 s
    → gateway aborta a conexão → 408/504
    → banking-api pode ter recebido parte, mas não completa
```

## Os 3 pilares (o que criamos e por quê)

> **Nota histórica:** versões anteriores desta req usavam 4 pilares — o
> antigo Pilar 3 era um `BufferPerRoute { disabled: true }` na rule do
> WebSocket, necessário porque o buffer filter engolia handshakes de WS.
> Com a migração pra Lua streaming (que só ativa em `POST /api/files/upload`),
> esse bypass ficou obsoleto — WebSocket passa pelo filtro sem entrar no
> loop de contagem.

### Pilar 1 — EnvoyFilter Lua streaming (o cap de tamanho SEM buferizar)

**Manifest:** [`manifests/01-envoyfilter-streaming-cap.yaml`](req026/manifests/01-envoyfilter-streaming-cap.yaml)

**O que faz:** injeta o filtro `envoy.filters.http.lua` antes do router,
com um script Lua que:

```lua
for chunk in handle:bodyChunks() do
  total = total + chunk:length()
  if total > MAX_BYTES then
    handle:respond({[":status"] = "413", ...}, "Payload Too Large")
    return
  end
end
```

`bodyChunks()` é a **API streaming** do Envoy Lua — o iterador yielda
um chunk por vez conforme os bytes chegam da conexão downstream. Em
qualquer momento a memória do gateway segura só **1 chunk** (16-64 KiB,
o socket buffer do Envoy), **não o request inteiro**.

**Por que não usar `envoy.filters.http.buffer`** (approach da versão
anterior): o buffer filter segura TODOS os bytes do request em memória
até validar o cap. Isso é "reject-by-size buffered", **não streaming** —
não atende ao requisito do cliente de "fluxo de bytes em chunks, sem
colocar em memória pra validar tamanho".

**Escopo:** o Lua só ativa em `POST /api/files/upload`. Outros paths
retornam imediatamente sem entrar no loop de contagem — zero overhead
pra WebSocket upgrades, JSON POSTs, GETs, ou streams de resposta SSE
do AI.

**Por que na gateway (namespace `openshift-ingress`), não na app:** o
gateway RHCL vive em `openshift-ingress`, e a EnvoyFilter precisa estar
no mesmo namespace do Envoy que ela quer patchear. O `workloadSelector.labels`
seleciona só o gateway do PoC (`gateway.networking.k8s.io/gateway-name:
rhcl-apps-gateway`) — não afeta outros gateways do cluster.

#### Framing HTTP malformado é rejeitado antes do Lua

O Lua só entra em ação em requests HTTP válidos. O parser de framing do
Envoy roda antes de qualquer filter: se o cliente mandar `Content-Length`
**e** `Transfer-Encoding: chunked` no mesmo request, Envoy fecha com
**400 Bad Request** direto do HTTP Connection Manager — o Lua nem é
invocado.

RFC 9112 §6 é explícita: "A sender MUST NOT send a Content-Length header
field in any message that contains a Transfer-Encoding header field". A
combinação é vetor clássico de HTTP Request Smuggling (um proxy
intermediário interpreta o framing por Content-Length, o backend por
chunked → atacante esconde uma segunda request dentro da primeira).
Envoy trata como framing inválido por default.

Confirmar em ~30s:

```bash
HOST=banking-api-connectivity.<zona>
curl -sk -X POST "https://$HOST/api/files/upload" \
  -H "api-key: <chave>" \
  -H "Content-Length: 100" \
  -H "Transfer-Encoding: chunked" \
  -H "Content-Type: application/octet-stream" \
  --data-binary "test" \
  -o /dev/null -w "HTTP %{http_code}\n"
# esperado: HTTP 400
```

Comportamento default do Envoy, alinhado com a RFC — nada a configurar.

#### Simetria opcional — cap na direção da resposta (download)

O req é **assimétrico** por design: limita só **upload** (request body).
A resposta do backend passa livre até o `Content-Length` que o Quarkus
mandar. Se o cenário exigir cap simétrico (upload = download), o mesmo
EnvoyFilter aceita um callback separado pra response:

```lua
function envoy_on_response(handle)
  local status = handle:headers():get(":status") or ""
  if status:sub(1,1) ~= "2" then return end   -- só limita 2xx

  local MAX_RESPONSE_BYTES = 33554432
  local total = 0
  for chunk in handle:bodyChunks() do
    total = total + chunk:length()
    if total > MAX_RESPONSE_BYTES then
      handle:headers():replace("x-rhcl-response-truncated", tostring(total))
      handle:respond({[":status"] = "502"}, "Response exceeded streaming cap")
      return
    end
  end
end
```

**Trade-off crítico** — no upload dá pra cortar limpo (413 antes do
backend receber qualquer byte). Na resposta o backend **já commitou
headers 200**, então cortar no meio vira 502 pro cliente + bytes
parciais entregues. Faz sentido apenas quando:

- Backend pode devolver payload absurdo por bug ou input untrusted, e
- O cliente sabe interpretar `x-rhcl-response-truncated` (ou aceita
  502 como sinal genérico de "resposta cortada").

Streaming legítimo (SSE, log tail, download de arquivo grande) **não**
deve ter cap de resposta — capar quebra o cenário.

### Pilar 2 — HTTPRoute `timeouts.request` (o cap de tempo)

**Template Ansible:** [`automation/roles/apps/templates/connectivity-httproute.yml.j2`](../automation/roles/apps/templates/connectivity-httproute.yml.j2) (rule 7)
**Patch renderizado:** [`manifests/02-httproute-timeout-patch.yaml`](req026/manifests/02-httproute-timeout-patch.yaml)

O que faz: adiciona uma rule na HTTPRoute do banking-api que matcha
`POST /api/files/upload` e seta `timeouts.request: 60s`. Se o upload
inteiro (cliente → gateway → backend → resposta) não terminar em 60 s,
o gateway aborta.

Por que é uma rule separada (não uma configuração global): o
`timeouts.request` do Gateway API (GEP-1742) é per-rule. Setar 60 s
globalmente quebraria chamadas legítimas que demoram mais (long polling,
AI streaming responses). Fica só no path de upload.

**Ordem da rule importa** (GEP-1742: longer prefix wins) — a rule vai no
index 7, ANTES do catch-all `/api` (index 8), pra que `/api/files/upload`
matche primeiro.

**`request` vs `backendRequest`:** o `request` cobre o upload INTEIRO
(cliente → gateway → backend → resposta). Se quiser timeout só do lado
upstream (gateway → backend), usar `backendRequest`. Esta req usa
`request` porque queremos abortar uploads lentos do CLIENTE também.

#### Variações — flows que precisam de timeout diferente (ou nenhum)

Situação default: `timeouts.request: 60s` mata a request inteira em
60 segundos. Pra flows longos (SSE, WebSocket, upload muito grande via
link lento) três caminhos:

**a) Remover timeout SÓ da rule de streaming (recomendado)**

Patch cirúrgico só na rule de upload — o resto do banking-api continua
com timeout default:

```bash
IDX=$(oc -n rhcl-apps get httproutes.gateway.networking.k8s.io banking-api-connectivity \
  -o json | jq '.spec.rules | to_entries | map(select(.value.matches[0].path.value | contains("/api/files"))) | .[0].key')

oc -n rhcl-apps patch httproutes.gateway.networking.k8s.io banking-api-connectivity \
  --type=json -p="[{\"op\":\"remove\",\"path\":\"/spec/rules/$IDX/timeouts\"}]"
```

Após isso, o `stream_idle_timeout` do HCM (default 300s) ainda mata
conexões idle — safety net contra streams zumbis mesmo sem
`timeouts.request`.

**b) Zerar `stream_idle_timeout` (nenhum timeout, nem idle)**

Requer EnvoyFilter porque não há equivalente no Gateway API:

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: files-upload-no-timeout
  namespace: openshift-ingress
spec:
  workloadSelector:
    labels:
      gateway.networking.k8s.io/gateway-name: rhcl-apps-gateway
  configPatches:
    - applyTo: HTTP_ROUTE
      match:
        context: GATEWAY
        routeConfiguration:
          vhost:
            route:
              # Nome determinístico do Istio: <ns>.<httproute>.<ruleIndex>
              name: "rhcl-apps.banking-api-connectivity.7"
      patch:
        operation: MERGE
        value:
          route:
            idle_timeout: 0s
            timeout: 0s
            max_stream_duration:
              max_stream_duration: 0s
```

⚠️ Perde defesa contra slowloris e leaks de conexão zumbi. Só faz
sentido em rotas WebSocket / SSE de longa duração legítima.

**c) Manter timeout mas grande (mais seguro operacionalmente)**

Ao invés de zero, colocar 1 hora:

```bash
oc -n rhcl-apps patch httproutes.gateway.networking.k8s.io banking-api-connectivity \
  --type=json -p='[{"op":"replace","path":"/spec/rules/'$IDX'/timeouts/request","value":"1h"}]'
```

Streams zumbis eventualmente morrem sozinhas, sem perder a proteção.

**Qual usar:**

| Cenário | Caminho |
|---|---|
| Upload comum de arquivo (até alguns MB) | Manter 60s atual |
| Upload de arquivo grande (30-40 MiB) via link lento | **a** — remover só da rule de upload |
| WebSocket / SSE / long polling | **a** + revisar `stream_idle_timeout` do HCM |
| Webhook infinito / streaming de log real-time | **c** com 1–6h |
| "Sem timeout" pedido sem contexto | **c** com 1h — cobre 99% do "sem timeout" na prática |

### Pilar 3 — Backend intocado (por design)

**Arquivo:** [`apps/backend/banking-api/src/main/java/io/gatewaysmashes/rhcl/api/FilesResource.java`](../apps/backend/banking-api/src/main/java/io/gatewaysmashes/rhcl/api/FilesResource.java)

Endpoints existem no banking-api mas **sem env vars especiais, sem
configuração de max-body-size ajustada, sem lógica de rejeição**. O
`FilesResource.upload()` faz stream do `InputStream` em chunks de 64 KiB,
calcula SHA-256 online, devolve JSON `{ sha256, bytesReceived, durationMs }`.
`quarkus.http.limits.max-body-size` fica no default `1G`.

**Prova da separação:** se você desabilitar a EnvoyFilter
(`APPS_STREAMING_ENABLED=false`), uploads de 500 MiB passam a funcionar
via o cap padrão do Quarkus. Isso confirma que a proteção era 100% do RHCL.

## Catálogo completo de knobs de streaming no RHCL

Só usamos 2 dos 6 knobs — o resto fica documentado pro caso de precisar:

| Knob | Superfície RHCL | Esta req seta |
|------|-----------------|---------------|
| **Streaming size cap** | EnvoyFilter `envoy.filters.http.lua` + `bodyChunks()` counter | **32 MiB** |
| **Per-route request timeout** | HTTPRoute `spec.rules[].timeouts.request` (GEP-1742) | **60 s** |
| Per-route backend timeout | HTTPRoute `spec.rules[].timeouts.backendRequest` | _(default Envoy)_ |
| Stream idle timeout | EnvoyFilter HCM `stream_idle_timeout` | _(default 300s)_ |
| Max request headers | EnvoyFilter HCM `max_request_headers_kb` | _(default 60 KiB)_ |
| Auth-side body buffering | AuthPolicy `spec.rules.authentication[].with_request_body` | **off** |
| Legacy: buffered cap | EnvoyFilter `envoy.filters.http.buffer.max_request_bytes` | _(descartado — buferizava)_ |

Os 4 defaults deliberadamente ficam intocados porque mexer neles muda
comportamento de outros endpoints (WebSocket long-lived, SSE de AI,
MCP). A combinação **body cap + timeout** já cobre os dois eixos do
requisito (tamanho máximo + duração máxima).

## Validação

Script pronto: `./scripts/validate.sh` — roda os 5 casos abaixo, exit 0
se todos passarem.

### Casos exercitados

| Caso | Resultado esperado |
|------|---------------------|
| Upload **1 MiB** | `HTTP 200` + JSON `{sha256, bytesReceived:1048576, durationMs}` |
| Upload **25 MiB** | `HTTP 200` + JSON `{sha256, bytesReceived:26214400, ...}` |
| Upload **50 MiB** | `HTTP 413` + `x-rhcl-streaming-cap: 33554432` + `x-rhcl-observed-bytes: <total>` (Lua abortou no chunk que estourou) |
| Upload **5 MiB a 100 KiB/s** (~52 s no fio) | `HTTP 408` ou `504` quando passar de 60 s |
| Download **10 MiB, chunk 256 KiB** | `HTTP 200` + `Content-Length: 10485760` |

### Prova de que o cap é do RHCL, não do backend

```bash
oc -n rhcl-apps get deploy banking-api-v1 \
  -o jsonpath='{.spec.template.spec.containers[0].env}' \
  | grep -c HTTP_MAX_BODY_SIZE
```

Esperado: `0`. Nenhuma env var de body size foi injetada no backend — o
`quarkus.http.limits.max-body-size` continua no default `1G`. Se você
temporariamente desabilitar a EnvoyFilter, uploads de 500 MiB passam a
funcionar via cap do Quarkus. Isso comprova que a proteção era 100% RHCL.

### Prova visual no 413 — header assinado pelo Envoy

```bash
dd if=/dev/urandom bs=1M count=50 status=none | curl -sk \
  -X POST -H "api-key: $API_KEY" -H "Content-Type: application/octet-stream" \
  --data-binary @- -D - -o /dev/null -w "HTTP %{http_code}\n" \
  "https://$GATEWAY_HOST/api/files/upload"
```

Esperado: `HTTP 413` + os headers `x-rhcl-streaming-cap: 33554432` e
`x-rhcl-observed-bytes: <total_no_momento_do_corte>` — assinatura Lua
do filtro RHCL, não do Quarkus. O `observed-bytes` sendo menor que 50 MiB
(e só um pouco acima de 32 MiB) é a **prova** de que a rejeição foi
streaming, não buferizada — se o Envoy tivesse segurado tudo,
observed-bytes seria = Content-Length do request.

### Demo pro cliente ver no browser

Abrir [`req026/index.html`](req026/index.html) local (ou pelo catálogo de
testes hospedado). Ajustar `GATEWAY_HOST` e `API_KEY` no topo do arquivo.
Botões:

- **1 MiB** → barra completa, painel mostra `sha256` + `durationMs`
- **25 MiB** → mesmo, com barra mais lenta
- **50 MiB** → barra avança e estanca; painel mostra `HTTP 413 —
  x-rhcl-streaming-cap: 33554432 (observed ~34 MB)`

A barra continua subindo até estancar mesmo no caso 413 porque o
browser continua tentando enviar bytes mesmo depois da rejeição — mas
o Envoy interrompeu o READ downstream no momento do respond(), então
os bytes que o browser envia depois são descartados sem serem
processados. A memória do gateway não cresce nesse período.

## Limitações conhecidas

- **Custo de CPU do Lua VM.** Cada request em `POST /api/files/upload`
  entra no loop `for chunk in bodyChunks() do`. Overhead é da ordem de
  microssegundos por chunk. Em prod com upload pesado, métrica pra
  monitorar é `envoy_http_lua_active_scripts` + CPU do pod do gateway
  (não memória — o Lua streaming segura só 1 chunk por vez, ~64 KiB).

- **`bodyChunks()` bufferiza o CHUNK, não o request inteiro.** Chunks
  são materialisados na Lua VM um-a-um pra contagem. Isso é streaming
  no sentido "não segura o request inteiro em memória", mas ainda tem
  o chunk atual em memória durante `chunk:length()`. Chunk típico do
  Envoy é 16-64 KiB — muito menor que os 32 MiB do buffer filter que
  usávamos antes.

- **Authorino antes do Lua.** Por design a AuthPolicy roda antes do
  filtro Lua — upload sem credencial recebe 401 sem entrar no loop de
  contagem (ótimo). MAS se ativarem `with_request_body: true` em alguma
  AuthConfig que toque `/api/files/upload`, o Authorino passa a
  buferizar primeiro e a ordem de rejeição muda (pode virar 500 em vez
  de 413 com payload grande). **Não ligue `with_request_body` nesse
  path.**

- **Rejeição só depois do 1º chunk que estoura.** Se o cliente mandar
  o `Content-Length: 50MB` header antes do body, o Lua não usa esse
  hint — só descobre o tamanho real chunk-a-chunk. Isso é intencional
  (`Content-Length` pode mentir), mas significa que o 413 dispara
  ~chunk depois de 32 MiB, não no header. `x-rhcl-observed-bytes` no
  response mostra exatamente quantos bytes o Lua viu antes de abortar.

- **Timeout `request` vs `backendRequest`.** `timeouts.request` cobre
  cliente→gateway→backend→resposta. Se você quer timeout só no lado
  upstream, usar `backendRequest`. Esta req usa `request` porque o
  objetivo é abortar uploads lentos do cliente.

- **Cap ativa somente em `POST /api/files/upload`.** Outros endpoints
  que quiserem cap próprio precisam de outra EnvoyFilter (ou expandir o
  script Lua com mais matches). Ver o `if path:sub(1, #UPLOAD_PATH) ~=
  UPLOAD_PATH then return end` no manifest — é o único ponto onde o
  path é escrito.
