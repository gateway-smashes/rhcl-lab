# Item 7 — Balanceamento de carga com suporte à sessão

## Requisito demonstrado

* **Item 7: Balanceamento de carga com suporte à sessão** — afinidade de
  sessão entre réplicas do backend `banking-api-v1`, configurada por
  cookie HTTP no nível do gateway (Istio `DestinationRule`).

---

## Visão geral

Este item demonstra **sticky session** entre réplicas do backend
`banking-api-v1`, usando o caminho do **Gateway API** (`rhcl-apps-gateway`
+ `HTTPRoute banking-api-connectivity`, que já existem na PoC).

A afinidade é aplicada pelo **Istio**, através de uma `DestinationRule`
com `consistentHash.httpCookie` apontando para o **Service** do backend
(`banking-api-v1.rhcl-apps.svc.cluster.local`).

A validação usa o endpoint público `/api/echo`, que devolve o nome do
pod no campo `instance` do JSON de resposta.

| Camada | Função |
|---|---|
| `Gateway` + `HTTPRoute` | Expõe a banking-api via `rhcl-apps-gateway` |
| `DestinationRule` | Aplica afinidade por cookie entre as réplicas do Service |
| `banking-api-v1` (com 2+ réplicas) | Backend que reporta o pod no `/api/echo` |

> **Por que NÃO usar o caminho `Route OCP` (`*.apps.<cluster>`)** — a Route
> nativa do OpenShift Router vai direto do HAProxy pro Service do K8s e
> **bypassa o Istio**. A `DestinationRule` é silenciosamente ignorada
> nesse caminho, e qualquer "stickiness" observada vem do cookie default
> do **HAProxy**, não do `CUSTOM_COOKIE_SESSION` do Envoy. Por isso a
> validação **precisa** ser feita pela hostname do `rhcl-apps-gateway`
> (Gateway API), nunca pela Route OCP.

## Pré-requisitos

```bash
# Login no cluster
oc whoami

# Backend instalado, com pelo menos 2 réplicas
oc get deploy banking-api-v1 -n rhcl-apps

# Gateway e HTTPRoute da banking-api funcionando
oc get gateway rhcl-apps-gateway -n openshift-ingress
oc get httproute banking-api-connectivity -n rhcl-apps

# DestinationRule de base já existente (a sticky session é um patch nela)
oc get destinationrule banking-api-v1-http1 -n rhcl-apps
```

O endpoint `/api/echo` deve ser público (sem APIKey) e retornar JSON com
o campo `instance` = nome do pod:

```bash
HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')
curl -sk "https://$HOST/api/echo" 2>/dev/null | python3 -c '
import json, sys
try:
    print("instance =", json.load(sys.stdin).get("instance"))
except Exception:
    print("instance = (no JSON — backend deu erro, retry)")
'
# instance = banking-api-v1-5575b4dd47-h29gc
```

## Setup (uma vez por cluster)

### 1. Escalar o backend para 2+ réplicas

Sticky session com **1 réplica** é falso-positivo: todo request vai pro
mesmo pod independentemente da DR.

```bash
oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=2
oc rollout status deploy/banking-api-v1 -n rhcl-apps
```

### 2. Fazer o backend reportar o nome do pod no `/api/echo`

O Quarkus do banking-api lê `APP_INSTANCE_NAME` e devolve esse valor no
campo `instance` do `/api/echo`. Por default vem fixado como
`banking-api-v1`, o que torna impossível distinguir as réplicas. Trocar
o valor por `valueFrom.fieldRef: metadata.name` faz cada pod reportar
seu próprio nome.

```bash
# Remove o valor fixo
oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME-

# Adiciona como fieldRef (nome do pod)
oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/template/spec/containers/0/env/0",
    "value": {
      "name": "APP_INSTANCE_NAME",
      "valueFrom": {"fieldRef": {"fieldPath": "metadata.name"}}
    }
  }
]'

oc rollout status deploy/banking-api-v1 -n rhcl-apps
```

> **Efeito colateral**: o label `instance` das métricas Prometheus do
> AI-mock ganha cardinalidade (1 label por pod em vez de 1 fixo). Pra
> nesta demo isso é OK; em produção, exporia uma segunda env
> `APP_POD_NAME` via `fieldRef` e ajustaria o backend pra usá-la no
> `/api/echo`.

### 3. Patchar a `DestinationRule` existente com sticky cookie

A `DestinationRule banking-api-v1-http1` já existe (faz parte da install
do banking-api) e cuida do connection pool. Vamos só **adicionar** o
sticky cookie no `loadBalancer`.

```bash
oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {
    "op": "add",
    "path": "/spec/trafficPolicy/loadBalancer",
    "value": {
      "consistentHash": {
        "httpCookie": {
          "name": "CUSTOM_COOKIE_SESSION",
          "path": "/",
          "ttl": "1800s"
        }
      }
    }
  }
]'
```

Confirmar:

```bash
oc get destinationrule banking-api-v1-http1 -n rhcl-apps -o jsonpath='{.spec.trafficPolicy.loadBalancer}'; echo
# {"consistentHash":{"httpCookie":{"name":"CUSTOM_COOKIE_SESSION","path":"/","ttl":"1800s"}}}
```

| Campo | Valor |
|---|---|
| `host` (da DR base) | `banking-api-v1.rhcl-apps.svc.cluster.local` |
| `httpCookie.name` | Nome do cookie usado pra afinidade |
| `httpCookie.path` | Escopo do cookie |
| `httpCookie.ttl` | Tempo de vida do cookie |

## Validação via `curl`

### 1. Round-robin **sem** cookie (baseline)

Antes de validar o sticky, mostrar que **sem cookie**, o tráfego vai pra
**ambos os pods** — confirma que a `DestinationRule` está ativa mas não
fixou nada.

```bash
HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')

for i in $(seq 1 10); do
  curl -sk "https://$HOST/api/echo" 2>/dev/null \
    | python3 -c '
import json, sys
try:
    print(json.load(sys.stdin).get("instance", ""))
except Exception:
    pass
' 2>/dev/null
done | grep -v '^$' | sort | uniq -c
# Saída esperada (números variam, mas DEVEM aparecer 2 pods distintos):
#   4 banking-api-v1-5575b4dd47-h29gc
#   6 banking-api-v1-5575b4dd47-wkfmj
```

### 2. Set-Cookie do Envoy na 1ª requisição

```bash
curl -sk -i "https://$HOST/api/echo" | grep -i 'set-cookie'
# set-cookie: CUSTOM_COOKIE_SESSION="37c5519780cbe86f"; Max-Age=1800; Path=/; HttpOnly
```

> O `Max-Age=1800` bate com o `ttl: 1800s` da DR. **Se a Set-Cookie vier
> com outro nome** (ex.: um hash MD5 hexadecimal sem o
> `CUSTOM_COOKIE_SESSION`), o tráfego está passando pela Route OCP
> (HAProxy), não pelo Gateway. Verificar o hostname.

### 3. Sticky com 5 cookies distintos

Cada cookie deve grudar em **um único pod**, e cookies distintos podem
cair em pods diferentes (distribuição é hash-based).

```bash
for cookieval in aaa111 bbb222 ccc333 ddd444 eee555; do
  pods=$(for i in $(seq 1 8); do
    # 2>/dev/null engole erros do curl; python try/except engole 503/JSON vazio
    # — banking-api às vezes 503 sob load, não queremos que UMA req ruim
    # derrube o script inteiro.
    curl -sk -H "Cookie: CUSTOM_COOKIE_SESSION=$cookieval" \
         "https://$HOST/api/echo" 2>/dev/null \
      | python3 -c '
import json, sys
try:
    print(json.load(sys.stdin).get("instance", ""))
except Exception:
    pass
' 2>/dev/null
  done | grep -v '^$' | sort -u | tr '\n' ',' | sed 's/,$//')
  echo "cookie=$cookieval → pods: $pods"
done
# Saída esperada (cada linha mostra UM ÚNICO pod no campo "pods"):
# cookie=aaa111 → pods: banking-api-v1-5575b4dd47-wkfmj
# cookie=bbb222 → pods: banking-api-v1-5575b4dd47-h29gc
# cookie=ccc333 → pods: banking-api-v1-5575b4dd47-wkfmj
# cookie=ddd444 → pods: banking-api-v1-5575b4dd47-wkfmj
# cookie=eee555 → pods: banking-api-v1-5575b4dd47-wkfmj

# Se algum cookie retornar "pods:" vazio, foi 100% falha do backend —
# todas as 8 reqs daquele cookie deram 503/timeout. Confirme com:
#   curl -sk -w '%{http_code}\n' -o /dev/null "https://$HOST/api/echo"
# e olhe os logs: oc logs -n rhcl-apps -l app=banking-api-v1 --tail=50
```

### 4. Nova sessão (cookie diferente) — pode cair em pod diferente

O importante não é qual pod a nova sessão pega; é que **depois de
estabelecida, ela permaneça estável**. O passo 3 já cobre isso (cada
cookie é uma "nova sessão" estabilizada).

## Troubleshooting

| Sintoma | Diagnóstico |
|---|---|
| Set-Cookie vem com nome `<md5hash>` em vez de `CUSTOM_COOKIE_SESSION` | Tráfego entrou pela Route OCP, não pelo Gateway API. Verificar que o hostname usado bate com o `spec.hostnames` da `HTTPRoute banking-api-connectivity`. |
| Round-robin acontece mesmo com cookie | A DR não foi aplicada ou o `host` da DR não bate com o Service. Verificar `oc get destinationrule banking-api-v1-http1 -n rhcl-apps -o yaml`. |
| 401 / 403 em `/api/echo` | Algum AuthPolicy gateway-level deny-all está pegando. A rota `/api/echo` é configurada como `anonymous` no `banking-api-connectivity-apikey` AuthPolicy — conferir que essa policy está `Enforced=True`. |
| `instance` no JSON sempre o mesmo, mas tem 2 réplicas | `APP_INSTANCE_NAME` ainda está fixo. Re-rodar o passo 2 do setup (`fieldRef metadata.name`). |
| Só 1 réplica responde | Healthcheck de uma réplica está falhando. `oc describe pod` na que não responde. |
| Sticky degrada após `oc rollout restart` | Esperado — pods novos têm nomes novos, hash do cookie mapeia para novo bucket. Cookies de sessões abertas antes do restart vão "saltar" para um pod aleatório (ainda estável dali em diante). |

## Rollback

```bash
# Voltar DR para o estado original (sem sticky)
oc patch destinationrule banking-api-v1-http1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/trafficPolicy/loadBalancer"}
]'

# Voltar APP_INSTANCE_NAME para valor fixo
oc patch deploy/banking-api-v1 -n rhcl-apps --type=json -p '[
  {"op": "remove", "path": "/spec/template/spec/containers/0/env/0"}
]'
oc set env deploy/banking-api-v1 -n rhcl-apps APP_INSTANCE_NAME=banking-api-v1
oc rollout status deploy/banking-api-v1 -n rhcl-apps

# (Opcional) voltar a 1 réplica
oc scale deploy/banking-api-v1 -n rhcl-apps --replicas=1
```
