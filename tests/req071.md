# Item 71 — OIDC / JWT Auth (enforcement no Gateway)

## Requisito demonstrado

| Item | Requisito |
|------|-----------|
| **71** | Suporte a **OIDC / JWT** — validação de tokens emitidos por um Identity Provider (assinatura, emissor, audiência, expiração) e **autorização** baseada em claims, **no nível do Gateway/API**, sem que a aplicação precise validar nada. |

A demonstração sobe um **Red Hat build of Keycloak (RHBK 26.4)** real via operator, cria um realm/cliente/usuários, e configura o **Gateway (Authorino, via `AuthPolicy`)** para validar o JWT e autorizar por **realm role / audience / scope**. O backend `banking-api` **não tem nenhuma dependência de OIDC/JWT** — ele apenas ecoa as claims que o gateway já verificou e encaminhou como headers `x-jwt-*`.

O token é **real**, emitido pelo Keycloak, e a **validação + autorização acontecem no gateway** (Authorino). A app não participa da decisão.

> O entregável do item 71 é o **JWT bearer** (padrão correto pra API). Também avaliamos o `OIDCPolicy` (login OIDC no gateway, para apps de browser) — ver **Cenário E**: funciona até o code exchange, mas a versão Tech Preview é incompatível com o listener wildcard deste gateway.

## Visão geral da arquitetura

```
                       ┌─────────────────────────────┐
   1) login / token    │  RHBK / Keycloak (realm rhcl)│
   cliente ───────────►│  keycloak.poc.rhcl.com.br    │  emite JWT (RS256)
        ▲              │  Route passthrough + LE cert │  iss/aud/exp/roles/scope
        │  Bearer JWT  └──────────────┬──────────────┘
        │                             │ JWKS (.well-known)
        │              ┌──────────────▼──────────────┐
        └─ 2) request ─►   Gateway / Envoy (Kuadrant) │
                       │   AuthPolicy → Authorino     │  valida assinatura, iss,
                       │   jwt.issuerUrl              │  aud, exp; autoriza por
                       │   authorization (role/scope) │  realm_access.roles etc.
                       │   response.headers x-jwt-*   │
                       └──────────────┬──────────────┘
                                      │ encaminha claims verificadas (x-jwt-*)
                              ┌───────▼────────┐
                              │  banking-api    │  /api/whoami só ECOA o que
                              │  (sem OIDC)     │  o gateway mandou
                              └────────────────┘
```

**Componentes**

- **RHBK (Keycloak)** — `rhbk-operator` (Red Hat Operators, canal `stable-v26.4`). CRs `Keycloak` + `KeycloakRealmImport` (`k8s.keycloak.org/v2alpha1`). Backend PostgreSQL no mesmo namespace `keycloak`. Exposto via **Route passthrough** com cert **Let's Encrypt** (cert-manager) — assim o Authorino confia no issuer por TLS sem CA extra.
- **AuthPolicy** (`kuadrant.io/v1`) — método de autenticação `jwt` com `issuerUrl` apontando pro realm; `authorization.patternMatching` exigindo `banking-customer`; `response.success.headers` encaminhando as claims verificadas pro backend.
- **banking-api** — sem `quarkus-oidc`/`smallrye-jwt`. O endpoint `/api/whoami` apenas reflete os headers `x-jwt-*` injetados pelo gateway.

> **Issuer e TLS**: o `iss` do token é `https://keycloak.poc.rhcl.com.br/realms/rhcl` — exatamente a `issuerUrl` da AuthPolicy. O Authorino busca o JWKS em `${issuerUrl}/.well-known/openid-configuration`. Como o cert é Let's Encrypt, a validação TLS funciona sem ajuste.

| Usuário | Senha | Realm roles | Para que serve |
|---------|-------|-------------|----------------|
| `alice` | `alice123` | `banking-customer` | passa em authN + authZ-por-role (customer) |
| `bob`   | `bob123`   | `banking-customer`, `banking-admin` | passa também em cenários que exigem `banking-admin` |

Cliente: `banking-api` (confidential, secret `banking-api-secret`, **Direct Access Grants** habilitado p/ password grant em demo). Mapper de **audience** injeta `aud=banking-api` no access token.

**Console admin do Keycloak** (realm `master`): **`admin` / `redhat`** — admin definitivo provisionado via `spec.bootstrapAdmin.user.secret` (Secret `keycloak-bootstrap-admin`), no lugar do `temp-admin` + senha aleatória que o operator gera por padrão.

## Cenários (gateway-side)

Todos atuam sobre o `HTTPRoute banking-api-connectivity`, path **`/api/whoami`**. Como só **uma `AuthPolicy` fica Enforced por target**, os cenários são variações da regra de `authorization` (via `oc patch`) sobre a policy instalada.

### Cenário A — authN (token válido)

Sem regra de role: qualquer token genuíno e não-expirado do realm passa.

| Request | Resposta |
|---------|----------|
| Sem `Authorization` | `401` |
| `Authorization: Bearer <lixo>` | `401` |
| Token válido (alice/bob) | `200` + claims `x-jwt-*` no corpo do `/api/whoami` |

### Cenário B — authZ por realm role

`authorization.patternMatching` exige `banking-admin` em `auth.identity.realm_access.roles`.

| Usuário | Roles no token | Resposta |
|---------|----------------|----------|
| `alice` | `[banking-customer]` | `403` |
| `bob`   | `[banking-customer, banking-admin]` | `200` |

> Default **instalado** pela automação: exige `banking-customer` (ambos passam; demonstra que a autorização está ativa). Troque o valor pra `banking-admin` para ver o `403` de alice.

### Cenário C — authZ por audience

Exige `aud == banking-api`. Tokens sem o mapper de audience (ex.: emitidos para outro client) recebem `403`.

### Cenário D — authZ por scope (opcional)

Exige um scope (ex.: `accounts`) presente na claim `scope`. Requer um optional client scope no realm; ver README.

## Cenário E — OIDCPolicy (login no gateway) — AVALIADO, bloqueado por bug upstream (#1504)

Além do JWT bearer (acima), o Kuadrant tem um **`OIDCPolicy`** (`extensions.kuadrant.io/v1alpha1`, **Tech Preview** no RHCL 1.3.3) que implementa o **OIDC Authorization Code Flow no próprio gateway**: navegação sem sessão → `302` pro Keycloak → login → callback → **cookie de sessão**. É o padrão para proteger **apps de browser** (SSO no edge, sem código na app), complementar ao bearer (que é pra **API**, cliente traz o token).

Avaliamos o `OIDCPolicy` protegendo a SPA `mobile-bank`. Resultado:

- ✅ **Funciona até o code exchange**: `GET /` → `302` pro endpoint `authorize` do Keycloak (`client_id`, `redirect_uri=…/auth/callback`, `response_type=code`); após o login, o gateway **trocou o code por um token de sessão real** (ID token de `alice`, `aud=mobile-bank-spa`). O `OIDCPolicy` cria sozinho a HTTPRoute de callback (`/auth/callback`) + as `AuthPolicies`.
- ⚠️ **Pré-requisito**: o provider do CRD **não tem `clientSecretRef`** — o token exchange usa só `client_id` (`grant_type=authorization_code`). Exige um client **público** no Keycloak (o `banking-api` é confidential e não serve). Criamos `mobile-bank-spa` (public, standard flow).
- ❌ **Bloqueador (bug)**: o `OIDCPolicy` deriva o **domínio do cookie** e o redirect pós-login do **hostname do listener do gateway** (em vez do hostname concreto da HTTPRoute). Como nosso gateway usa um **listener wildcard** (`*.poc.rhcl.com.br`), ele emite:
  - `set-cookie: jwt=…; Domain=*.poc.rhcl.com.br` → **Domain inválido** (`*` literal não é permitido) → browsers/curl **rejeitam** o cookie → a sessão nunca se estabelece (loop de login);
  - `location: http://*.poc.rhcl.com.br` → redirect quebrado.
  - Adicionar um listener de hostname específico e prender a rota nele (`sectionName`) **não resolveu** — o controller continua lendo o listener wildcard.

**Bug, não limitação de design.** Os outputs são malformados independentemente da intenção: `Domain=*.poc.rhcl.com.br` é **inválido por RFC 6265** (o atributo `Domain` é uma string de domínio; `*` literal não é permitido — o correto seria `Domain=poc.rhcl.com.br` ou omitir), e `http://*.poc.rhcl.com.br` tem host inválido + esquema errado. A causa raiz é usar o hostname do **listener** (que o Gateway API permite ser wildcard) em vez do hostname concreto da **HTTPRoute**.

- **Já rastreado upstream**: [`kuadrant-operator#1504`](https://github.com/Kuadrant/kuadrant-operator/issues/1504) — *"[OIDCPolicy] Redirect URI is not built correctly if hostname is not exact"*, label `kind/bug`, aberto. Cobre o redirect URI; o sintoma do **cookie `Domain` inválido** observado aqui é a mesma causa raiz e vale como evidência adicional no issue.
- **Caminho no produto (RHCL)**: como o `OIDCPolicy` é **Tech Preview** (`extensions.kuadrant.io/v1alpha1`), se o cliente precisar dele suportado, abrir caso de suporte / RFE com a Red Hat referenciando o bug upstream #1504.

**Conclusão**: enquanto o bug não é corrigido, o `OIDCPolicy` precisa de um **gateway com listener de hostname específico** (como no tutorial upstream, que usa `bakery.<ip>.nip.io`). Nosso gateway precisa manter o wildcard `*.poc.rhcl.com.br` pro banking-api. Para o item 71, o entregável é o **JWT bearer (AuthPolicy)** — padrão correto pra proteger a API. O `OIDCPolicy` fica registrado como avaliado e recomendado para um cenário futuro de **SSO de browser** num gateway dedicado.

> Como reproduzir o teste (gateway dedicado): crie um `Gateway` com um único listener
> `hostname: <host-específico>` + cert, uma `HTTPRoute` da app nele, um client **público**
> no Keycloak, e a `OIDCPolicy` apontando `issuerURL`/`authorizationEndpoint`/`tokenEndpoint`
> do realm. Docs: kuadrant-operator `doc/extensions/oidcpolicy.md` e
> `doc/user-guides/oidcpolicy/oidc-keycloak.md`.

### E num cenário corporativo?

O bug **exato** (wildcard) provavelmente **não** recorre num ambiente corporativo com
`apps_connectivity_listener_wildcard_enabled=false`: nesse caso o listener usa o
**hostname específico** (`banking-api-connectivity.<zone>`) e o cookie `Domain` sai válido.

**Mas um ambiente corporativo troca um sintoma do #1504 por outro.** A topologia corporativa típica é
`navegador → NGINX corporativo → OpenShift Route (termination: edge) → Gateway ClusterIP :80 (http)`.
Ou seja, **o TLS termina no Route** e o Gateway recebe **HTTP puro**. Como o OIDCPolicy
monta o `redirect_uri`/cookie a partir do que o **Gateway enxerga** (listener HTTP/80) e
não do que o **browser** usa (https no edge), o redirect provavelmente sairia como
`http://banking-api-connectivity.<zone>/auth/callback` (esquema errado / cookie sem
`Secure`), mesmo sem wildcard — e não há garantia de que ele honre o
`X-Forwarded-Proto: https` injetado pelo Route. **Conclusão**: OIDCPolicy num ambiente corporativo
**continua exigindo validação dedicada** (não está resolvido só por não ter wildcard).
Padrão seguro: terminar TLS no próprio Gateway (listener `https` com o hostname externo
exato) + `spec.provider.redirectURI` explícito em `https://…`.

> O **JWT bearer (`AuthPolicy`)** — entregável do item 71 — é **imune** a tudo isso:
> não deriva redirect nem cookie, só valida o Bearer que o cliente traz. Funciona igual
> com wildcard, edge-TLS-no-Route e layering de proxy. O risco do #1504 é exclusivo do
> OIDCPolicy (login de browser no gateway).

## Verificação dos componentes do Kuadrant (Authorino & data plane)

Validar pela borda (curl 401/403/200) prova o comportamento; para **entender e
depurar**, olhe a cadeia de componentes que a `AuthPolicy` gera. Uma `AuthPolicy`
**não é executada diretamente** — o Kuadrant a traduz numa `AuthConfig` do
Authorino, e o Envoy do Gateway chama o Authorino via `ext_authz` (gRPC),
configurado por um `WasmPlugin` + `EnvoyFilter`.

```
AuthPolicy (kuadrant.io, ns rhcl-apps)
   │  kuadrant-operator traduz
   ▼
AuthConfig (authorino.kuadrant.io, ns kuadrant-system)   ← config de runtime
   │  Authorino busca JWKS do issuer e avalia
   ▼
Authorino (deploy/authorino)  ◄── ext_authz gRPC ── Envoy do Gateway
                                   (WasmPlugin + EnvoyFilter kuadrant-auth)
```

### 1. A `AuthPolicy` foi aceita e está em vigor?

```bash
oc -n rhcl-apps get authpolicy banking-api-connectivity-apikey \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
# Esperado: Accepted=True e Enforced=True.
# Se Enforced=False → geralmente OUTRA AuthPolicy mira o mesmo target (só uma
# fica Enforced por target; a outra vira "Overridden"). A message diz o motivo.
```

### 2. A `AuthConfig` gerada — onde confirmar que a policy "virou" config

O Kuadrant gera **uma `AuthConfig` por rota/regra protegida** (em `kuadrant-system`),
com **nome e `spec.hosts` em HASH** (não o hostname real — é a chave usada no wasm).
Por isso ache a sua pelo **conteúdo**, não pelo host:

```bash
# Quais AuthConfigs e se estão prontas:
oc -n kuadrant-system get authconfig          # coluna READY deve ser true

# Inspecionar a tradução (issuer JWT + authZ + headers de claim):
oc -n kuadrant-system get authconfig -o json | python3 -c '
import sys,json
for ac in json.load(sys.stdin)["items"]:
    s=ac["spec"]; a=s.get("authentication",{})
    if "jwt-keycloak" in a:
        print("authconfig:", ac["metadata"]["name"], "ready:", ac.get("status",{}).get("summary",{}).get("ready"))
        print("  issuerUrl:", a["jwt-keycloak"]["jwt"]["issuerUrl"])
        print("  authorization:", list(s.get("authorization",{}).keys()))
        print("  headers p/ backend:", list(s.get("response",{}).get("success",{}).get("headers",{}).keys()))
        break'
```

> **`READY=true` é o sinal-chave do OIDC/JWT**: significa que o Authorino conseguiu
> buscar o `.well-known/openid-configuration` + o **JWKS** do issuer. Se o issuer
> estiver inacessível, com cert não-confiável, ou `iss` divergente, a AuthConfig
> fica `ready:false` e **"token válido vira 401"**. É o primeiro lugar a checar.

### 3. Authorino — o motor de decisão (logs por request)

```bash
oc -n kuadrant-system get authorino authorino                       # réplicas, logLevel
oc -n kuadrant-system get pods -l authorino-resource=authorino      # Running/Ready

# Logs (a fonte de verdade por request): qual identidade casou, resultado da
# validação do JWT (assinatura/iss/aud/exp) e o motivo da negação de authZ:
oc -n kuadrant-system logs deploy/authorino -f

# Detalhe verboso (sobe pra debug; rola o pod):
oc -n kuadrant-system patch authorino authorino --type=merge -p '{"spec":{"logLevel":"debug"}}'
# procurar: fetch do JWKS, linhas "authenticated"/"authorization rejected"
```

### 4. Data plane — o Envoy do Gateway chama o Authorino

```bash
# Wiring ext_authz (→ Authorino) e rate-limit (→ Limitador) no Gateway:
oc -n openshift-ingress get wasmplugin,envoyfilter
#   wasmplugin/kuadrant-rhcl-apps-gateway
#   envoyfilter/kuadrant-auth-rhcl-apps-gateway          (ext_authz → Authorino)
#   envoyfilter/kuadrant-ratelimiting-rhcl-apps-gateway  (→ Limitador)

# Logs do Envoy do Gateway (vê 401/403/200 e idas ao ext_authz):
oc -n openshift-ingress logs deploy/rhcl-apps-gateway-openshift-default
```

### 5. Kuadrant operator — quem traduz AuthPolicy → AuthConfig

```bash
oc -n kuadrant-system get kuadrant kuadrant \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'     # Ready=True
oc -n kuadrant-system logs deploy/kuadrant-operator-controller-manager | grep -iE 'error|authpolicy'
```

> **Visão na console**: o RHCL console plugin (OCP Console → seção Kuadrant)
> desenha a topologia das policies anexadas a Gateway/HTTPRoute.

### Sintoma → onde olhar

| Sintoma | Componente a inspecionar |
|---------|--------------------------|
| Token válido → **401** | AuthConfig `READY` (fetch do JWKS); `authorino` logs; `iss` do token == `issuerUrl` |
| Token válido → **403** | regra de authZ na AuthConfig (`jwt-require-role`); `authorino` debug "authorization rejected"; a claim existe no token? |
| **Preflight CORS** falha | regra `cors-preflight` (OPTIONS) + authZ excluindo OPTIONS (ver fix do #1504/CORS) |
| Policy não fica **Enforced** | conflito de AuthPolicy no mesmo target; logs do `kuadrant-operator` |
| Claims **não chegam** no backend | `response.success.headers` na AuthConfig; selector nulo = claim ausente (header omitido) |

> **Itens de rate limit** (61–65): o componente equivalente ao Authorino é o
> **Limitador** — `oc -n kuadrant-system get limitador`, `logs deploy/limitador-limitador`,
> e os contadores no Redis. Ver [`req061-65-RateLimit`](req061-65-RateLimit/README.md).

## Limpeza

```bash
# Standalone (equivalente ao rhbk-remove.yml)
oc delete namespace keycloak                     # apaga Keycloak + realm + tudo
oc -n openshift-ingress delete dnsrecord.kuadrant.io keycloak-rhcl --ignore-not-found

# Desligar o JWT no gateway (uma das duas opções)
oc -n rhcl-apps patch authpolicy banking-api-connectivity-apikey --type=json \
  -p '[{"op":"remove","path":"/spec/rules/authentication/jwt-keycloak"}]'
# OU, se preferir o role apps gerenciando:
APPS_CONNECTIVITY_JWT_ENABLED=false ansible-playbook automation/playbooks/apps-install.yml -e apps_skip_build=true

# Batch alternativo:
cd automation && ansible-playbook playbooks/rhbk-remove.yml
```
