Scenario 1 Global, same site

A simple global RLP on the HTTPRoute. Counters shared across Gateway instances behind the same Limitador.

Apply the policy

oc apply -f manifests/01-global-same-site.yaml

Fire load (CLI alternative)

HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')

# 60 requests IN PARALLEL against /api/echo. Sequential does not exceed the
# 10s window because of the TLS handshake — use ampersand + wait.
{ for i in $(seq 1 60); do
    curl -sk -o /dev/null -w "%{http_code}\n" "https://$HOST/api/echo" &
  done; wait; } | sort | uniq -c
# Expected with policy 20/10s: 20x 200 + 40x 429

Scenario 3 Gateway + API together

A Gateway-level RLP with defaults coexisting with an API-level RLP (HTTPRoute). Demonstrates how RHCL resolves conflicts between policies at different levels.

Apply both policies

# API-level (HTTPRoute)
oc apply -f manifests/01-global-same-site.yaml

# Gateway-level (with defaults)
oc apply -f manifests/04-api-vs-gateway.yaml

# View the policies
oc get ratelimitpolicy -A -l app.kubernetes.io/part-of=rhcl-req61-65-ratelimit

A request must pass both limits; the more restrictive one wins.

Force a non-negotiable ceiling (overrides)

To make the Gateway-level limit non-negotiable, edit manifests/04-api-vs-gateway.yaml changing defaults: to overrides:. After that, even an API team setting 100000/s in its policy cannot exceed the ceiling set at the Gateway.

Reuse the Run buttons above (Scenario 1 or 2) to validate the outcome — any burst exceeding the more restrictive limit falls to 429.

Troubleshooting

SymptomDiagnosis
No 429 even after many sequential requests Sequential curl adds ~200ms between reqs due to the TLS handshake. The 10s window may not be exceeded. Use parallel: { for i in ...; do curl … & done; wait; }
Too many 429 (all requests) The counter is blocking. Check the window — short windows (1s) plus delays can confuse it. Use 1m in the demo.
Limitador CrashLoops after applying an RLP with request.headers["..."] Quoting bug: double quotes inside the CEL nest into the descriptor key unescaped. Use single quotes: request.headers['x-customer-id'].
An RLP with 3+ limits entries applies nothing Observed when one entry uses auth.identity and another uses only request.*. Limit to 2 entries in limits per RLP, or compose separate RLPs with distinct sectionName.
The Gateway RLP has no effect When both (Gateway-level defaults and API-level) coexist, API-level wins. For an absolute ceiling use overrides: at the Gateway level.
Multiple RLPs Enforced=False/Overridden Only one RLP per target is enforced. For composition, use distinct targets (HTTPRoute + Gateway with overrides) or sectionName to target specific rules.

Scenario 4 Shared Redis (externalized state)

By default, Limitador keeps counters in memory in its own pod. For true global rate limiting (and multi-site), the state must move to an external store. Here we use a Redis in the same cluster, in a dedicated shared-store.

Step 1 — Bring up Redis in shared-store

oc apply -f manifests/06-redis-shared-store.yaml
oc -n shared-store rollout status deploy/redis

# Sanity check
POD=$(oc -n shared-store get pod -l app=redis -o jsonpath='{.items[0].metadata.name}')
oc -n shared-store exec $POD -- sh -c 'redis-cli -a "$REDIS_PASSWORD" ping'
# PONG

Step 2 — Point Limitador at Redis

oc apply -f manifests/02-limitador-redis.yaml
oc -n kuadrant-system rollout status deploy/limitador-limitador

# Confirm the storage
oc -n kuadrant-system get limitador limitador -o jsonpath='{.spec.storage}'; echo

Step 3 — Validate (counters now live in Redis)

oc apply -f manifests/01-global-same-site.yaml
HOST=$(oc get httproute banking-api-connectivity -n rhcl-apps -o jsonpath='{.spec.hostnames[0]}')

{ for i in $(seq 1 60); do
    curl -sk -o /dev/null -w "%{http_code}\n" "https://$HOST/api/echo" &
  done; wait; } | sort | uniq -c
# Expected with 01 (20/10s): 20x 200 + 40x 429

# PROOF — the state is in Redis (not the pod's memory):
POD=$(oc -n shared-store get pod -l app=redis -o jsonpath='{.items[0].metadata.name}')
oc -n shared-store exec $POD -- sh -c 'redis-cli -a "$REDIS_PASSWORD" --scan' \
  | grep -i counter
# namespace:{rhcl-apps/banking-api-connectivity},counter:{"limit":...}

Scenario 4 Multi-cluster — 2 clusters sharing counters

Each cluster runs its own Limitador, but all point at the same Redis. Validated across two independent OpenShift clusters (distinct AWS sandboxes, both us-east-2).

ClusterRole

# (Cluster B) limitador-redis Secret URL:
#   redis://default:<password>@$REDIS_LB:6379/0

Where the limit comes from — the RateLimitPolicy

The 20/10s is not infra config: it is declared in a RateLimitPolicy attached to the HTTPRoute. It is the SAME policy (manifests/01-global-same-site.yaml) from the earlier scenarios — and it must exist identically on both clusters: 

apiVersion: kuadrant.io/v1
kind: RateLimitPolicy
metadata:
  name: req061-global-same-site
  namespace: rhcl-apps
spec:
  targetRef:                      # attaches to the HTTPRoute (not the Gateway)
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: banking-api-connectivity
  limits:
    global-burst:
      rates:
        - limit: 20               # ← THE LIMIT: 20 requests…
          window: 10s             # ← …per 10s window

Show it live on each cluster before the test — the spec.limits must be identical on both sides (that is what guarantees the same counter key): 

# run on EACH cluster (A and B) — must print exactly the same thing:
oc get ratelimitpolicy req061-global-same-site -n rhcl-apps \
  -o jsonpath='{.spec.limits}{"\n"}'
#   {"global-burst":{"rates":[{"limit":20,"window":"10s"}]}}

# and confirm Kuadrant accepted AND is enforcing the policy on both:
oc get ratelimitpolicy req061-global-same-site -n rhcl-apps \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {end}{"\n"}'
#   Accepted=True Enforced=True

Counter identity

Both Limitadors must compute the same counter identity. Since the counter namespace is {ns-da-route}/{nome-da-route} (rhcl-apps/banking-api-connectivity) and the descriptor is derived from the RLP content, just apply the same HTTPRoute (same name/namespace) + the same RateLimitPolicy on both clusters — Kuadrant then generates the identical key (limit.global_burst__69c1664f, namespace rhcl-apps/banking-api-connectivity).

⚠️ redis vs redis-cached

O 02-limitador-redis.yaml usa redis-cached, which keeps a local counter cache per site and syncs to Redis in batches (flush-period). This optimizes latency/availability, but does NOT guarantee a strict global limit: a site with a "cold" cache admits requests before seeing the others' usage.

Storage Sequential test (A:18 → B:18, limit 20/10s) Behavior
redis-cached A=18×200, B=18×200 (36 total) Local per-site cache → over-admits. Eventually consistent.
redis A=18×200, B=5×200 + 13×429 (≈23 total) Every check hits Redis → strict global limit.

For a strict global limit across sites, switch the storage to pure redis on both clusters: 

oc -n kuadrant-system patch limitador limitador --type=json \
  -p '[{"op":"replace","path":"/spec/storage","value":{"redis":{"configSecretRef":{"name":"limitador-redis"}}}}]'
oc -n kuadrant-system rollout status deploy/limitador-limitador

Cross-cluster validation (with strict redis)

# Consume most of the budget on cluster A, then hit B
for i in $(seq 1 18); do
  curl -sk -o /dev/null "https://$HOST_A/api/echo" &
done; wait    # ~18x 200

sleep 1

for i in $(seq 1 18); do
  curl -sk -o /dev/null "https://$HOST_B/api/echo" &
done; wait    # maioria 429
# Cluster B sees A's usage via the shared counter
# → caps at the same 20/10s.

# PROOF of the single counter: the SAME Redis key rises with traffic from ANY site
POD=$(oc -n shared-store get pod -l app=redis -o jsonpath='{.items[0].metadata.name}')
oc -n shared-store exec $POD -- sh -c \
  'redis-cli -a "$REDIS_PASSWORD" --no-auth-warning --scan --pattern "*global_burst*"'
# 0 → 5 (after 5x on cluster A) → 10 (after 5x on cluster B): one counter, two sites.
Small overages (e.g. 23 instead of 20) are normal under concurrency against any distributed counter — check-then-increment is not atomic on a burst.
Production — the 06-redis-shared-store.yaml Redis uses emptyDir (volatile) and no TLS (intra-cluster traffic). For production: PVC + replication/Sentinel or a managed Redis, and rediss:// (TLS) in the URL.
