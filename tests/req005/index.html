REQ 05

Balanceamento de carga por peso origin: …

Demonstra que o gateway (RHCL / Gateway API) distribui o tráfego entre as duas versões do banking-api (banking-api-v1 e banking-api-v2) segundo o campo weight de cada backendRef da HTTPRoute. Como os dois Deployments rodam a mesma imagem, o path neutro escolhido (/api/whoami) é servido por ambos; o campo instance da resposta (banking-api-v1 ou banking-api-v2) identifica qual Service o gateway escolheu em cada chamada. Um filtro RequestHeaderModifier por backendRef ainda injeta x-route-version: v1|v2 antes do encaminhamento, e o backend ecoa esse cabeçalho em allHeaders — um segundo sinal independente do split.

Cenário

[ cliente ]                       [ RHCL / Gateway ]                   [ backends ]
    |                                       |                                 |
    |  GET /api/whoami                      |                                 |
    |-------------------------------------->|                                 |
    |                                       |  weight: v1=90 / v2=10          |
    |                                       |                                 |
    |                                  ┌────┴────┐                            |
    |                                  │ ~90%    │ injeta x-route-version: v1 |
    |                                  │         │------------------------->  |
    |                                  │         │                  banking-api-v1
    |                                  │         │ <-------------------------|
    |                                  │         │ instance=banking-api-v1    |
    |                                  ├─────────┤ allHeaders[x-route-version]=v1
    |                                  │ ~10%    │ injeta x-route-version: v2 |
    |                                  │         │------------------------->  |
    |                                  │         │                  banking-api-v2
    |                                  │         │ <-------------------------|
    |                                  │         │ instance=banking-api-v2    |
    |                                  └─────────┘ allHeaders[x-route-version]=v2
    |  HTTP 200 OK { instance, allHeaders, … }                                |
    | <--------------------------------------|                                |
O que esta página prova. Disparando N requisições sequenciais (ou em paralelo) contra o mesmo path neutro, o gateway seleciona um backend por chamada respeitando os pesos da HTTPRoute. A página tabula instance (e o eco de x-route-version) de cada resposta e compara a proporção observada com a esperada. Em amostras pequenas o desvio é normal — aumente N para ver a distribuição convergir.
Por que não URLRewrite por backendRef? O controller openshift.io/gateway-controller/v1 (Istio) declara URLRewrite apenas em HTTPRouteRule.filters, não em HTTPBackendRef.filters. Aplicando-o por backendRef o recurso vira com ResolvedRefs=False, reason=InvalidFilter, message="unsupported filter type URLRewrite". Por isso o demo usa um path que existe nos dois pods e o sinal vem de RequestHeaderModifier (suporte core no Istio) + instance da resposta.

Distribuição por instance

O campo instance da resposta vem do env APP_INSTANCE_NAME do Deployment — vale banking-api-v1 ou banking-api-v2. Réplicas do mesmo Deployment compartilham o valor (não é o hostname do pod). A coluna x-route-version é o eco, vindo de allHeaders, do header injetado pelo RequestHeaderModifier em cada backendRef — confirmação independente da escolha do gateway.

Atalhos de comparação /api/v1 e /api/v2

A mesma HTTPRoute também publica dois atalhos sem reescrita: /api/v1/accounts/summary sempre vai ao banking-api-v1 e /api/v2/accounts/summary sempre vai ao banking-api-v2. Útil para confirmar que os Services estão saudáveis antes de tirar conclusões da amostra com peso.
