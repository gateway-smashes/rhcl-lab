API product via the admin API

RHCL Lab · Create and fully configure an API product via the Kubernetes API

The requirement

"Allow creating and fully configuring an API product through an administrative API."

In RHCL/Kuadrant, the admin API IS the Kubernetes API. Every piece of a product is a CRD exposed at /apis/<group>/<version>/.... Any HTTP client (curl, Postman, Python, Go) with a Bearer token from an RBAC-scoped SA can create, update, list and delete an entire product — no console, no GitOps, no Ansible.

This demo creates the pix-api product end-to-end two ways: declarative (oc apply) and raw REST (curl + SA token, zero oc). Both reach the same state and prove the requirement.

Model: what makes up an API product

All the CRs below are manipulable via the Kubernetes REST API. This demo creates them all:

CRGroup / VersionRole
HTTPRoutegateway.networking.k8s.io/v1Roteamento, matches, filtros (URLRewrite, headers)
APIProductdevportal.kuadrant.io/v1alpha1Metadados (displayName, version, publishStatus, tags, contact)
PlanPolicyextensions.kuadrant.io/v1alpha1Tiers e rate limit por plano (predicate CEL)
AuthPolicykuadrant.io/v1Auth (api-key/jwt/anonymous) + response headers
Secret (api-key)v1 (core)Valor da chave + annotations da identidade
APIKeydevportal.kuadrant.io/v1alpha1Key request/approval (governance)
Role + RoleBindingrbac.authorization.k8s.io/v1Permissions for whoever operates via the API

Demo: criar o produto pix-api

The most idiomatic path: oc apply for each manifest, plus a smoke test.

cd tests/req031
./scripts/create-via-oc.sh

O script descobre o host do banking-api-connectivity, aplica os 6 manifests, aguarda AuthPolicy.Enforced=True, e faz o smoke test:

TesteEsperado
curl /pix/v1 sem api-key401
curl /pix/v1 com api-key200

The point: no proprietary tooling — just HTTP + Bearer.

cd tests/req031
./scripts/create-via-k8s-api.sh

O script:

  1. Applies 06-rbac.yaml via oc (the only cluster-admin step — creates the SA req031-product-admin).
  2. Mints an ephemeral (1h) SA token via oc create token.
  3. Creates each CR via curl POST $APISERVER/apis/... authenticated by the Bearer token only.
  4. Lista os APIProducts via curl GET pra confirmar.
  5. Smoke test 401/200.

Example raw POST to create the APIProduct (extracted from the script):

APISERVER=$(oc whoami --show-server)
TOKEN=$(oc -n rhcl-apps create token req031-product-admin --duration=1h)
curl -sk -X POST \
  "$APISERVER/apis/devportal.kuadrant.io/v1alpha1/namespaces/rhcl-apps/apiproducts" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/yaml" \
  --data-binary @manifests/01-apiproduct.yaml
In production the token would come from a Workload Identity (SPIFFE/OIDC) or an OIDC-federated client, not a long-lived SA token. The demo uses an ephemeral (1h) SA token for simplicity.

To explore by hand, without running the scripts:

HOST=$(oc -n rhcl-apps get httproute banking-api-connectivity \
       -o jsonpath='{.spec.hostnames[0]}')
KEY=$(oc -n rhcl-apps get secret pix-api-key-tester \
      -o jsonpath='{.data.api_key}' | base64 -d)

# sem auth -> 401
curl -sk -o /dev/null -w "%{http_code}\n" "https://$HOST/pix/v1"

# com auth -> 200
curl -sk -o /dev/null -w "%{http_code}\n" -H "api-key: $KEY" "https://$HOST/pix/v1"

# burst -> 5x 200 + 2x 429 (plano bronze, 5/min)
for i in $(seq 1 7); do
  curl -sk -o /dev/null -w "%{http_code} " -H "api-key: $KEY" "https://$HOST/pix/v1"
done; echo

Listar o produto via REST puro com SA token:

APISERVER=$(oc whoami --show-server)
TOKEN=$(oc -n rhcl-apps create token req031-product-admin --duration=10m)
curl -sk -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/apis/devportal.kuadrant.io/v1alpha1/namespaces/rhcl-apps/apiproducts/pix-api" \

Caveats / pegadinhas

  • Dev portal enabled: the APIProduct only reconciles if Kuadrant.spec.components.developerPortal.enabled=true. Without it the CR is created but not reconciled — auth + rate limit still work (straight from AuthPolicy/PlanPolicy).
  • 1 AuthPolicy + 1 RateLimitPolicy per HTTPRoute: PlanPolicy replaces RateLimitPolicy (don't use both on the same route).
  • Path-based: este produto reusa o host do banking-api. Pra um produto em host separado, adicionar um listener no Gateway (fora do escopo do item 31).
  • Secret vs APIKey CR: real auth is via the Secret (label-selected by the AuthPolicy). The APIKey CR is a governance object (request/approve); on approval the developer-portal-controller materializes its own Secret. This demo uses a fixed-value Secret for reproducibility.
